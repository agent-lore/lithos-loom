# Lithos Loom — Specification

Version: 0.1.0
Date: 2026-05-29
Status: Aligned with Implementation

---

## 1. Goals

### 1.1 Primary Goals

1. **Project Lithos work into Obsidian.** Render open Lithos tasks the operator needs to see as Tasks-plugin-compatible lines in a vault file, so that an existing Obsidian daily-view workflow surfaces Lithos work alongside personal todos.
2. **Push vault-side edits back to Lithos.** Tick-to-complete, priority emoji edits, due-date edits, and project-context body edits made in Obsidian propagate to Lithos with optimistic locking.
3. **Capture Lithos work from inside Obsidian.** Templater macros for creating tasks and project-context docs let the operator stay in the editor.
4. **Adopt existing Obsidian project docs into Lithos.** A `project import` CLI extracts `- [ ]` task lines as real Lithos tasks with dependency edges derived from indentation.
5. **Run subprocess plugins against Lithos tasks.** A route-runner child claims tasks by tag, invokes a plugin subprocess with a small contract, and applies the result back to Lithos.
6. **Stay out of project repos.** Loom configuration is host-local TOML; project repo `AGENTS.md` / `CLAUDE.md` files carry no Lithos / Loom references.

### 1.2 Non-Goals

1. **Cloud sync, multi-tenant operation, web UI.** Single-operator, local-first. Obsidian Sync (or any other vault-sync layer) is the operator's choice.
2. **Real-time co-editing.** File-based, poll-driven; latency target is ≤500ms end-to-end for projection + push.
3. **Replacing Lithos as the source of truth.** Lithos owns the corpus and the task lifecycle. The vault is a projection plus a write surface for specific edits.
4. **Cross-host coordination.** The vault host is the only host running `obsidian-sync`; other hosts run headless route-runners. Loom does not coordinate across hosts via shared state.
5. **Reopening a completed task.** Lithos exposes no `task_reopen` primitive. Untick (`[x] → [ ]`) posts a `[ReopenRequested]` finding instead.
6. **Plugin bodies for PRD decomposition, story implementation, story review.** Scaffolding exists in `src/lithos_loom/plugins/`; the implemented surface stops at the orchestration spine plus the Obsidian bridge. Generating PRDs, reviewing diffs, and brain-driven decisions are not implemented today.

### 1.3 Compatibility Policy (Pre-1.0)

1. **TOML schema evolves.** Field renames or removals require a documented migration step but are otherwise free.
2. **Event names are stable.** Subscribers depend on dotted event names (`lithos.task.created`, `obsidian.note.modified`); changing them is a breaking change.
3. **`result.json` schema is versioned.** Plugins ship a `schema_version` integer; incompatible changes bump it.
4. **Vault-projected file layout is stable.** `_lithos/tasks.md`, `_lithos/awaiting-review.md`, `_lithos/projects/<slug>/<file>.md`, `_lithos/conflicts/<slug>.<file>.<ts>.md` are documented locations operators query and grep against.

## 2. Architecture

### 2.1 Component Overview

Loom is structured as `sources → bus → subscribers`. Sources publish typed events onto an in-process async bus; subscribers consume them. The route-runner is a special claim-bound subscriber that owns a task's lifecycle to `result.json`.

### 2.2 Data Flow

**Task projection (Lithos → vault).**
`LithosEventStream` connects to `<lithos_url>/events` filtered to `task.*` events. It bootstraps once on connect by calling `lithos_task_list(status='open', with_claims=true)` and re-emitting `lithos.task.created` for every open task, then streams live events with `Last-Event-ID` resume. `obsidian-projection` filters via `is_human_actionable(task, routes)` and rewrites `<vault>/<tasks_file>` atomically.

**Status push (vault → Lithos).**
`ObsidianFSWatcher` polls `<vault>/<tasks_file>` (default 250ms), parses line-by-line, and emits `obsidian.task.status_changed`, `obsidian.task.priority_changed`, or `obsidian.task.due_date_changed` when a line diverges from the last-known state. Self-write suppression compares mtime + content hash against the projection's last write. Three subscriptions consume these events and call `lithos_task_complete` / `_cancel` / `_update` against Lithos.

**Project-context projection (Lithos → vault).**
`LithosNoteStream` connects to `/events` filtered to `note.*` events; bootstrap calls `lithos_list(path_prefix='projects/', tags=['project-context'])` and re-emits `lithos.note.created` for each match. `project-context-projection` re-fetches via `lithos_read` (events are summaries; tags need verification post-fetch), then writes `<vault>/<projects_dir>/<slug>/<filename>.md` with a frontmatter envelope.

**Body push (vault → Lithos).**
`ObsidianDirWatcher` polls `<vault>/<projects_dir>/**/*.md` (default 250ms), computes body-only hash, and emits `obsidian.note.modified` when divergent. `note-push` calls `lithos_write(id=..., expected_version=...)`. On `version_conflict`, the conflict resolver moves the operator's body to `<vault>/_lithos/conflicts/<slug>.<file>.<ts>.md`, pulls canonical to the original path, and logs a `[Friction]` WARNING.

**Task lifecycle (route-runner).**
`LithosEventStream` (running in the route-runner child) emits `lithos.task.*` events. Each `[[routes]]` stanza registers a claim-bound subscriber against `lithos.task.created`, `lithos.task.updated`, and `lithos.task.released` that requires every tag in `match.tags` to be present on the task (same semantic as the bus matcher and `is_human_actionable`). Since #86, editing a task's tags after creation re-triggers route pickup **without a daemon restart**: the tag edit arrives as `lithos.task.updated` (force-refreshed by the source into the full task envelope) and matches exactly as `created` would. `updated` is treated as "re-evaluate match," not "always run" — a plugin's own end-of-run `task_update` (e.g. `story-develop` writing `develop_*` metadata) fires `updated` but cannot self-trigger a re-run, because the task is already in the runner's in-process claim-dedup set; for `completes_task = false` routes the delivered story's `pr` gate additionally keeps it off `lithos_task_ready` across a restart (US11 retired the `loom_delivered` marker that used to do this). On match, the runner asks Lithos whether the task is actually dispatchable — `lithos_task_ready(tags=match.tags, project=…)`, the server-side ready frontier (**Epic G / US4**). A task behind an unsatisfied `blocks` predecessor, an unmet gate, or a cycle is simply absent from that frontier, and the runner defers; it no longer derives readiness itself from `metadata.depends_on`, so readiness (including the rule that a *cancelled* blocker keeps its dependents blocked) is computed once, server-side, and shared with every other agent. `lithos_task_ready` has no per-task filter, so the check is a membership test over a frontier narrowed to the route's tags and (when declared) the task's `metadata.project`, capped at `READY_QUERY_LIMIT` (500). A **full page** means the frontier was truncated, which makes absence from it meaningless — the runner then reads the task fresh and classifies it by its **own** project + tags with the blocked page as the other half of the partition (`dispatch_guards.classify_readiness`, shared with the pr-gate resolver's recovery; PR #352 review). Only both pages full is undetermined, and an undetermined (or unreadable) task is **re-checked** rather than dropped — one coalesced sleeper per task, backing off from `READY_RECHECK_SECONDS` (60) to `READY_RECHECK_MAX_SECONDS` (900) and never giving up — re-armed after every republish, since the bus is fire-and-forget and a full route queue drops an event silently — until the runner's definitive answer resets it (a restart's bootstrap replay re-asks too) — a nudge for a released dependent used to be lost here. Deferring is the safe direction: nothing dispatches on a guess; the inverse mistake would dispatch a task whose blocker is still open, which is exactly what this gate exists to prevent. Once ready, the runner claims via `lithos_task_claim`, spawns the plugin subprocess, periodically renews the claim, and waits for `result.json`. It then reads only the `status` field:

**Serial admission (PRD pr-reconciliation S6).** A PR-producing route (`completes_task = false`) claims a ready story only while the project's **open `pr` gates** — delivered-but-unmerged PRs — are under `[orchestrator] max_open_delivered_prs` (default **1**). Readiness is Lithos's answer first; then the runner counts the project's open `pr` gates with one filtered `lithos_task_list` (`task_type=gate`, `metadata_match={gate_type: pr, project: <slug>}`). It counts **gates, not claims** — the distinction `max_concurrency` misses: once delivery releases its claim, the next story would otherwise start while the first PR is still unmerged — plus this process's admitted-but-not-yet-delivered runs, so a second PR-producing route on the same project cannot slip a story past the count while the first is still running. Each reservation is keyed by **(route, story)**: a task may match several PR-producing routes, each a run that delivers its own PR, so each takes a slot and one route's release never erases another's. A reservation is released when its run ends, whatever the outcome, or when the claim is lost. **Escalated** gates — whose story carries an open loom `human` gate, matched by the `pr` gate's `metadata.story_id` (recorded since S6) or, for older gates, its `waits_on_gate` edge — do not count against the limit (operator decision 2026-08-24: a decision the operator owes is not loom's work-in-progress, and counting it would turn operator latency into a project stop). A gate whose story is already **terminal** (completed by hand, or by the issue mirror when the work landed via another PR, while the delivered PR stayed open — #372) counts against neither dial: that PR is the operator's, not loom's work-in-progress, and the watcher sweep completes such a gate on its next pass; the waiter is read only when a cap is in question, and an unreadable or gone waiter keeps its gate counted (fail closed). A looser backstop, `max_open_delivered_prs_total` (default **3**), counts every open `pr` gate including escalated ones; reaching it stops dispatch and posts `[AdmissionHeld]` on the refused story, once per project per daemon process. Both dials are overridable per project in the project-context doc's metadata under the same keys; `0` = unlimited; a project total below its limit is raised to the limit. Fail closed: an unreadable gate list holds the story, an unreadable human-gate list counts every gate, and an unreadable context doc holds the story too (a project may tighten the host defaults, so an unknown dial is an unknown limit). A held story is **not claimed and carries no marker**: it is remembered in-process and re-evaluated when the **admission waker** (a subscriber in the route-runner child on gate `created` / `completed` / `cancelled` events) sees a `pr` gate close or a loom `human` gate escalate one in its project — a synthetic `lithos.task.updated` with `origin="admission-recheck"` — with the readiness re-check sleeper (exponential backoff to 15 min) as the fallback, since the bus is fire-and-forget; a restart's bootstrap re-asks every open story afresh. **Release order ([ADR 0012](adr/0012-admission-release-order.md), 561db86a):** when a slot frees and several held stories want it, the story's `metadata.priority` decides first (`highest` › `high` › `medium` › *none* › `low` › `lowest` — the default sits in its Obsidian place, so `medium` and above jump the queue and `low` / `lowest` yield to unmarked work), and within one rank the order the stories first asked admission in this process (one story's waits under several routes run in the order they ask — the guarantee is which story leaves, not which of its routes): a refusal re-asked keeps its place, so does a story whose run ended without a gate and asks again, a newcomer joins the back, and the priority is read when the slot frees — marking a waiting story up (Obsidian, lens, `lithos_task_update`) is the operator's lever. The choice is made **inside `Admission`** under the bucket lock, not by whichever producer publishes first: with more askers than free slots, an asker outside the first *free* places is refused (`queued`) and those places are nudged with the same synthetic event (every free slot is filled when the limit allows more than one), so the re-check sleeper cannot pre-empt the waker's sweep and the same inputs always release the same story. Every transition that can free a place re-nudges the bucket in order — a gate event, an admission that leaves slots free, a run that ends without a gate, a head that leaves the queue — after counting the headroom, so a full bucket nudges nobody; the sleeper stays the fallback for a dropped nudge. Starvation by priority is accepted and stated (the operator set it; within a rank there is none). A head that never asks is the one way this fails (a stall, never a spin), so a held story the runner cannot place on the ready frontier (**not ready**, undetermined, or unreadable) gives up that route's wait, a wait whose story **no longer carries its route's match tags** (re-tagged to park it, or onto another route) is dropped at the next pick, and a story nudged as next ten times without asking is named in the log — the story keeps its **place** through all of that, so a Lithos blip that drops every wait does not reorder the queue; a story that cannot be read (for any reason) keeps its place at the rank it was last seen and is not nudged (its own sleeper re-asks; one failed read never loses the rest of the sweep); one no longer open is forgotten, and its terminal event releases the scheduler's memory of it; a story held in one project and moved or admitted under another leaves no phantom wait behind, and the bucket it left is woken. Counting is per project, not per base branch (a `pr` gate records no base); stories and gates that name no `metadata.project` (a route with an absolute repo path needs none) share one **projectless bucket** under the host defaults — a projectless story is bounded by the projectless `pr` gates, never exempt. Each bucket's read → decide → reserve transition runs under a per-bucket lock, so the route runners sharing the one admission gate cannot both admit on the same snapshot while a human-gate read is in flight. The exclusion of an escalated gate is keyed on the loom `human` gate's `waits_on_gate` **edge**, not its `story_id` metadata: gate creation is not atomic, and a gate task whose edge never landed blocks nothing, so it must not free a slot. Any other exception on a read — the client re-raises raw transport errors once its reconnects are spent — holds the story rather than escaping and dropping the event. Ordinary routes (`completes_task = true`) are never held.

- `succeeded` → `lithos_task_complete` — **unless** the route sets `completes_task = false` (§3.1), in which case the runner instead raises a first-class **`pr` gate** (**Epic H / US10**), records `metadata.pr_gate_id` on the story (provenance), and `lithos_task_release`s, leaving the task **open**. This is for PR-producing routes (e.g. `story-develop`) where success = "a reviewed branch + PR exist, awaiting human merge", not "done": completing on approval would close a github-linked issue for un-merged work. The gate is a `task_type="gate"` task carrying `metadata.gate_type="pr"` (repo / pr_number / pr_url / `required_state="merged"`), joined to the story by a `waits_on_gate` edge (from=gate, to=story), so the story is **structurally blocked** — absent from `lithos_task_ready` until the gate resolves, undispatchable with no Loom-private marker. The runner builds it from `result.json`'s `pr_url` (parsed with `parse_github_ref`) and, on success, records `metadata.pr_gate_id = <gate>` on the story so the merge resolver (§2.2 PR-gate resolver) owns the story's lifecycle. Gate creation is **best-effort** but load-bearing: if it fails, or the run is `succeeded` with no `pr_url`, no gate exists and the runner posts a loud `[Friction]` — there is no fallback (US11 retired `loom_delivered`), so a restart could re-develop the delivered story into a duplicate PR until a human merges the PR or creates the gate. Completion then happens on PR merge — github-issue-linked tasks via the issue close-mirror, and (since #87) non-issue tasks via the github-watcher's PR-gate resolver (see §2.2; otherwise the operator). The `pr` gate keeps a delivered story off `lithos_task_ready`, so a daemon restart's bootstrap (which re-emits every open task as `created`) does not re-develop it — the runner's readiness check defers it. (US11 replaced the old `loom_delivered` guard, which special-cased `completes_task = false` routes, with this single readiness guard for every route. **Failed** stories are guarded separately: they stay on the ready frontier, so the runner declines a bootstrap-replayed event when `metadata.loom_last_attempt:<route>` records a failed last attempt for an unchanged task — see the `failed` bullet below.) `lithos_task_complete` **returns the tasks whose last blocker this completion just cleared**, and the runner republishes each of them onto its bus as a synthetic `lithos.task.updated` (**Epic G / US6**) — so the next task in a chain dispatches off the completion itself instead of waiting for a Lithos round-trip. Routing the nudge through the bus (rather than re-entering the runner directly) means it reaches whichever route matches the unblocked task — usually a *different* route than the one that just finished — and it re-enters the same ready-check + collision-safe claim path, so a double-evaluation is harmless. Two boundaries: the nudge is confined to the route-runner child (children each run their own bus with no IPC), so a task completed elsewhere — e.g. by the github-watcher on PR merge — still relies on the event stream / restart bootstrap; and a failure to nudge is logged but never fails the already-completed task.
- `failed` → **needs-human escalation** (b91177d2): the run ended without delivering, so the runner raises a first-class loom **`human` gate** on the story — `task_type="gate"`, `metadata.gate_type="human"`, `raised_by="loom"`, joined by a `waits_on_gate` edge (from=gate, to=story) — so the story is **structurally blocked** exactly as a delivered story is by its `pr` gate: absent from `lithos_task_ready`, undispatchable on every origin including a restart's bootstrap. The gate is the operator's decision, not a status: title `Needs human: <story title>`, tags `project:<slug>` + `needs-human`, a closed-vocabulary `metadata.escalation_reason` (`max_rounds` / `stalled` / `disputed` / `needs_decision` / `cost_exceeded` / `coder_failed` / `reviewer_failed` / `failed` / `infra` / `delivery` / `contract_violation` / `timeout` / `resume_exhausted` / `pr_closed_unmerged` / `pr_gone` / `remediation_exhausted` / `conflict_unresolved` / `unknown`), a one-line `escalation_summary` (≤200 chars), `route`, `story_id`, `run_id`, and a nested `run_brief` (branch, rounds, cost, gate verdict, findings by severity, worktree, conversation log — everything the operator would otherwise dig out by hand); its description is the prose brief with the two actions — joined, whenever the brief names a `branch` and the gate names a run, by a **third**: `lithos-loom develop deliver <run-id>` keeps the branch (pushes it, opens the PR, swaps this gate for a `pr` gate; `--converge` re-reviews it under the revised acceptance — §4.15c), since completing the gate re-develops the story from scratch and discards the rounds that landed. The same command rides the `[NeedsHuman]` finding and both push sinks (the toast and the `@mention`), so it is copy-pasteable from wherever the operator is standing. A caller that supplies its own `actions` — a stranded PR, an exhausted remediation, an unresolved conflict — is unchanged: those gates do not sit on a stopped run's branch. The runner builds it from the plugin's `escalation` block in `result.json` (§5.2) when present, else from `error.category` / `error.message` + `rounds` / `worktree`. It then writes ONE story update carrying `metadata.needs_human_gate_id` (provenance only — never a guard) plus the failed-attempt marker `metadata.loom_last_attempt:<route> = {status: "failed", ended_at, task_fingerprint, run_id?, gate_id}`, posts a **`[NeedsHuman]`** finding on the story (reason, summary, the run facts, the gate id, the actions, and the `develop deliver` command when the run left a branch), fires the push notifications (`[notifications]`, §3.1), and `lithos_task_release`s. **A marker that names a `gate_id` never declines a bootstrap replay** — the gate is the guard, and a marker that kept declining after the operator ticked the gate would strand the story. **Resolution:** the operator *completes* the gate (a tick in Obsidian `tasks.md`, lens, or `lithos_task_complete`) — that is the retry gesture. Live, the route-runner child's **escalation resolver** watches `lithos.task.completed` for loom-raised human gates and republishes a synthetic `lithos.task.updated` (`origin="gate-resolved"`) for the waiting story — only while the story is open and still names that gate — which un-dedups the runner's in-process "fail once per task" set so the story re-runs in the same daemon process. If the daemon was down when the gate was ticked, the restart bootstrap re-surfaces the story and readiness passes; either way the runner clears `needs_human_gate_id` + the marker on the dispatch path, after a successful claim, so the loop's correctness never depends on the live nudge. Cancelling the *gate* strands the story (a cancelled gate is unsatisfiable); to abandon, cancel the *story*. If the gate cannot be raised at all, the runner degrades to the pre-gate contract below (marker without `gate_id` + `[BlockerFailed]`) with the gate problem folded in as `[Friction]` text. The one non-delivering exit that raises **no** gate is a misconfigured route (`{{repo}}` unresolvable — a host problem, not a story decision; a gate per task would be spam): it keeps the marker + `[BlockerFailed]` path.

  The **marker-only fallback** (the pre-b91177d2 contract, still the guard whenever no gate exists): best-effort `metadata.loom_last_attempt:<route> = {status: "failed", ended_at, task_fingerprint, run_id?}` record on the task, then `lithos_task_release` + `[BlockerFailed]` finding (the error message is pulled from `error.message` if present). One key per route (the per-key metadata merge then keeps concurrent routes' guards independent). The marker is what makes failure survive a restart: a bootstrap-replayed `created` for a story whose last attempt failed **for the same route** — and whose title/description/tags still match the recorded `task_fingerprint`, i.e. nobody edited it since — is declined before the readiness query. A restart is a process lifecycle event, not anyone asking for another run. Two retry gestures are guaranteed across a restart: **deleting the marker key** (the canonical signal — no marker, no decline) and **editing the task** — on a lithos#415 server, an edit of *any* kind (#339): at failure time the runner records the task's `updated_at` — taken from the marker write's own `task_update` response, since that write is the failure path's last stamp-bumping mutation (`finding_post` and claim/release don't bump; measured 2026-08-29) — in a loom-local stamp store (`<work_dir>/route-runner/attempt_stamps/`, beside the SSE cursor; the marker cannot contain the stamp its own write creates), and declines only while the bootstrap payload's `updated_at` still equals it, so metadata-only changes (e.g. `develop_image`) and reverted edits (remove + re-add the same trigger tag — every write bumps, so the revert lands on a new stamp) both re-dispatch. When the stamp is unavailable — pre-#415 marker or server, wiped work dir — the guard falls back to the recorded `task_fingerprint` of title/description/tags, whose two blind spots (metadata-only edits, reverted edits) then apply; delete the marker for those. A stamp mismatch caused by another agent's write fails OPEN into one re-dispatch — the pre-guard behaviour, never a stuck task. A live `lithos.task.updated` also dispatches directly when the runner has not suppressed the task in-process, and the T10 resume re-dispatch is unaffected. Within one daemon process, a task that failed stays suppressed by the in-process dedup regardless of edits ("fail once per task per daemon process", issue #11 — pre-existing, unchanged). A later gated delivery clears the route's marker (and any `needs_human_gate_id`), and an `interrupted` run clears it too — interrupted's designed recovery is the restart bootstrap, which a stale failure marker must not veto. The contract-violation / timeout / unknown-status exits escalate like `failed` (reasons `contract_violation` / `timeout` / `contract_violation`, with the retained work dir as the brief); only the route-misconfigured exit stays on this marker-only path. `loom_last_attempt:*` is a reserved runner-owned key namespace — plugins see it in `task.json` metadata and must not repurpose it.
- `interrupted` → `lithos_task_release`, no finding. When the result also carries a `resume` block (`resume_after` timestamp — e.g. a story-develop run that checkpointed on a provider usage limit), the runner additionally schedules an in-process re-dispatch: at `resume_after` it re-checks the task is still open, then re-claims and re-runs the plugin. Bounded at `MAX_RESUMES_PER_TASK` (3) re-dispatches per task per daemon process; on exhaustion the runner **escalates** — a needs-human gate with `escalation_reason=resume_exhausted` + `[NeedsHuman]` (the claim was already released on this path, so it is not released again). The schedule is in-memory only — a daemon restart loses it, but the event-stream bootstrap re-surfaces open tasks on startup anyway.
- Unknown / missing status → escalation with `escalation_reason=contract_violation` (a needs-human gate + `[NeedsHuman]`, then `lithos_task_release`).

Other `result.json` fields (`metadata_updates`, `artifacts`, `commits`, `spawned_tasks`, `exit_code`, `error.retriable`) are schema-validated but currently ignored. On plugin timeout, the runner sends SIGTERM with a grace period before SIGKILL.

**GitHub issue mirror (GitHub → Lithos).**
`GitHubIssueWatcher` (running in the github-watcher child) polls every repo flagged for watching on its `[github_watcher].poll_interval_seconds` cadence (default 60s). Watch eligibility is derived from project-context metadata: a doc with `github_watch_enabled = true` and a non-empty `github_repos` list enrols its slug → repo mappings (a project may map several repos, each polled independently). Discovery is one filtered call — `note_list(path_prefix="projects/", metadata_match={"github_watch_enabled": true})` — and each returned item carries its metadata, so the repo list and exclude filters are read without a follow-up per-doc fetch. The watcher subscribes to `lithos.note.{created,updated}` on the in-process bus so a `project enable-github <slug>` mid-run takes effect without a daemon restart. Per-repo `updated_at` cursors persist in a daemon-owned Lithos doc (default `projects/_lithos-loom-internal/github-watcher-state.md`, configurable) so cold restart doesn't re-walk every open issue. Coord-doc writes are CAS-protected: on `version_conflict` the watcher merges the just-observed cursor advances with the remote cursors (latest timestamp wins per repo) and retries, so concurrent writes don't lose progress. Per-repo polls split into two paths: **bootstrap** (no cursor yet for this repo) lists `state=open` with full `Link: rel="next"` pagination so every open issue surfaces in one cycle regardless of historical-closure volume; **incremental** (cursor present) lists `state=all` since the cursor with the same pagination so closes on previously-seen issues — their `updated_at` advances at close time — surface alongside fresh opens. Each issue surfaced this poll publishes one `github.issue.seen` event onto the in-process bus; the auto-wired `github-issue-sync` subscriber resolves an `<!-- lithos:<task_id> -->` linkage marker in the issue body, then takes one of these branches:

- Marker → open Lithos task: drift-sync only (title / body / labels — see below).
- Marker → open Lithos task, GH closed-completed: drift-sync + `lithos_task_complete`.
- Marker → open Lithos task, GH closed-not_planned: drift-sync + `lithos_task_cancel`.
- Marker → terminal Lithos task: drift-sync only (idempotent close mirror). If GH state transitioned from closed back to open and `metadata.github_state_snapshot != "open"` on the task, also post a `[ReopenRequested]` finding (de-duped via the snapshot field).
- Marker → missing task (operator force-deleted): create a fresh task; the marker writer overwrites the stale id.
- No marker, Lithos task carries `metadata.github_issue_url` for this URL: re-write the canonical marker on GitHub. No duplicate task.
- No marker, no matching task, GH open: `lithos_task_create` with `title=issue.title`, `description=issue.body`, `tags=issue.labels + ["github-issue"]`, `metadata={project, github_issue_url, github_issue_number, github_labels, github_state_snapshot=issue.state}`. Then write the canonical `<!-- lithos:<task_id> -->` marker into the issue body via `PATCH /repos/{owner}/{repo}/issues/{n}` — fetched fresh via `get_issue` immediately before the PATCH so an operator edit during the poll-to-PATCH window survives.
- No marker, no matching task, GH closed: skip (historic closures are not backfilled).

**Per-project exclude filters.** The watcher ships each event with the project's import-time filters, sourced from these metadata keys on the project-context doc (applied to every repo the project maps):

- `github_exclude_labels` (list) — drop the issue at import time if it carries any of these labels.
- `github_exclude_authors` (list) — drop if the GH author login matches (e.g. `dependabot[bot]`).

Filters apply only on the create branch (no marker + no matching URL + GH open). Already-linked tasks are unaffected if an exclude tag is added after import — the PRD explicitly locks "exclude is only at import time" so the operator never has a once-imported task quietly stranded.

**Dispatch contract (GH → Lithos).** The watcher source dispatches each issue inline to the `github-issue-sync` handler before advancing the persistent cursor — the bus path is reserved for tests that assert on queue contents. Cursor advancement is per-issue: the watcher walks GitHub's `updated_at`-ascending list, advances the in-memory cursor to each issue's timestamp only after dispatch succeeds, and halts the loop on the first exception so the next poll re-fetches starting from the failed boundary. Issues that failed dispatch are tracked in a `_stuck_issues: dict[str, set[int]]` map and retried by direct `github.get_issue` lookup at the top of the next poll — that path is independent of the cursor and the `state=` filter, so a bootstrap walk that's about to lose a closed-before-retry issue still gets it. The stuck set is persisted in the coord doc as `stuck:<owner>/<name>#<number>` rows alongside the cursor rows, so daemon restart between a partial reconciliation (e.g. `task_create` succeeded, marker PATCH failed) and the next retry preserves the repair record. CAS-write semantics protect both halves: deletion tombstones are tracked at function entry for both cursors and stuck rows so a `version_conflict` reload-then-merge doesn't resurrect locally-drained state.

**Dispatch contract (Lithos → GH).** The push direction uses the bus because `LithosEventStream` already serves multiple subscribers across child processes. The consumer loop classifies handler exceptions: permanent errors (`GitHubAuthError`, `GitHubRepoNotFoundError`) log `[Friction]` and drop without retry — retry won't help. Other `GitHubError` subclasses (transients — 5xx, network blips, rate-limit exhausted) retry with exponential backoff capped at 60s, up to 8 attempts (inter-attempt waits 2/4/8/16/32/60/60 s ≈ 3 minutes total before drop). Outages outlasting that budget are caught by the **periodic reconciliation sweep**: every `[github_watcher].reconcile_interval_minutes` (default 60) the child re-fetches open Lithos tasks plus completed + cancelled tasks resolved within `resolved_replay_days` (skipped entirely when `resolved_replay_days = 0`), filters to those carrying `metadata.github_issue_url`, and re-dispatches each one through the push handler. Terminal tasks dispatch both a synthetic `task.updated` (so title drift reconciles) AND the matching close event. The handler is idempotent (re-fetches GH before PATCH) so the sweep is a no-op in steady state. The sweep keeps recovery cadence within the configured interval even without a daemon restart; set to 0 to disable.

**PR-gate resolver (Epic H / US12+US13).** The same reconcile sweep, on the same `[github_watcher].pr_merge_poll_enabled` gate (default on), also resolves the first-class **`pr` gates** the runner raises (§2.2 above). For each open `task_type="gate"` task carrying `metadata.gate_type="pr"`, it reads the gate's `repo` / `pr_number`, finds the gated story via the `waits_on_gate` edge, fetches the PR, and acts on the state: **merged** → complete the **story first**, then the **gate** (both swallowing `task_not_found`), and post `[GateResolved]` on the story; **closed without merging** or **deleted (404)** → the gate has nothing left to watch but the story still needs a decision, so the resolver **converts the stranding into the escalation primitive** (04c2448b / [#268](https://github.com/agent-lore/lithos-loom/issues/268)): it raises a loom **`human` gate** on the story (`escalation_reason=pr_closed_unmerged` / `pr_gone`, `route=pr-gate`, `run_brief={pr_url, pr_state, superseded_pr_gate_id, branch}`; `[NeedsHuman]` on the story with the three real choices — the work already landed → complete the **story**; re-develop into a fresh PR → complete the **gate**; abandon → cancel the story; the push sinks), records `superseded_by_gate_id` on the **`pr` gate** in the **same** `task_update` as its merge marker + `needs_human` state, posts a one-shot `[DeliveredPRClosed]` on the story as the audit trail, and only then **completes** the `pr` gate — never cancels it (a cancelled gate is terminal), and never before the human gate holds the story (so it is never momentarily unblocked: one blocker, one decision, and the `pr`-gate list stops lying). A story already behind an open loom `human` gate (a conflict or remediation escalation — read from the story's **incoming `waits_on_gate` edges**, never from `needs_human_gate_id`, which is provenance only and can be stale or absent after a partial write) gets no second one — the `pr` gate is superseded by that gate, whose `run_brief` gains the stranding facts (`pr_url`, `pr_state`, `superseded_pr_gate_id`) and whose `escalation_summary` says the PR died meanwhile, so the gate the operator reads does not keep asking for a converge on a dead PR; a story that is already **terminal** (the #268 shape: the work landed via another PR and the issue mirror completed the story before the superseded PR was closed) has nothing to decide, so the `pr` gate is just marked and completed — no gate, no finding, no notification; an unreadable story defers the whole conversion to the next sweep. The human gate's description carries the same three choices (not the runner's complete-to-re-dispatch pair — `human_gate_brief` renders the caller's `actions`). The idempotency key is the `pr` gate's own `superseded_by_gate_id` (never the story's key, which goes stale on the daemon-down path and would suppress a *second* stranding after a re-develop): a sweep that raised the gate but could not complete the `pr` gate leaves the marker, and the next sweep completes it with no second gate, finding or GitHub call. When no human gate can be raised the resolver falls back to the pre-conversion contract — `pr` gate left **open** with its url-scoped marker + state, the `[DeliveredPRClosed]` naming the problem as `[Friction]` — and the terminal-marker guard retries the conversion every sweep until it lands; the same guard is how a gate stranded before this shipped **self-migrates** on its next sweep, without a GitHub call. The human gate then **polls its PR** (below); **still open** → re-poll next sweep, classify **landability** (PRD S1, below) and, when `[github_watcher].external_reviews_enabled` is on — the default — ingest external review activity (further below); **transient `GitHubError`** → retry next sweep; a gate whose metadata won't parse → one-shot `[Friction]`. **Story-first ordering is non-negotiable:** completing the gate first would momentarily ready a story still tagged `trigger:story-develop`, and if story completion then failed the gate would be gone from the open set → story stranded open+ready+tagged → duplicate PR. The de-dup marker for the non-merged end-states (`metadata.develop_pr_merge_state` + `develop_pr_merge_url`, PR-scoped) is written **on the gate** (the durable node that stays open and would be re-swept), so a re-develop into a replacement PR (which updates the gate) re-evaluates. On **merge** the gate itself is completed, so no marker is needed. Completing all gated stories means the Lithos→GH push then closes any linked issue on merge (the push re-fetches before PATCH, so the ownership change is race-benign). The story completion's `unblocked` return — the dependents whose last `blocks` predecessor just cleared — is **nudged** (#350): the watcher runs no `RouteRunner` and has no IPC to the child that does, so each unblocked id gets a no-op `task_update(metadata={})`, which bumps `updated_at` and emits `lithos.task.updated` for the route-runner to route-match, ready-check and claim on its normal SSE path. **The nudge runs between the two completions** — after the story's, before the gate's: completing the gate is the durable "merge resolved" transition that takes it out of the swept open set, so anything after it is never retried. An interrupted batch therefore leaves the gate open, and the next sweep — whose story completion now raises `task_not_found`, the response gone for good — recovers the ids from the story's outgoing `blocks` edges, then puts **each one individually** to `lithos_task_ready`: those edges name every dependent, not just the ones this story released, and a dependent still held by a sibling blocker must not be written to (see below). The membership query is narrowed to **that candidate's own project and tags** — the narrowing `READY_QUERY_LIMIT` is sized for, and the only one that cannot drop the candidate itself; enumerating the whole instance instead would make the answer hostage to unrelated ready work (the github-issue watcher turns every unseen open issue on a watched public repo into an edge-less, immediately-ready task, so the global count is not loom's to bound). A full page means truncation, so absence from it is undetermined rather than not-ready — and since ready and blocked partition the open work tasks, the candidate is then looked for on `lithos_task_blocked` under the same narrowing, which settles a still-blocked dependent the saturated ready page could not. **Recovery progresses per candidate.** Because no narrowing settles a task carrying neither project nor tags, an unclassifiable candidate must not strand its classifiable siblings — the tagged dependents this path exists to dispatch — so the ones that classify are nudged now and written into a `metadata.develop_pr_merge_nudged` record on the gate (`pr_url`, `nudged[]`, `undetermined`), which is also what stops anyone being nudged twice; only the residue keeps the gate open (`error`), with a one-shot `[Friction]` on the story (de-duped on the gate) so the deferral is not silent. That deferral is **not bounded** (PR #352 review): completing the gate is the durable transition that leaves the swept open set, and nothing after it can ever emit a released dependent's event — so the gate stays open until every candidate is definitively ready, blocked or terminal. The classification is the one both children share (`dispatch_guards.classify_readiness`): the candidate's own project + tags, then — when that ready page is still full — the **blocked** page for the same scope as the other half of the partition (open work is ready XOR blocked, so a complete blocked page that lacks the candidate settles it as ready), which makes "undetermined" need both pages full or a failed read: a transient state, not a steady one. That recovery fan-out is then recorded on the gate (`metadata.develop_pr_merge_nudged`, scoped to the PR url) so it is sent **once**: the merged branch writes no `develop_pr_merge_state` marker, so a gate whose own completion fails durably stays in the swept open set and would otherwise re-nudge its whole fan-out every sweep — a loom write that is indistinguishable from the human edit the #339 guard reads as authorization to re-run a failed story. That recovery runs **only** on the already-terminal branch: a completion that succeeds and names nobody is authoritative (the ordinary fan-in dependent still waiting on a sibling blocker is not ready and is deliberately left untouched, since the no-op write would still bump its `updated_at` and consume the #339 bootstrap-replay guard's evidence). Anything that leaves the ids *unknown* — a failed completion, or an edge read that errored — defers the whole resolution (`error`, gate left open) rather than resolving a gate whose dependents no later sweep could reach. Best-effort: a failed nudge posts `[Friction]` on the story and never changes the merged outcome, with the restart bootstrap as the backstop.

**A terminal story's still-open PR (#372).** Before anything below runs on a still-open `pr` gate, the sweep reads the gate's waiter: a story already `completed` / `cancelled` (by hand, or by the issue mirror when the work landed via another PR — the sibling of the #268 closed-PR shape) means the PR is the operator's now, so the gate is completed (marker `develop_pr_merge_state=waiter_resolved` + `develop_pr_merge_url`, the audit trail, deliberately outside the terminal-marker set so a completion that did not land is retried; nothing is posted on the story) and no dispatcher runs; for a `completed` story the released dependents are first recovered from its `blocks` edges and nudged, exactly as the merged path does when the story was completed by someone else — whoever completed it discarded the `unblocked` answer, and the gate is the only retry surface that survives its own completion (a cancelled blocker releases nothing) — no landability finding, no review ingestion or paid remediation round, no re-gate / resolver subprocess, no S6 admission slot held. An unreadable story holds the whole branch (`error`, retried next sweep — fail closed: nothing spends on a story Lithos could not describe); a waiter Lithos no longer returns is not "done" and takes the ordinary branch. The sweep summary counts these as `waiter-resolved`.

**PR landability (PRD S1, detection).** On each **still-open** `pr` gate the sweep classifies the PR from the `mergeable` / `mergeable_state` fields on the same `GET /pulls/{n}` it already fetched, keyed on the base branch's **live tip** (`GET /git/ref/heads/<base>` each sweep — the payload's `base.sha` is a snapshot GitHub takes at the PR's last update, never a base-move key; an unreadable tip is `unknown` for this sweep): `unknown` (GitHub computes `mergeable` lazily and returns `null` on a cold fetch — "ask again", never clean; nothing is written), `dirty` (a conflict with the base — `mergeable_state: dirty` or `mergeable: false`), or `mergeable` (everything else, including `behind` / `blocked` / `unstable`, which are not conflicts). A `dirty` PR gets a one-shot **`[PRConflicted]`** finding on the blocked *story* naming the base branch and the two shas; the de-dup marker is `metadata.pr_landability` on the **gate** — `{pr_url, base_sha, head_sha, state, mergeable_state}` — keyed on **both** shas, because pushing a conflict resolution moves the head and not the base, and a base-scoped marker would suppress the re-check that proves the fix landed. A PR that becomes mergeable again flips the marker silently (the merge is the event the gate reports). The API does not name the conflicting paths; that list is S3's trial merge (not yet shipped), and S5's automatic resolution builds on both. Rides the `pr_merge_poll_enabled` pass; no separate dial.

**External-review ingestion (PRD S2, detection).** On each **still-open** `pr` gate the same sweep also reads the PR's reviews, inline review comments and **Conversation-tab comments** and posts anything new as a one-shot **`[ExternalReview]`** finding on the blocked *story* (author, review state, `path:line`, a one-line excerpt, and the thread url per comment; "on the PR conversation" plus the comment url for a conversation comment). The conversation stream exists because GitHub refuses a review from a PR's own author, and every loom-delivered PR is opened under the operator's `gh` login — so the operator's verdicts arrive as conversation comments and nowhere else (#353). Per-state policy: `CHANGES_REQUESTED` always posts; `DISMISSED` is recorded silently — a dismissal has had its say; every other state, `APPROVED` and `COMMENTED` alike, posts on a non-empty body (`APPROVED` left the silent set with the 827cedf8 guard: an approval that *asks* — "LGTM, but rename X" — is a finding whatever state the reviewer clicked). Whether a row is a *bare* approval is a separate question, asked only where it decides a spend — see below; the converge intake (`actionable`) never filters approvals on any stream, so the S5a triage keeps its model-driven look at them; a conversation comment posts unless empty or loom-authored. **An approval is not a finding** (827cedf8): a row that asks for nothing — an `APPROVED` review with no inline comments of its own, or any review / inline / conversation body that is approval prose end to end ("LGTM", "**No findings.** Ready to merge.", "👍") — is classified `approval`. A `CHANGES_REQUESTED` review is **never** an approval row whatever its body says — the state blocks the PR on GitHub until it is dismissed or superseded, so a contradictory "No findings. Ready to merge." body stays the finding its state makes it (the same `BLOCKING_REVIEW_STATES` both rules read). It advances the marks like any other activity and is reported on the story as an `- [approval] …` row — `- [approval, unverified author] …` when loom cannot verify the author as a repo write/admin collaborator, since anyone who can comment on a public PR can leave an approval and this is the text a merge decision is read against — with a `disposition: approval — …no remediation round was reserved or spent` line when the whole batch approves (an approvals-only batch in which *no* approval is verifiable gets the weaker note instead: recorded, not evidence the PR is ready); it is kept OUT of the dispatchable batch, so it parks no pending trigger, spends no S5b round, and never holds the merge-gate. The classifier fails towards *actionable*: matching is per sentence / list item / line and must cover the unit end to end, so an approval that also asks ("LGTM, but rename `foo`") stays a finding. The body is **canonicalised, never deleted** — typographic punctuation folds to ASCII and zero-width marks are dropped, and a unit still holding a non-ASCII character is prose the vocabulary cannot read, hence actionable: an ASCII approval token beside an ask in another script ("LGTM. 请重命名变量") is a finding, not an approval. A review that clicked approve and wrote **nothing** while leaving inline comments is not an approval row either — it has nothing of its own to say and its comments are reported on their own stream (the AC's "`APPROVED` and no inline comments") — but a review that *wrote* approval prose is always reported, whatever it owns: a body no bucket takes is a body the operator never sees. Trust is unchanged: an untrusted author's approval is recorded and ignored exactly as their findings would be. The model-driven half of the same rule is the S5a triage verdict `NOTHING_TO_REMEDIATE` (§4.15a). Thread replies and loom's own automated replies and notices (a converge conversation reply, or the `[NeedsHuman]` `@mention` — both posted under the operator's login and marked as loom's) are never re-ingested. De-dup is a triple of **high-water marks** (`last_review_id` / `last_comment_id` / `last_issue_comment_id` — GitHub REST ids are monotonic, so a summary-only review with zero inline comments still keys exactly; the three streams have separate id spaces) held in a `metadata.external_review_seen` marker on the **gate**, scoped to the PR url so a replacement PR re-evaluates from scratch; the marker also carries `last_comment_at` / `last_issue_comment_at` cursors passed as `since` on the two comment fetches (minus a one-second overlap — GitHub's `since` is strictly-after with second precision, and the id marks drop the overlap's repeats) so a long-lived PR's history isn't re-paginated every sweep. Backfill guard: a root comment whose automated reply proves a **landed** fix — the `Fixed in <sha>` reply shape (a held-back red-gate or "Not changed" reply carries the same marker with the root still unresolved, and never suppresses), **authored by a write/admin collaborator** (body strings are forgeable, so the reply author is permission-checked, one call per unseen author, failing closed to "report" on a probe error) — was already remediated by the delivery-time inline round, so a markerless gate's first sweep skips it — and skips a non-`CHANGES_REQUESTED` summary review by the same handled author — instead of re-reporting handled history; a conversation comment is proven handled the same way by a landed-fix conversation reply that names it in its `_(replying to <comment url>)_` line (conversation comments have no thread structure). A transient `GitHubError` leaves the marker untouched and the whole batch retries next sweep. Gate: `[github_watcher].external_reviews_enabled` (default on; rides the `pr_merge_poll_enabled` pass). The companion `trusted_bots` allowlist has no effect on detection — it feeds remediation (ADR 0011 decision 8), below.

**Base-move re-gate (PRD S3, the watcher half).** On each **still-open** `pr` gate — after landability and remediation — the same sweep asks *"will the base break if this merges now?"* by spawning `lithos-loom develop merge-gate <pr> --story <story id> --json --repo <path>` as a crash-isolated subprocess (§4.15b): a trial merge of the base's **current** tip in a throwaway worktree, the project's **current** check-set on the result (resolved through `--story`, strictly), and — green and behind — the merge commit pushed onto the PR branch (append-only, never a rewrite; ADR 0011 decision 2). Zero agent tokens. Under the project's generated-paths policy (`develop_generated_paths` + `develop_regenerate_command`, PRD S4) the trial merge is `--no-commit`: a conflict confined to those paths is taken from the base, the generator runs on the composed tree in the gate container and the merge is committed once with fresh outputs (a clean merge regenerates too — composition moves generated output even when the files auto-merge); only a conflict OUTSIDE them is a `conflict` (reported without the generated noise; the set-aside paths ride in the record as `generated_conflicts`), and a generator that fails is a red `regenerate` check row (`[MergeGateFailed]`), nothing pushed. The **re-run key** is `(head_sha, base_sha, settings fingerprint)` — `base_sha` the live tip read above — held in a url-scoped `metadata.merge_gate` record on the **gate**: a moved head or base re-gates; an unchanged pair re-gates only when the story's resolved gate settings changed, probed each sweep with `merge-gate --resolve-only` (no fetch, no merge, no checks — the check-set fingerprint needs a worktree the sweep does not have) as a **background task per gate**, never inline in the sweep; the settings fingerprint hashes the profile by **definition** (its check declarations and their catalog commands, plus a schema version) so a loom upgrade that tightens what `standard` means re-gates too; a conflict / fork / unmapped record is settled by the shas alone and never probed (a `pr_closed` answer from the run writes nothing — the merge poll owns closed and merged). A probe acts only on the record it was scheduled for: a key that moved meanwhile cancels the probe, and a probe that outlives its record starts nothing. Every run is **pinned to the gate's repo**: the sweep first reads the mapped checkout's `origin` itself (`git remote get-url`, milliseconds, no network) and a mismatch — **or a read that cannot answer** (not a git checkout, no origin remote, an origin that is not a GitHub url; `checkout_unresolved`, with the reason on the record and in the finding — never permission to dispatch a child that would only die in `gh`) — is refused **before any subprocess** — recorded as `repo_mismatch` with the mapped path and the origin it found, one `[Friction]` on the story, re-checked every sweep; `--expect-repo` on the run itself remains the authoritative check (`gh`, redirect-aware; a PR URL naming another repository is refused too), and a run it refuses is a bounded retry. A mismatch of either kind **settles on what the sweep observes** — the mapped path and its own origin read — and re-arms for the same shas the moment one of those moves (the two checks can disagree, e.g. a rename `gh` follows, so the read matching is never by itself a re-arm; the operator's lever is the mapping or the checkout's remote url). A stale `[projects.<slug>].repo` must never act on the same PR number in another repo — and the same origin read guards remediation: a mismatch there spends no budget round and leaves the parked review trigger in place, and a converge the CLI refuses **refunds** its round, **re-parks** the trigger and settles on the same key (never a spawn per sweep). That refund's state write is **strict**: retried with backoff, and when it still does not land the story is told exactly that — the round stays spent and the trigger consumed — and an exhausted budget escalates to a human like any other unconverged last round; never a success claim over state that did not land. **One in-flight run per project** (a deferred gate simply dispatches on a later sweep), and a **mutual per-PR hold** with remediation — a converge in flight defers the re-gate, a re-gate in flight defers the converge dispatch (its pending trigger stays parked; the hold is re-checked the moment a background probe would start a run, not only when it was scheduled) **and** keeps the budget's head observation inert (a head seen while a merge commit may be landing cannot be attributed) — because either may push to the branch and a leased push beside another push loses. Outcomes, each a one-shot record on the gate: **green** records (a pushed merge commit is recorded as loom's own `last_loom_pushed_sha` on the S5b budget, else the next sweep would read it as a human push and reset the remediation counter); a green verdict whose merge commit **failed to push** (the CLI reports the push beside the verdict, never folded into it) is **`push_failed`** — a `[Friction]` on the story with the push error, retried once on the same key, then the verdict stands until a settings change, a head push, a base move or a daemon restart (the restart re-arm below); **red / errored** posts **`[MergeGateFailed]`** on the story naming the failing (or unverified) checks; a **conflict** widens S1's **`[PRConflicted]`** with the conflicting paths — the trial merge is the only source of that list; an unresolvable config (`config_unresolved`, exit 4), an unmapped project, a fork PR (never fetched), a repo mismatch, an intake fetch that failed on the host (`infra_failed`, #431 — the `[Friction]` names the host action, not a verdict on the merge) or a crash posts `[Friction]` **on the story** — never silent, never gated with built-ins (a crash, an infra failure or a mismatch is retried once on the same key, then waits for a head or base move — or, for a crash, an infra failure or a failed push, a **daemon restart**: any of them may be loom's own bug or the host's, and the restart is the fix attempt, so each boot gets its own bounded retry pair on the same shas — a repo mismatch settles on the origin read instead; a `no_project` record re-gates once the project is mapped). The PR's repo path resolves exactly as remediation's does (`gate.metadata.project` → the story's `project` → `[projects.<slug>].repo`). Host dial: `[github_watcher] merge_gate_enabled` (default on). Per-project opt-out: context-doc `develop_merge_gate = false` (an unreadable doc fails closed — no run that sweep).

**Conflict resolver (PRD S5, the watcher half).** On each **still-open** `pr` gate — after the re-gate, whose `metadata.merge_gate` record is the trigger — the same sweep resolves a conflict the re-gate NAMED (under the S4 policy that is never a generated-only conflict — the re-gate regenerates and pushes those — and the intake sets any generated paths aside, resolved to the base's copy, so the coder is handed the real conflicts only plus the regenerate command to run before handing off; the loop then regenerates after every round commit as its own `story-develop r<n>: regenerate` commit, and the panel's merge context names the set-aside paths as generated, not hand-merged): when that record says `conflict` for the **current** `(head_sha, base_sha)` and no `metadata.conflict_resolve` record exists for that pair, it spawns `lithos-loom develop converge <pr> --resolve-conflicts --story <story id> --repo <path> --expect-repo <owner/name> --expect-head <head> --expect-base <base> --json` (§4.15a) as a crash-isolated subprocess — **once per sha pair** (PRD S5: escalate, never retry the same inputs; a moved head or base is a new attempt the re-gate runs first). The attempt is **reserved on the gate before the spawn** (a `running` record, written strictly — a reservation that does not land spawns nothing) and remembered in-process for the boot, so no failed breadcrumb can let the same pair be paid for twice; the child is **pinned to the pair** (`--expect-head` / `--expect-base`: a head or base that moved meanwhile is refused before any agent runs and recorded as `head_moved` / `base_moved`), so the attempt is never recorded against inputs it did not act on and a human push is never hidden from the remediation budget. **One run in flight at a time** (it spends a coder session and a panel), **held while remediation or the re-gate is busy on that PR and holding both** (any of the three may push to the branch). The same preconditions as the other two: the project resolved from the gate / story to `[projects.<slug>].repo`, the per-project dial `develop_conflict_resolve` (default on; an unreadable doc fails closed), the sweep's own origin read (an unresolvable or mismatched checkout spawns nothing — the re-gate already said so on the story). Outcomes, each a one-shot record on the gate: **converged and pushed** records the merge commit as loom's own `last_loom_pushed_sha` on the S5b budget (record and budget in one write, made first and strictly — from a fresh read of the gate, else the dispatch-time snapshot; a write that still does not land becomes a **held debt**: the PR stays held so remediation's head observation stays inert, the story gets a `[Friction]`, and every sweep retries the write until it lands — and because the push is breadcrumbed on the **story** (`metadata.conflict_resolve_pushed`) before that write is attempted, a daemon restarted mid-debt recovers the hold from the breadcrumb before its first head observation, so a restart cannot turn loom's push into a budget reset) and only then posts **`[ConflictResolved]`** on the story naming the paths, the pushed sha and the rounds — the next sweep re-gates at the new head; an **`infra_failed`** run (#377: the host died under the run — a slice-B auth / transport / spawn failure that persisted through its retries, or the **intake fetch** of the PR head + base failing through its own 3 attempts, #431 — so there is no verdict on the merge) is a `[Friction]` on the story naming the host action and is re-armed once per daemon boot, never a gate; **`not_converged` / `failed` / `conflict_unsupported`** raise a loom **`human` gate** on the story (`escalation_reason=conflict_unresolved`, `run_brief` = pr url, shas, paths, status, rounds, cost; `[NeedsHuman]`; the push sinks) once per sha pair, the gate id recorded on the resolve record and `needs_human_gate_id` on the story — the operator merges the base in by hand or re-runs with a higher round budget, then completes the gate; **`no_conflict` / `merge_race` / `merged`** just record (the world moved on — the merge poll and the re-gate own what follows); a **crash** — the child died without writing a record at all, which since #431 no longer covers a failed intake fetch (that is the `infra_failed` above, with its host action, not a `crashed` record carrying a rich traceback frame); the finding carries the child's last logical **message** line — the trailing run of non-frame lines rejoined, so a rich-wrapped `RuntimeError: …` reads whole and a panel frame is never published as the reason (an output that ends mid-panel says it has no message line rather than reaching back past it), stripped and bounded like every quoted line — and the whole tail goes to the daemon log at WARNING — or a **repo-mismatch refusal** posts `[Friction]` on the story (the record first, strictly; the breadcrumb second), a crash re-armed once per daemon boot and a repo mismatch settled on the mapped path + the sweep's own origin read, re-armed for the same shas when either moves. Host dial: `[github_watcher] conflict_resolve_enabled` (default on).

**Reconciliation state (PRD S7).** Findings are history; *"what is the state of this PR right now?"* is answered on the `pr` gate itself (ADR 0011 §2) by four flat, scalar, `metadata_match`-queryable keys the sweep writes on every still-open gate **after** every dispatcher has run, from a re-read of the gate: `reconciliation_state` (one of `awaiting_review` · `reconciling` · `behind` · `resolving_conflict` · `gate_failed` · `needs_human` · `ready_to_merge`), `reconciliation_detail` (one line, ≤200 chars, why), `reconciliation_since` (when the state last *changed* — a detail-only move keeps it), `reconciliation_pr_url` (the PR the state describes — a replacement PR on the same gate starts fresh). The state is **derived, not tracked**: a pure function of the url-scoped records the dispatchers already keep (`pr_landability`, `merge_gate`, `conflict_resolve`, `external_remediation`, `external_remediation_pending`, `develop_pr_merge_state`), the freshly fetched PR, and what this process has in flight. Precedence, highest first: `needs_human` — automation stopped: an escalation gate is recorded on the current sha pair (`conflict_resolve.needs_human_gate_id`) or on the budget (`external_remediation.needs_human_gate_id`), the PR was closed unmerged / deleted, or a dispatcher refused for a reason only the operator can fix (`repo_mismatch` / `checkout_unresolved` / `config_unresolved` / `fork_unsupported` / `no_project`); `resolving_conflict` — `converge --resolve-conflicts` is running; `reconciling` — a remediation or merge-gate run is in flight, or a remediation trigger is parked behind one (a remediation in flight also outranks the *gate-less* exhaustion reading: the round is reserved at dispatch, so the budget counts as spent while the run that spends it is still running — its outcome, a push or the escalation that records the gate id, settles the state); `gate_failed` — the current pair's trial-merge **status** (`merge_gate.status`, the outcome vocabulary; `verdict` is the RED/GREEN beside it) is `red` / `errored`; `behind` — the trial merge conflicts (`conflict`), a green merge commit's push failed (`push_failed`), GitHub reports conflicts, or GitHub says `behind`; `awaiting_review` — GitHub has not classified the PR, or says `blocked` / anything but `clean`, or the re-gate `crashed` and awaits its retry; `ready_to_merge` — landable, `clean`, and the current pair's status is `green` or `no_checks` (vacuous), **or** no re-gate is owed at all — the merge-gate dispatcher is unconfigured, `disabled`, or `project_disabled`. **Absence is not "not required":** the derivation also takes each dispatcher's `consider` label for this sweep (`Dispositions`), so a required re-gate that has not been evaluated — `unknown_shas` (the live base tip was unreadable), `no_story`, `project_settings_unavailable` — is `awaiting_review`, one that is queued or under way (`deferred_busy` / `deferred_remediation` / `probing` / `dispatched`) is `reconciling`, and a refusal label is `needs_human` even when its record write did not land. A prior `green` / `no_checks` record is accepted only when the dispatcher confirms it still stands this sweep — `unchanged`: the key matched outright, or the background settings probe re-read the fingerprint and found it intact — or no dispatcher is configured; under any fail-closed label it is `awaiting_review` ("prior trial merge green unconfirmed"). `probing` is the dispatcher's *promise* (it has just scheduled the probe), never its answer: the sweep writes such a gate's state only after the probe has settled (`MergeGateDispatch.settle_probe`, awaited once every gate's probe is out so probes still run concurrently) — `unchanged` confirms, `dispatched` / `deferred_busy` / `deferred_remediation` mean the fingerprint moved and mask the recorded outcome as `reconciling`, `probe_failed` / `probe_crashed` / `superseded` (or a probe still out after `PROBE_SETTLE_SECONDS`, which stays `probing`) leave it unconfirmed. Only `dispatched` / `deferred_busy` / `deferred_remediation` mask a recorded outcome as `reconciling` — and `dispatched` only while the run is still in flight: a re-gate that finished before the sweep's re-read (a conflict or a refusal takes seconds) has its fresh record on the current pair read as the verdict, which confirms itself. Likewise the conflict resolver's `escalated` label (an open loom `human` gate already waits on the story — the story-side lookup runs **before** the resolver's record-based early returns, and an unreadable lookup is the distinct `escalation_unknown`, never a claimed gate) and a settled conflict outcome on the current pair (`not_converged` / `failed` / `conflict_unsupported`) are `needs_human` whether or not the best-effort gate-id write reached the record, as is an exhausted remediation budget **unless its last round settled the PR** (#408, lens #88: round 2/2 had just converged and pushed, and the board said `needs_human` over a PR that needed nothing but the operator's re-review): the run that spent the round records the CLI's own `succeeded` verdict on the budget (`external_remediation.last_settled`, beside `last_status` — `converged`, or the reported-not-remediated `already_clean` / `triage_rejected`, #380; the #387 `reverted` shape is *not* settled), and a spent budget whose recorded verdict is settled is a fact about what loom will do next, not a stop — it falls through to the ordinary states, and an `awaiting_review` / `ready_to_merge` it lands on carries the note "remediation budget spent (*n* round(s) used) — loom will not remediate again until a human push" in its detail (the note survives the 200-char truncation; the base detail gives way). **Fail-closed:** the reservation clears the verdict when a round is spent, so a round whose outcome never landed (a crash, a daemon restart mid-run — #407), an unconverged last round whose gate could not be raised, and a record from before the field existed all read `needs_human` ("the last round recorded no outcome" / "last run `<status>`"); so does a settled spent budget with a **new** trusted batch parked on it (`external_remediation_pending` for this url — ingestion parks the trigger, the exhausted dispatcher leaves it parked until a human push re-arms the budget): automation has stopped with work waiting, "remediation budget spent (*n* round(s) used) and new review material is parked with no round left — a human push re-arms it", never `reconciling` behind a run that is not there; an `infra_failed` conflict outcome on the current pair, and a remediation dispatcher holding the PR after an `infra_failed` run (its `held_infra` label), are `needs_human` with the host fix + restart named in the detail — no verdict was reached and only the operator can move it (#377); both sit below every human-gate check so a gate that already waits is named first. A persisted `running` conflict record is a reservation, not a process: only this process's in-memory busy signal yields `resolving_conflict`; a stale one on a dirty PR reads as `behind`. A held conflict-resolver debt (a pushed resolution whose record write is pending) is `reconciling`, not `resolving_conflict` — nothing is running. One-sweep staleness is by design: a push during the sweep moves the head, but the state describes the PR as fetched at the top of that sweep; the next sweep re-derives. A closed / deleted PR writes `needs_human` in the **same** `task_update` as its `develop_pr_merge_state` marker (and, on conversion, the `superseded_by_gate_id`), so the two never disagree — the `pr` gate is then completed and the state lives on as a record of why; it stays the live state only on the no-human-gate fallback and on an orphan gate, where the terminal-marker guard backfills a gate closed before the state existed on its next sweep, with no GitHub call. The detail is truncated at the source, so an over-long push error is compared as stored and never rewrites identical state. **One writer**: only the reconcile sweep writes these keys (`lithos_task_update` has no compare-and-swap); the `gates` CLI (§4.4a), Lens and any future webhook read them. A transition is logged (`reconciliation-state: <url> <old> → <new>`); it posts no finding — the state is the model, findings stay history. Records for another sha pair or another PR url are ignored, and a malformed record is treated as absent; a failed re-read derives from the sweep's copy, and a failed write is retried by the next sweep.

**Autonomous remediation (PRD S2 slice C + S5b).** When a posted `[ExternalReview]` batch carries at least one **trusted** actionable item (an allowlisted bot, or a human probed to repo write/admin — probe failure never dispatches), the sweep spawns `lithos-loom develop converge <pr> --from-github --story <story id> --json --repo <path>` as a crash-isolated subprocess — converge's own CLI re-applies the trust filter, runs the S5a triage, injects survivors, pushes and replies (§4.15a). The PR's repo path resolves `gate.metadata.project` → `[projects.<slug>].repo`, falling back to the story's `metadata.project`; neither resolvable → `[Friction]` log + skip. **One in-flight remediation globally** — while one runs, detection continues; a **dispatchable** batch (dispatchability — trust and the own-sha guard — is evaluated *before* any durable state) parks a durable pending trigger (`metadata.external_remediation_pending` on the gate, url-scoped) **in the same `task_update` as its seen high-water marks** — the marks consume the batch, so its dispatch debt becomes durable in the same write or the whole batch retries. An undispatchable batch neither parks nor clears (a newer batch can never erase an older batch's parked debt, and no park-then-clear crash window exists for the own-sha guard to leak through); a later quiet sweep resumes a parked dispatch, the trigger is consumed atomically with the budget reservation, dispatch-time refusals that retrying cannot fix (explicit opt-out, unmapped project) clear it, and it survives a busy slot, an exhausted budget, and restarts. Watcher shutdown cancels the in-flight run and terminates its converge subprocess (never an orphan that keeps pushing). Per-project dial: context-doc `develop_external_review_converge` (default **on**, ADR 0011 decision 6; an *unreadable* context doc fails **closed** — it may hold an explicit opt-out — leaving the pending trigger parked to retry, while a readable doc without the key is the default-on). The **S5b budget** lives in `metadata.external_remediation` on the **gate** (`{pr_url, rounds_used, last_loom_pushed_sha, last_seen_head_sha, needs_human_gate_id, needs_human_reason, no_change_refunded, last_status, last_settled, in_flight_boot_id, in_flight_pid, in_flight_pid_start, in_flight_host_boot}`, url-scoped; `last_status` / `last_settled` are how the budget's last run ended and whether it settled the PR (the CLI's `succeeded` verdict); `in_flight_boot_id` / `in_flight_pid` / `in_flight_pid_start` / `in_flight_host_boot` name the boot and the process identity that reserved the round while its run is in flight — stamped at reservation, cleared by every outcome write (#407) — every run outcome writes them, the reservation clears them, and the reconciliation state reads them, #408): default **2** rounds per PR (`[github_watcher].external_remediation_budget`; `0` disables dispatch), incremented **before** each run — strictly: a reservation write that did not land never spawns (an exit-0 run with no JSON result — nothing live to ingest — gives the round back; a produced result spends it — except a reported-not-remediated one, `already_clean` or `triage_rejected`, refunded once per budget, below). The counter **never resets on a loom-authored push** (the two-bot ping-pong the budget bounds; a completed run records its `pushed_sha` as `last_loom_pushed_sha`) and **resets when a human pushes** (head moved to any sha other than loom's recorded push — the operator took ownership; the first sighting is initialization only, so a PR whose spending rounds never pushed still resets); head observation goes inert while a run is in flight (attribution is ambiguous). Material reviewing loom's own pushed sha is reported, never auto-remediated (own-sha skip). **Exhaustion escalates** (PRD S5b → S7): a run that ends the budget still not converged (or dies without a result) raises a loom **`human` gate** on the story — `escalation_reason=remediation_exhausted`, `route=external-remediation`, `run_brief={pr_url, rounds_used, budget, last_status, cost_usd}` — through the same `raise_needs_human` core as the route-runner's failed exit (gate → record → push sinks → `[NeedsHuman]` on the story), once per budget (the gate id is recorded in the marker; a human push resets the budget and re-arms it, and so does completing the gate). The gate is a decision, not a re-dispatch — the story stays behind its `pr` gate — so its actions are remediation's own: push the fix branch by hand, re-run `develop converge <pr> --from-github` with a higher cap, or address the finding directly. Dispatch stops; `[ExternalReview]` keeps posting with the exhaustion stated in the finding body. **A reverted fix escalates too, with rounds to spare** (#387, lens #84: the coder fixed the external finding in round 1, the panel held the change contradicted the story's acceptance criteria, round 3 reverted it in full and loom replied `Fixed in <sha>` over a net no-op): a run whose result carries an external outcome `reverted` raises the same loom `human` gate now — `escalation_reason=disputed`, `run_brief={pr_url, finding_id, author, thread_url, coder_reason, pushed_sha, rounds_used}`, actions = decide between the review and the acceptance criteria (amend the criteria and re-run `converge --from-github`, or answer the reviewer and leave the code) — once per budget (`needs_human_reason` on the marker says why; the reconciliation state names the decision rather than an exhaustion), and a budget carrying an OPEN loom remediation gate — this one or the exhaustion gate — dispatches nothing (`escalated` — `consider` and a parked trigger alike, the trigger kept; the gate is read before the round count, so the last budgeted round is covered) until the gate goes terminal or a human push resets the budget. The gate is the budget's stop, and completing it is the operator's consent to continue: the marker forgets the gate and the budget **re-arms** (rounds reset, loom's push attribution kept), so the next batch or the parked trigger fires on a fresh budget — the decision need not involve a push. The objective backstop behind every `fixed`: an approved run whose final tree equals the PR head outside the generated paths undid its own fix — `reverted` whatever the coder wrote, since round 1 must commit. Each completed run posts an `[ExternalReview]`-prefixed *remediation outcome* finding on the story (status, pushed sha, per-finding dispositions — each with its `[note: …]` when the epilogue read a final acknowledgement against an earlier round's, #399 — spend); a run that fails without a result posts `[Friction]`. A run that ends `already_clean` — every injected finding refuted by triage, triaged `NOTHING_TO_REMEDIATE` (no claim at all: the run ends at round 0, before any coder or panel turn — 827cedf8), or dispositioned `no_change_needed` by the coder **and** the loop's own gate + panel approving the unchanged head, nothing committed (#380: an approval verdict ingested as a finding) — or `triage_rejected` (every claim refuted with citations at this head — the lens #84 route) is reported, not remediated: the reserved round is **refunded once per budget** (`no_change_refunded` on the marker — a paid run, so the refund is bounded; a fresh budget — a human push, or the completed decision gate — re-grants it) and nothing escalates. A dispatched run the daemon itself kills at shutdown is not a spent round (#407 slice 2a): the watcher's stop cancels the in-flight converge, then — guarded on a re-read of the gate, only while the reservation carries no recorded outcome (`last_status` empty, #410) — refunds the round in the same strict write that re-parks the trigger, and posts one `[Friction]` on the story ("lost to a loom shutdown … re-dispatches after the next boot"); a cancel that landed after the run recorded its outcome refunds nothing. The reservation also names the **boot** that made it (`in_flight_boot_id`, cleared by every outcome write), so a daemon that died *without* a shutdown — SIGKILL, a host crash — is reconciled by the next one (#407 slice 2b): the first sweep over the gate finds a stamp from another boot with no run in flight and no recorded outcome, refunds and re-parks it the same way ("lost to a daemon restart"), and the parked trigger re-dispatches later in that same sweep. A stamp whose dispatcher **identity** (pid + process start time + host boot id — a reused pid never matches) is still alive is a run that outlived its daemon — held as a real hold on the single-flight slot and on the per-PR holds the merge-gate and resolver read, never refunded or re-dispatched beside, and reconciled once it ends; and a run loom spawned binds its lifetime to loom — only under the `LITHOS_LOOM_BOUND_TO_PARENT` marker the spawn passes beside its own pid and start marker (`LITHOS_LOOM_PARENT_PID`, `LITHOS_LOOM_PARENT_START`; one `bound_child_env()` for every spawn site), so a hand-run CLI never dies with its shell. The child is bound to the **spawner as an ancestor**, not to its immediate parent (f6537c52: the story-develop route command is `uv run python -m …`, and `uv run` spawns python rather than exec'ing it, so the plugin's parent is `uv` — a parent-equality check exited every route plugin at startup with 143 while the `sys.executable`-spawned converge and merge-gate were unaffected): the child exits at once unless the spawner's pid is somewhere up its parent chain (`/proc/<pid>/stat` field 4, walked from `getppid()`, bounded; pid 1 is never accepted — a chain that reaches init without meeting the spawner is a child reparented because the spawner died in the spawn-to-bind window, to pid 1 or under a subreaper to anything), asks the kernel for SIGTERM on its immediate parent's death where it can (`PR_SET_PDEATHSIG`, Linux — right whoever that parent is; an intermediary that dies has taken the child's pipes and exit code with it), and always runs a spawner-watch thread that polls the spawner's **identity** (pid + start marker, the one the spawner stamped or one captured at bind time) and SIGTERMs itself on positive death only — a reused pid reads as dead, an unverifiable probe holds — so the guarantee holds off Linux, holds *through* an intermediary (where PDEATHSIG cannot see past `uv`), and a SIGKILLed watcher takes its converge child with it; the process identity reads `/proc` on a procfs host and `ps -o lstart=` / `sysctl kern.boottime` elsewhere — one provider per host, chosen by platform and never by whether a read succeeded, since the two report a start time in different units and a marker re-read through the other provider would look like a reused pid, i.e. positive death (PR #417 review); a provider that cannot answer is *unknown* — and identity capture fails closed: a new run is not reserved or dispatched until both its start marker and host-boot marker can be recorded, while a foreign stamp whose identity is missing or temporarily unprobeable remains a real hold until the watcher has positive evidence that its dispatcher died (the lifetime bind is cleanup after parent death, not proof that death already happened); a stamp beside a recorded outcome is not refunded (the outcome wins); the reconcile runs only where remediation runs at all (`external_reviews_enabled` on), never raises, and logs a refusal once per boot. **`lithos-loom drain`** (#407 slice 3) is the restart that spends nothing: SIGUSR1 at the supervisor is relayed to every child; the three dispatchers answer `draining` to every new decision from then on — before any reservation, so no round is stamped and a parked trigger stays parked for the next boot exactly as a busy slot leaves it — while the run in flight (and a dispatch already committing its reservation) finishes and records its outcome as usual; the child exits 0 once nothing of its own is running, and the supervisor exits 0 when the last child has (§4.1a).A dispatched run that ends **`infra_failed`** (#377) is not a spent round: the sweep refunds it, re-parks the review trigger, posts one `[Friction]` on the story naming the host action, and holds the PR from re-dispatch until the next daemon boot (the operator's fix attempt) — never an exhaustion escalation, since the change was not judged.

**Drift sync** (GH → Lithos, Slice 7.2). Every poll that matches a known Lithos task layers three checks on top of the close mirror:

- **Title drift** — `issue.title != task.title` → `task_update(title=issue.title)`.
- **Body drift** — `strip_marker(issue.body) != task.description` → `task_update(description=...)`. The `<!-- lithos:<id> -->` marker is never reflected into the Lithos task description.
- **Label diff** — read `metadata.github_labels` snapshot; compute `removed = old − new` and `added = new − old`; new tag set is `(task.tags − removed) | added`. Operator-added Lithos tags never in any GH snapshot survive untouched. The snapshot in metadata rolls forward to `issue.labels`.
- **State snapshot** — `metadata.github_state_snapshot` rolls forward to `issue.state` on every poll. Reopen detection compares the *prior* value before drift sync overwrites it.

All four drifts in one poll batch into a single `task_update` call. Steady-state polls (nothing changed) cost zero round-trips. Drift runs on **every** matched task, terminal or open — lithos#303 once forced a terminal-task skip, now lifted (#124), so a reopened terminal task's `github_state_snapshot` rolls forward in the same poll and the `[ReopenRequested]` finding stays one-shot.

**GitHub issue mirror (Lithos → GitHub, Slice 7.2).**
The `github-issue-push` subscription (auto-wired in the github-watcher child) consumes `lithos.task.{created,completed,cancelled,updated}` events from `LithosEventStream` on the in-process bus. The `task.created` event is the open-task snapshot replay surface at daemon startup — a Lithos rename that happened while the watcher was down only re-fires as `task.created` on restart, so the title branch consumes it identically to `task.updated`. The handler branches as follows:

- `lithos.task.completed` → fetch GH issue; if not already closed-as-completed, `PATCH state=closed state_reason=completed`.
- `lithos.task.cancelled` → same, with `state_reason=not_planned`.
- `lithos.task.updated` → if `task.title` differs from the current GH issue title, `PATCH title`.

Tasks without `metadata.github_issue_url` are filtered at the handler entry (the by-far-common case) and stay silent at INFO. Permanent GH errors (auth / repo-404) during the push surface as `[Friction]` log lines, not retries — a permanent failure shouldn't loop.

**Deleted linked issue self-heals (#69).** When the linked issue is gone — the GET returns `None` (404), or the PATCH raises the issue-specific `GitHubIssueNotFoundError` (a deletion racing the GET; distinct from a repo-404 so a deleted issue is never mistaken for a deleted repo and never drops the repo from the watch list) — the handler posts a one-shot `[LinkedIssueGone]` finding and writes a `metadata.github_issue_gone_url` marker scoped to the gone url. The handler entry skips a task whose marker matches its current `github_issue_url`, so subsequent `task.*` events stop re-probing the dead link (vs. a `[Friction]`/skip per event forever). The marker write's own `task.updated` event carries the marker (the event stream re-enriches with current metadata), so it lands on the skip and the heal does not loop. Re-linking the task to a new issue changes `github_issue_url`, the stale marker no longer matches, and the new link is re-evaluated.

Pull requests are filtered at parse time (presence of GitHub's `pull_request` field on the row). A 404 on a watched repo drops it from the in-memory watch list with a `[Friction]` log line; the next bus-driven refresh re-adds the slug if the operator fixes the typo. GitHub rate-limit responses (403 with `X-RateLimit-Remaining: 0`) trigger a sleep until `X-RateLimit-Reset`; a 403 with non-zero remaining surfaces as auth/permission error rather than retried indefinitely.

### 2.3 Restart and Recovery

Loom has no persistent event log. On restart:

- `LithosEventStream` and `LithosNoteStream` bootstrap (re-list and re-emit) and then resume via `Last-Event-ID`.
- `ObsidianFSWatcher` and `ObsidianDirWatcher` re-scan their watched files on startup; sync-state baselines are rebuilt incrementally as projection events fire.
- `obsidian-projection` writes the full file from scratch on every flush. Idempotent re-runs are no-ops thanks to atomic-write + content-hash dedup.
- `project-context-projection` re-reads each doc and rewrites if the full-file hash differs.
- `note-push` and `obsidian-status-transition` pre-check Lithos state before mutating (re-firing an already-completed task is a no-op).
- The route-runner does NOT reclaim stale claims from a previous process at startup. Stale claims age out via Lithos's own claim-expiry mechanism; a future run picks the task back up when the claim TTL elapses.

Subscriptions are idempotent by construction; replay is safe. Bootstrap-replayed events additionally carry `Event.origin = "bootstrap"` (everything else is `"live"`), and the route-runner uses it to decline re-dispatching a story whose `metadata.loom_last_attempt:<route>` records a failed last attempt for an unchanged task — a restart must not re-spend a full plugin run that failed; editing the task (any edit when the recorded `updated_at` stamp is available, else a title/description/tags fingerprint change) or deleting the marker makes the replay re-dispatch it (§2.2).

### 3.2 Validation

`lithos-loom validate-config` parses, typechecks, and lists projects / routes / subscriptions. `validate-config --dry-run` additionally polls Lithos and prints which routes / subscriptions would fire for each currently-open task plus any orphans (tasks no route matches) and dead config (routes / subscriptions no task currently matches). Both forms exit non-zero on invalid TOML.

**Readiness in the dry-run (Epic G / US7).** The simulation reads the same server-side ready-queue the runner dispatches off (§2.2) — one `lithos_task_ready` sweep for the dispatchable frontier plus one `lithos_task_blocked` sweep for the reasons — rather than re-deriving readiness from `metadata.depends_on`, so the report cannot drift from runtime behaviour. A tag-matching task Lithos doesn't consider ready renders as `deferred (<kind>: <predecessor> (<status>))` using Lithos's own structured blocker vocabulary: **`task`** (predecessor still open — just waiting), **`gate`** (waiting on an unresolved gate), **`blocker_unsatisfiable`** (the predecessor was *cancelled* — this one needs operator intervention, not patience), or **`cycle`**. A task that is neither ready nor blocker-shaped (e.g. an `epic` / `gate` task, which is never dispatchable work) renders as `deferred (not on Lithos's ready frontier)`. Neither sweep has a per-task filter, so both are capped at `READY_QUERY_LIMIT` (500); if either comes back full the report prints a `⚠ … query limit` line, since the rows below may then be incomplete.

**Orphan / dead config vs deferred.** These are *routing* questions, so they key off whether a task's tags **matched** a route — not whether it would claim right now. A deferred task is routed and waiting, so it is **not** an orphan, and a route matching only deferred tasks is **not** dead config; reporting either would send the operator to fix routing that is already correct. Deferred tasks instead get their own informational summary section (`deferred tasks (N) — routed, waiting on Lithos's ready-queue`), with the per-task reasons in the table above.

`lithos-loom doctor` verifies the configured `vault_path` exists, `_lithos/` is creatable, and a probe write+read round-trip works. It probes the **Lithos task-graph extension** end to end (creates throwaway probe tasks — an `epic`, a blocker + dependent joined by a `blocks` edge, and a spawned follow-on — asserts `lithos_task_ready` / `lithos_task_blocked` honour the edge — including that a *cancelled* blocker keeps its dependent `blocker_unsatisfiable` — and that `task_type` / `lithos_task_spawn` round-trip; it then probes **gate** semantics (Epic H): a `pr` gate joined to a waiter by a `waits_on_gate` edge must withhold the waiter from `lithos_task_ready`, surface as a `kind="gate"` blocker in `lithos_task_blocked`, and — on `lithos_task_complete` — report and release its waiter; finally cancels the probe tasks). It also reads `lithos_list(path_prefix='projects/')` and warns about TOML `[projects.<slug>]` entries with no corresponding Lithos project-context doc. The same task-graph probe gates `lithos-loom run` (see §4.1).

## 4. CLI Reference

### 4.1 `lithos-loom run`

Starts the daemon: supervisor + per-domain children. Foregrounded process; SIGINT / SIGTERM trigger graceful shutdown — the supervisor signals children to stop, in-flight plugin subprocesses are cancelled, and the supervisor waits up to a timeout before SIGKILLing any child that didn't exit. Cancelled plugins that don't write a result file trigger the contract-violation release path; claims may also be left to age out via Lithos's claim TTL. SIGUSR1 is the **drain** (§4.1a): relayed to every child, which stops admitting new dispatch, finishes what is in flight and exits 0; the supervisor exits 0 when the last one has, with no grace clock and nothing killed.

**Pidfile (#407 slice 3).** First thing, `run` claims `<work_dir>/supervisor.pid` and holds it for its lifetime; `lithos-loom drain` finds the daemon through it. Ownership is an exclusive `flock` on the file (taken non-blocking; released by the kernel when the process ends, however it ends; never released by an unlink — nothing unlinks the file), so two boots racing the same work dir admit exactly one and there is no stale-eviction step to race: a held lock refuses the boot (exit `1`, before the orphan reap and the boot gate: one daemon per work dir — two route-runners would claim the same tasks); a file nobody holds, whatever it names, is stale and claimed over. The content is the process identity (pid + start time + host boot id), not a bare pid — the fallback for liveness only where the lock is unknowable, and what `drain` signals. A pidfile that cannot be opened or locked at all **refuses the boot** too (exit `1`, with the reason): the lock is the singleton boundary, and without it one daemon per work dir cannot be proven.

**Boot gate (Epic G).** Before starting the supervisor, `run` runs the same task-graph capability probe as `doctor` (a real Lithos round-trip) and **refuses to start** (exit non-zero) if the extension is missing / broken — the runner schedules dependencies via Lithos's server-side ready-queue, so an incompatible server must surface at boot, not mid-PRD. This means the daemon also won't start while Lithos is unreachable or mid-restart (the probe reports `lithos_unreachable`); re-run once Lithos is back. **Orphan reap (#407).** Right after the gate, before any child spawns, `run` removes every run container a previous daemon left behind: each sandbox is started with a `loom.pid=<owner pid>` label, and `docker rm -f` takes the ones whose owner process is gone — the operator's own hand-run `develop converge` / plugin runs are alive processes and are left alone; a container started before the label existed is never touched. Never fails the boot.

```
lithos-loom run [-c config.toml]
```

Exit codes: `0` clean exit, non-zero on child crash before shutdown or SIGKILL after timeout, or when the boot gate refuses (task-graph extension unavailable), or when a live daemon already holds the work dir's pidfile (or its lock cannot be established).

### 4.1a `lithos-loom drain` — finish in-flight runs, then exit (#407)

The restart that costs nothing. Reads the supervisor's pidfile under the configured work dir, checks that the identity it read is not positively dead, that the file still names it, and that its lock is held (the lock alone proves only that *some* process owns the path — a successor that claimed within a poll is not the daemon being drained; the identity is the fallback where the lock is unknowable), sends SIGUSR1, and waits for that daemon to exit — a successor that takes the file meanwhile is reported, never signalled or waited on. The supervisor relays the signal; each child stops admitting new dispatch — the route-runner claims nothing more (a task that arrives, a bootstrap replay, an admission wake, a usage-limit resume are all refused before any Lithos read, and again right before the claim; every run in flight is counted, so a resume running beside a bus-path run holds the drain until both end), and the github-watcher's remediation, merge-gate and conflict-resolve dispatchers answer `draining` to every new decision before any reservation (a merge-gate probe already out never starts the run it would have; a pushed resolution's unflushed record + budget write still flushes — that is the run's own outcome; a parked trigger stays parked for the next boot; the sweep keeps observing, but leaves the S7 reconciliation state as the last deciding sweep recorded it — `draining` is a refusal to decide, not a verdict) — finishes what is in flight, lets it record its outcome, and exits 0; obsidian-sync, which runs nothing paid, treats the drain as a stop. The supervisor exits 0 when the last child has. A restart after `drain` returns is safe by construction: no run was killed, no remediation round refunded, nothing re-dispatched twice. SIGTERM during a drain is the ordinary shutdown (the remaining children are terminated; the watcher refunds the round it kills, §2.2); a child that exits non-zero while draining — or exits at all before the drain was relayed — is a crash like any other. A child still importing when the signal lands ignores it (SIGUSR1 would otherwise terminate it); every SIGUSR1 at the supervisor is relayed, so re-running `drain` reaches it.

```
lithos-loom drain [-c config.toml] [--timeout SECONDS]
```

`--timeout` (default `0`, no deadline) bounds the wait only: when it runs out the daemon keeps draining and `drain` says so. Exit codes: `0` the daemon exited; `1` no daemon to signal (no pidfile, a stale one, or the signal could not be sent — reported, never guessed at); `2` the timeout ran out with the daemon still draining (stop it now with SIGTERM if you must — a killed remediation round is refunded).

### 4.4a `lithos-loom gates`

```
lithos-loom gates [-c config.toml]
```

Read-only inventory of **every open gate** (`task_type=gate`). Columns: `GATE`, `TYPE` (`metadata.gate_type`), `STATE` (a `pr` gate's `metadata.reconciliation_state`, PRD S7 — `—` for other types), `REF` — the watched PR (`owner/repo#number`) for a `pr` gate (Epic H), the `escalation_reason` for a loom-raised `human` gate (b91177d2), `—` otherwise — the story the gate blocks (its `waits_on_gate` waiter), the waiter's status, and a one-word **health** classifying the wiring the resolvers depend on. A loom-raised `human` gate adds an indented `↳ <escalation_summary>` line under its row — the one-line "why loom stopped" the operator triages by. The operator's own `human` gates and `timer` / `ci` / `external_task` gates are listed with wiring health only.

- `ok` — open waiter + readable loom metadata (working as intended).
- `orphan` — no `waits_on_gate` edge, so the gate blocks nothing.
- `malformed` — a `pr` gate whose PR metadata is missing/ill-typed, so `parse_pr_gate` can't read a PR to watch (the waiter stays blocked forever), or a loom `human` gate with no `escalation_reason`.
- `waiter-gone` — the `waits_on_gate` edge points at a task that no longer exists.
- `waiter-resolved` — the waiter is already completed/cancelled while the gate is still open. For a **loom-raised `human` gate** this is transient: the github-watcher's reconcile sweep completes every loom human gate whose waiter is terminal (04c2448b hygiene — the operator completed or cancelled the story by hand; the tidy-up never nudges), so the row clears within one `reconcile_interval_minutes`. The operator's own `human` gates are never touched.

Precedence when several apply: `orphan` → `malformed` → `waiter-gone` → `waiter-resolved` → `ok`. The listing closes with a three-line summary footer: a headline count (`N open gates: H healthy, A need attention`), a per-type breakdown (`by type: 1 human, 2 pr, 1 raised by loom`), and a per-health breakdown (`by health: 2 ok, 1 orphan, …`) counting each health class present, in the order `ok` → `orphan` → `malformed` → `waiter-gone` → `waiter-resolved` (zero-count classes omitted). An empty inventory prints just `no open gates`. Non-mutating (one open-task sweep plus a per-gate edge/waiter read; no GitHub round trip). Exit codes: `0` on a successful listing regardless of gate health; `1` if the config can't load or Lithos is unreachable.

Exit codes: `0` success, `1` Lithos call failed, `2` validation failure (unknown project, unknown priority, mutually-exclusive output flags).

### 4.14 `lithos-loom develop list` / `attach` / `dump` / `prune`

```
lithos-loom develop list   [-f text|json] [-c config.toml]
lithos-loom develop attach <run-id|task-id> [--once|--wait|--stream] [-c config.toml]
lithos-loom develop dump   <run-id|task-id> [-c config.toml]
lithos-loom develop prune  [--dry-run] [-f text|json] [-c config.toml]
```

Mostly read-only observability over in-flight `story-develop` runs (#88) — `prune` is the one mutating command. Discovery is zero-state: it scans the orchestrator `work_dir` for the `<work_dir>/<task_id>/<run_id>/` layout the route-runner + plugin produce, reads the per-round `handoff/` files, and queries `docker` for the run's `loom-develop-<run_id>-*` agent containers (the **active** agent is the one with a live `claude`/`codex` process — a turn is one `docker exec`; each container also carries a `loom.pid` label naming the host process that started it, which `prune` falls back to for a run dir with no owner marker of its own). The route-runner **reaps the work dir on success**, so these commands observe **in-flight + failed/interrupted** runs; a succeeded run's dir is gone (its outcome is the `[DevelopResult]` finding).

- **`list`** — table (or `json`) of inspectable runs: run id, task id + title, current round, the active agent (or `idle` / `done`), and an `updated` timestamp (the run's last on-disk activity — the newest mtime across the run dir, its `handoff/` dir + handoff files, and any terminal `conversation.md`, since a fresh round handoff bumps the `handoff/` dir, not the parent; this is also the newest-first sort key; local wall-clock in text, raw epoch `mtime` in `json`). The title is the one **this run started with** — story-develop snapshots the task envelope into the run dir at start, so an older retained run keeps its own title even after the task is re-dispatched (the shared per-task `task.json` is overwritten each dispatch); it falls back to the per-task file for in-flight runs predating the snapshot. A **`pr`** column names the PR this run's branch is behind — the run's own delivery (its run-bound `result.json`) or a hand one (`develop deliver`, which records the url in the run's private `delivery.json`) — so a stopped run whose work is already on the maintained path is distinguishable from one still waiting on its needs-human gate; `—` (empty string in `json`) when it has none. Those two are local files; for any run they cannot answer for (a delivery that predates the marker, or one whose best-effort write failed) the column falls back to the **authoritative** record, the story's `pr_gate_id` → that gate's `pr_url`, in one Lithos session for the stories that need it. Only an **open** `pr` gate counts — `pr_gate_id` outlives the gate it names, and a story whose PR closed unmerged can be re-escalated and re-developed, so a stale gate would report a live run as delivered. The answer is about a **story** and a task can retain several runs, while the gate records no run, so it is attributed to the run the story's `manual_delivery` marker names **for that PR**, and — with no marker, or one about another PR — only when exactly one run could be its subject, which counts the runs that answered for themselves too (a sibling whose own `result.json` / `delivery.json` already records that PR **is** the delivery, so the gate is placed and nothing unresolved may claim it as well — otherwise the run nobody could answer for inherits its sibling's PR for exactly that reason): a sibling run is never shown behind a PR it did not produce, which matters most in `prune`, where it would be deleted for it. An unreachable Lithos yields nothing at all rather than an error. Every cell is stripped of terminal control bytes and folded to one visual line before it is laid out (a mirrored story's `title` is an outside issue title, and the whole row is emitted as one write, so a bare CR would rewrite it from column 0); the `json` form is escape-safe via `json.dumps`.
- **`attach <run-id|task-id>`** — follow a live run, printing each handoff as it lands plus the current round + active agent, until the run reaches a **terminal state**, then a one-line outcome summary. Following keys on terminal *state* — the recorded **outcome** (`state.json` with a status) — **not** agent liveness, so it spans both the **startup window** before the first container comes up (the old container-liveness check exited there instantly as "done") and the commit / test-gate / teardown after the last agent turn. An **approved** verdict is not yet terminal in daemon mode: PR delivery (branch push, PR open, `result.json` write) runs *after* the dialogue approves — `develop()` writes the approved `state.json` and returns, then `__main__` calls `deliver()` — so attach follows through a distinct **"delivering PR…"** phase rather than exiting on the bare verdict (which would re-open the false-done window). The real end of an approved run is its `result.json` landing (a `succeeded` status in the shared per-task dir, distinguishing it from a prior retained run) or the success reap. The terminal signal is deliberately the outcome and not `conversation.md`: the plugin writes the log *first* and `state.json` *after*, and it also force-removes the agent containers *before* either, so attach **grace-polls** through the window where the containers are gone but the outcome isn't written yet rather than declaring a crash (and `--wait` / the summary can always read the recorded status). On **success** the route-runner reaps the whole work dir (taking `state.json` with it), and a fast run can be written-and-reaped between two polls; attach then recovers the outcome from the plugin's host-persistent **completion store** (the idempotency record, written before the reap and never removed by the route-runner), located by this run's id via the recorded conversation-log path — so it is found regardless of whether the run used the default (task-id) idempotency key or an explicit `--idempotency-key`, and a missed `state.json` on an approved run is still reported as approved. The outcome summary reflects the recorded/recovered status (`approved`, `NOT approved (max rounds reached)`, `failed`, `interrupted (re-run to retry)`, `stopped (stalled|dispute…|cost…)`) — and, so the line answers "did it finish, and how?" (#188), names the **delivered PR url** for an approved run (read from this run's `result.json`, recovered from the completion store on a reap) and **why** a stopped run stopped (the failure reason from `state.json`) — notes a reaped run whose success couldn't be recovered (e.g. a non-default idempotency key), notes a crash only when the containers vanished and no outcome was ever recorded across the grace window, names that an approved run's **PR delivery failed** with its reason (#194) — when `deliver()` raised before a PR opened, the daemon marks the run's private `run_dir/delivery.json` failed, so attach reports it terminally at once (and `--wait` exits non-zero) instead of waiting out the delivery deadline — or notes that an approved run's **PR delivery did not complete** — the `"delivering PR…"` phase is bounded by the **delivery deadline the daemon records** before delivery starts (`run_dir/delivery.json` = now + the delivery overhead budget — no agent phase remains since the inline Copilot round was retired, S2 slice D; a generous flat fallback when no deadline was recorded). Delivery runs host-side *after* the agent containers stop, so their absence is not a crash signal, and the bound is the daemon's actual budget — so a healthy slow delivery is **never** falsely timed out, while a crash/reboot that leaves `result.json` unwritten is reported as delivery-incomplete rather than followed forever (#189). Handoff name/body are agent-writable (RW bind mount), so the text view strips terminal control/escape bytes and the read is bounded in both per-file size and per-poll file count (the JSON `--stream` path is escape-safe via `json.dumps`). Modes (mutually exclusive): `--once` prints a single snapshot and exits; `--wait` blocks **quietly** — first until the run *appears* (so it can be invoked immediately after dispatch, before the run dir is seeded) **or until the completion store shows it already finished without an observable run dir** (an idempotency replay writes `result.json` and exits *before* creating the dir; a fast success is reaped between two polls — either way `--wait` recovers the outcome from the store and reports it rather than hanging forever, #196), then through PR delivery to the terminal state — and prints **only** the outcome, exiting non-zero unless the run was `approved` **and fully delivered** (a delivery that timed out (#189) or failed (#194) exits non-zero too, so `attach --wait && gh pr view` can't race a PR that never opened) (a scripting primitive); `--stream` emits newline-delimited JSON events (`{"event":"state"…}` / `{"event":"handoff"…}` / a terminal `{"event":"outcome"…}`) for machine consumption. Read-only; `Ctrl-C` exits cleanly.
- **`dump <run-id|task-id>`** — print the assembled conversation log: `conversation.md` for a finished run, else the per-round handoffs assembled live (the plugin writes `conversation.md` / `state.json` only at run end). Keyed by run id or task id.
- **`prune`** — delete the on-disk run-state dirs of **finished** runs: the failed / interrupted / killed dirs that accumulate (succeeded runs are already reaped), plus the on-demand worktrees under `work/converge/`, `work/review/` and `work/merge-gate/`. *Finished* is decided from **liveness**, not from one file — a run dir counts as finished when **either** it wrote its terminal `state.json` / `conversation.md` (the epilogue `develop()` writes after the agent containers stop) **or** nothing is alive for it **or** its branch is delivered as a PR — the daemon's own delivery record, a `develop deliver` that **finished** (its run-dir marker's completion bit, written only after the gate swap and the provenance landed: a partial delivery's exit-2 text says to re-run on that dir, so the dir outlives it), or the story's open `pr` gate attributing the delivery to this run (`delivered as <pr>` in `--dry-run`; only a live agent container outranks it). Before this the terminal log was the *only* signal, so a run killed before its epilogue (OOM / SIGKILL / crash), a converge `-intake` pass, a `merge-gate` worktree, or a run that died during startup read as "in flight" forever and the residue only grew.
  - **"Nothing is alive for it"** is read, not guessed. (0) If `docker` cannot be asked at all, nothing is decided: a killed plugin can leave its `--rm` container — and the `docker exec` inside it — running, so absent a terminal log the dir is `unknown — kept` whatever else says. (1) No **running agent container** for the run id. (2) The run's **owner marker**: every run stamps `owner.json` into its run dir — the *identity* of the process running it (pid + kernel start time + host boot id, so a reused pid is not mistaken for the original) — **before** it fetches and checks out its worktree. That marker is the only signal that survives `--rm` and the teardown `docker rm -f`, and the only one that exists at all during the containerless startup phase, which is unbounded. It is not best-effort: a host that cannot read its own process facts still writes a marker saying *that* (read as `unknown — kept`, never as "nobody home"), and a producer that cannot write one at all fails before it touches the run dir. A marker whose process is **positively gone**, with docker reporting no container up, settles that half definitively. Absent a marker (a run dir predating it), the `loom.pid` **label** on a stopped container stands in. (3) The other half is always the **idle test**: nothing anywhere under the run dir has been written for longer than one agent turn — the run's **own** largest agent-turn timeout (`max(--coder-timeout, --reviewer-timeout)`, recorded in its `owner.json` before any slow work; the `--coder-timeout` default of 3600 s is the floor, so a run that recorded a shorter one still gets the default grace window and a run without the field — a marker predating it — gets the default) — *longer than*, so the boundary itself keeps the dir. It is not a proxy for liveness but the **grace window** a just-stopped run gets, so a crash stays on disk long enough to be looked at (and long enough for the route-runner to finish reading its result); a run whose owner died seconds ago is kept, and goes on the next sweep after the window.
  - The **idle test reads mtimes the run's own agents can write**, so it is hedged — and every hedge resolves the same way: *if the age is not established, the dir is kept and named, never deleted*, which is the acceptance criteria's own rule for a dir the sweep cannot classify. The walk never follows a symlink (an agent could otherwise point it at a continuously-written host path and read that as its own activity). A mtime in the **future** is neither counted as the newest (`utime(2)` on a file one owns needs no privilege, so counting it would pin the dir as "fresh" forever) nor ignored (ignoring it would hide the real newest write behind an older visible one): it is recorded, and it means the age is unknown. So does a subtree that could not be listed (a mode-000 directory — which a red check can leave behind by itself, `check_runner.py`) or a walk that stopped at its **entry budget**; the budget is deliberately set far above any honest tree (a big worktree plus a gate export per check per round runs to hundreds of thousands of entries) because a truncated walk holds the dir rather than sweeping it, and the size it did measure is then reported as the floor it is (`>= 1.2 GiB`; `size_partial` in `-f json`).
  - **A gap in the walk outranks the liveness answer.** A provably-dead owner establishes that nothing is being written *now*; it cannot establish that an unseen file was not modified in place seconds before the run died (an in-place write bumps no visible ancestor mtime), so a settled liveness answer plus an incomplete age is still `unknown — kept` — with the blocking path named, so the operator can finish the job by hand. The cost is accepted deliberately: a dir that could have gone holds disk the operator can reclaim, while the other reading deletes a dead run's artifacts inside the window that exists to preserve them. A run whose own agent left a mode-000 directory behind is therefore held by this sweep — that is the trade, not an oversight.
  - A path quoted in a reason is **agent-chosen** (any byte but NUL and `/` is a legal filename) and lands on one line of the screen the operator decides on, so it is rendered line-safe: control bytes stripped as `attach` / `dump` strip them, plus the LF and TAB that stripping deliberately keeps for multi-line bodies — one record, one line, so a crafted filename cannot forge or erase a record beside a real one.
  - A converge **intake** pass (`<run>-intake` — review-only, so it never writes an epilogue) is finished with its parent run, and held while the parent is live; on its own (parent already gone) it follows the same liveness rule.
  - A dir the rule **cannot classify** — `docker` unavailable, a marker that is unreadable or that names no process this host can verify, an owner pid the kernel will not answer for, a container row whose `loom.pid` label is absent or not a checkable pid, or a tree whose age it could not establish (unreadable, future-stamped, too large to walk) — is reported as `unknown — kept` and **never** deleted, with the reason naming what it could not read. In-flight runs are likewise named and kept, never touched.
  - `--dry-run` lists every candidate with **why** it counts as finished (`terminal log written` / `no live process and nothing written since <time>` / `intake pass of run <id>, finished: …`) and **how much disk** it holds, and deletes nothing. `-f json` reports each discovered run with `state` (`finished` / `in flight` / `unknown`), `reason`, `size_bytes` + `size_partial` and a `pruned` flag (plus an `error` field when a deletion fails). Emptied per-task dirs are reaped too. A failed deletion is reported as an error, never as success, and exits non-zero.
  - Discovery is wider than the other three commands' (which need a seeded `handoff/`): prune also recognises a run dir by its `worktree/`, `agents/` or `test_gate/` subdir, its owner marker, or its terminal log — that is what brings the `merge-gate` worktrees (which never seed a handoff dir) into the sweep. A dir with none of those is not a run yet (a dispatch caught between `mkdir` and its first write) and is left alone, and a **symlinked** task or run dir is skipped outright — nothing loom creates is a symlink, and following one would point a privileged walk (and an `rmtree` that then fails on every future sweep) outside the work dir. Not the daemon's own `retain_failed_workdirs` reaping (§5.3) either — this one is the operator's.

Live `docker exec` transcript streaming (watch the agent think token-by-token) is a deferred follow-up; `attach --stream` emits handoff/state/outcome *events*, not the raw agent token stream. When `docker` is absent the file-based views still work; the active agent shows as `—`.

### 4.15 `lithos-loom develop review` — review-only mode (#154)

```
lithos-loom develop review <pr|range|branch>
    [-p|--profile standard] [--reviewer NAME ...]
    [--ac TEXT | --ac-file PATH] [--base REF] [--test-timeout N]
    [--repo PATH] [--json PATH] [--keep-worktree] [-c config.toml]
```

Runs *just* the reviewer panel + deterministic gate against a change that **already exists** — no coder, no fix loop — and emits a consolidated report. Where `develop()` *produces* a change (worktree off a base, coder commits onto it), review-only *consumes* one: it materialises a **detached** worktree at the change's head, resolves the base separately, runs the resolved profile's check-set once on that tree (each check against its own fresh, never-reused export of the committed tree — verdicts independent of earlier checks' workspace mutations, #282), runs each reviewer once (round 1), and reports. It drives the **same** `run_panel_round` primitive the develop loop uses, so the two review paths can never diverge. See [ADR 0004](adr/0004-review-only-mode.md) and [`docs/cli/review.md`](cli/review.md).

- **Change input** (auto-detected from the argument):
  - a **GitHub PR** — `#142`, bare `142`, or a PR URL — resolved via the typed GitHub client (`GitHubClient.get_pull_request`: head sha, base branch, title, body — one seam shared with the watcher family, ADR 0008); the base is derived as the merge-base of the base branch and the head (the true diff base, avoiding spurious deletions when the base advanced), and the PR head + base refs are fetched so both commits are local. Works for fork PRs (`pull/N/head`). The PR *number* selects the PR against the local checkout's origin (a bare number or a URL both resolve there).
  - an explicit **`base..head` ref range**.
  - a **local branch / ref** — base is its merge-base with `main` (override with `--base`).
- **Acceptance criteria** (the reviewer's brief) precedence: `--ac-file` > `--ac` > the **PR body** (for PR input). A bare range / branch with no AC is rejected — a reviewer with no criteria is near-useless.
- **Panel / profile.** `--profile` selects the persona panel + check-set (default `standard`); `--reviewer NAME` (repeatable) overrides the personas. The deterministic gate runs the profile's full check-set (fast + candidate, since review is a one-shot) on the head tree.
- **Output.** A human-readable markdown summary (grouped by reviewer, plus a gate line) to stdout; `--json PATH` writes the structured report (the stable contract the review-correctness eval harness, #183, consumes). No GitHub / Lithos side effects in this slice — posting findings to a PR / Lithos task is a deferred follow-up. The worktree is removed on exit unless `--keep-worktree`.
- **Intake fetch failures are `infra_failed`, not tracebacks (#431).** The PR head + base fetch every intake surface shares retries a transport failure (`Could not read from remote repository`, a reset, a timeout, an `early EOF`, a `kex_exchange` — matched against git's **whole** stderr, since the one reported line is a collapse that hides a `fatal: early EOF` under an `error: RPC failed …`) **3×** with a short backoff, the attempts sharing **one** fetch timeout so a hung origin costs one, not three; a `git` that cannot even be spawned is the same kind of failure, not an exception. One that persists ends the command with a single line naming what to fix on the host — git's own first `fatal:` line, stripped of anything that could render as something else and bounded, since the origin host wrote it — `{status: "infra_failed", host_action, message}` under `--json`, and exit **1**.
- **Exit code** is non-zero when the review is **blocking** (any reviewer finding at/above its threshold, an incomplete panel, or a required gate check blocking — the *same* floor `develop()` applies).

Needs `docker` + the agent CLIs (`claude`/`codex`) + `gh` on the host, like a develop run; it is host-only, not part of the hermetic `make check`. Before any container starts, the explicit-model policy (#304, §5.5) applies `[story_develop.default_models]` to the resolved panel (including the built-in fallback reviewer a gate-only profile folds in) and rejects any reviewer still on `model=None` with a usage error. `develop converge` (§4.15a) applies the same policy and extends it to its coder.

### 4.15a `lithos-loom develop converge` — on-demand PR convergence (ADR 0009)

```
lithos-loom develop converge <pr>
    [-p|--profile standard] [--reviewer NAME ...]
    [--ac TEXT | --ac-file PATH] [--base REF] [--coder claude|codex]
    [--max-rounds N] [--max-cost USD] [--test-timeout N] [--no-push]
    [--repo PATH] [--json PATH] [-c config.toml]
```

Converges an **existing PR** to review-green: it runs the reviewer panel + deterministic gate against the PR (the same intake `develop review` runs), and if that **blocks**, enters a coder fix loop on the PR branch — implement→review→fix rounds until the panel LGTMs **and** the gate floor is clean — then **fast-forward-pushes** the fixed branch back to the PR head ref, ready for the human merge gate. This automates the operator's manual "paste the review, tell the coder to fix, re-review, repeat" chore and realises [ADR 0003](adr/0003-code-quality-review-strength.md) §9 "Shape 1" (re-dispatch development on the PR branch without resolving the `pr` gate) as the on-demand / human-triggered variant. See [ADR 0009](adr/0009-converge-pr-loop.md) and [`docs/cli/converge.md`](cli/converge.md).

- **One loop, not a fork.** converge does **not** re-implement the develop loop: it calls `develop()` with a `LoopEntry` override so the coder/panel/gate/dispute/stall termination is single-sourced (the parameterization shipped as converge PR 2). Round 1 is a cold-start prompt that reconstructs the PR author's intent (acceptance criteria + `git log base..head` commit log + the code) before changing anything, and **disputes** a finding that conflicts with a deliberate decision rather than blindly complying. The intake reviewers are **cold** by design (no coder-summary anchoring); only the fixer needs intent.
- **Isolated intake artifacts.** The intake review runs under a **distinct `run_id`** (`<run_id>-intake`) from the fix loop, so their round-1 handoff dirs, gate tree exports (`gate_dir/round_01/tree`) and container names — all `run_id`-derived — can never collide. A shared id would let intake's PR-head export or a stale reviewer handoff bleed into the fixed-tree gate + panel; the in-memory intake seed (reviews + check-set) carries over regardless.
- **Three intake modes.** By default it converges against loom's in-container codex/claude panel + check-floor. With `--from-github` (PRD S2 slice B) it instead ingests the PR's external review findings — reviews, inline comments and Conversation-tab comments (the only channel open to the PR's own author, #353): trust-filtered (allowlisted bots + write/admin humans; everyone else reported, never prompted — ADR 0011 d8), **triaged** by a cheap read-only turn that may reject only with cited `file:line` evidence resolving to a real tracked file (referent-checked; line-existence/content deliberately not — that is the S8 eval fixtures' job) and defaults to act (S5a; all-rejected → `triage_rejected`, exit 0). The same turn may answer `NOTHING_TO_REMEDIATE` for material that is no claim at all — a pure approval, the other half of "an approval is not a finding" (827cedf8, §2.2): nothing is injected for it, no thread is answered, and a batch whose every finding is one ends the run `already_clean` at round 0 (the #380 outcome without the coder turn and panel pass). It cites nothing — there is no claim to refute — so the **stated reason** is what the operator reads in place of a citation (a bare `NOTHING_TO_REMEDIATE` proceeds, like a bare `REJECT`), and that reason rides the finding's `nothing_to_remediate` disposition onto the story's remediation-outcome finding. Its guard is **eligibility**, decided in code from the row rather than from the verdict sentence: the verdict is honoured only for a finding whose own body carries recognised approving words (`carries_approval` — the weak half of the ingestion classifier, with the approval **emoji** — and its `:+1:`-style shortcode — counting only when it is the whole verdict, never as decoration inside prose, so a checkmark-bulleted defect report is not eligible; the floor also reads the body at a **coarser** split than the end-to-end rule — a finer split is conservative where every unit must pass and permissive where one passing is enough, so `:` is not a boundary here and a label line, a citation or an unknown shortcode ("Field: `approved`.", ":lgtm: the token is logged") cannot hand it a bare approval word its author never wrote; the floor also reads only **authorial** text, at the granularity GitHub renders — a block quote, a fenced code block (parsed structurally: it ends only at a line holding nothing but a fence at least as long as its opener, so a longer run with trailing text is content), an inline code span (closed by a run of exactly its own length), an indented code block, a strike-through, an **HTML comment** (invisible on the rendered PR, so nothing a human can see approves), an enumeration of values (a list whose items are not all approvals, or one under any lead-in that is not itself a verdict, and a **GFM table** — the table spelling of the same enumeration, recognised structurally by its delimiter row so pipe-bearing *prose* is not mistaken for one, pipes optional at either end) and each of those blocks' **lazy continuation** (CommonMark §5.1 and GFM's table rule: the paragraph line straight after a quote, a list item or a table renders *inside* it, so it is not the author's voice either — a blank line ends the block and the approval after one is theirs) are masked before the scan; a `.` inside an identifier (`[A-Za-z0-9_]` either side, the underscore included since the decoration strip deletes it) is not a unit boundary, so the `task.approved` a reviewer names in prose is not a bare `approved`; and **hard-wrapped prose is rejoined into its paragraph**, since a line break is not a sentence end and a wrap landing in front of an approval word must not manufacture a verdict — an approval word the author merely quoted, showed as data, struck out, hid or never wrote is not their verdict; the end-to-end rule deliberately still reads those contexts, where every unit must pass and a quoted defect is what makes the body actionable; the strong half would leave the verdict unreachable, since a body it recognises whole is never dispatched) and whose row is **not** a blocking `CHANGES_REQUESTED` review (that state blocks the PR whatever its body says, so its review state is carried through the intake and shown to triage in the attribution — `[dave, CHANGES_REQUESTED review] …`). Anything else PROCEEDs, so a claim that carries no approval at all — "this leaks the token" — can never be dropped as one, however confidently a verdict line says so. It is not a cheap REJECT — an approval that also asks proceeds on its ask, and the S8 eval scores the verdict on a must-proceed finding as over-suppression, then injected straight into the fix loop via the same `LoopEntry` seam — bypassing the local intake whose `already_clean` short-circuit is the panel that missed the defect. The injected round-1 coder prompt mandates a per-id `## External findings` acknowledgement (`FIXED` / `DISPUTED` / `REVERTED` / `NO CHANGE NEEDED` per injected id, every round); a `fixed` disposition requires that explicit acknowledgement **and** the loop's approval — an id the coder omits stays `unaddressed` (loop approval alone is tree-level evidence, never a per-thread claim). The verdicts describe the TREE, not the round's work (#399: `FIXED` = a fix is in the tree whichever round made it, and stays `FIXED` in every later handoff; `NO CHANGE NEEDED` = never a defect, nothing was ever changed for it; the panel's same-looking `f-00N` never belong in the section), and the epilogue reads EVERY round's acks: a decisive final ack (`FIXED` / `REVERTED` / `DISPUTED`) stands on its own (#387); a final `NO CHANGE NEEDED` over round 1's `FIXED` restated unbroken through every round between is read as round 1's `FIXED` — round 1 predates the panel, so only its section is trusted to speak of the external ids (lens #87: fixed in round 1, the id re-used for panel work in rounds 2-3, "nothing further this round" in round 4) — while any other disagreement is `unaddressed` (no thread answered; a false `Fixed in` is the one unacceptable outcome), the reading recorded per finding as `note` in the JSON (`external_outcomes[].note`). A round-1 handoff acknowledging every injected id `NO CHANGE NEEDED` with nothing committed is a claim, not the round-1 no-commit failure: the loop admits the empty round, runs the fast checks on the unchanged head, and the panel — given the injected findings as review context — judges it; `no_change_needed` likewise requires the loop's approval; the admitted round is a validation pass, not an entry to the fix loop — a claim the panel (or a red required check) rejects ends the run `not_converged` with the rationale, the claim `unaddressed`. Replies are posted for rejections, disputes, and (only for acknowledged fixes actually pushed) fixes — on the thread for an inline finding, as a conversation comment naming its target for a conversation finding. See [`docs/cli/converge.md`](cli/converge.md). With `--resolve-conflicts` (PRD S5, the CLI half) the **merge is the intake**: the base's current tip is merged `--no-commit` into a throwaway worktree at the PR head; a clean merge exits `no_conflict` (no agent, worktree removed — `merge-gate` owns that case); a binary / symlink / submodule / modify-delete / markerless conflict exits `conflict_unsupported` before any agent runs (text conflicts only — nothing could tell a coder's resolution of such a path from an untouched one); a conflict is left in progress and round 1's coder resolves the marked paths from a brief (paths, PR intent, the base's landed commits, the bounded hunks) under a pre-commit guard that proves the intended base is what gets merged (no markers; MERGE_HEAD is exactly the base tip on the PR head; afterwards the base tip is an ancestor of HEAD), so the round commit is the merge commit and the check-set + panel judge the composed tree (fork point = base tip, S5c) — every reviewer prompt carries a merge context naming the conflicted paths and both parents, since a path resolved to the base's version is absent from the fork-point diff; approval pushes the merge commit after a final base-is-ancestor proof. Exclusive with `--from-github`.
- **`--story <task id>`.** Resolves the story's develop settings — the project doc's + the task's `develop_*` (rounds, profile, panel, check-set, image, models) — through the daemon path's own layering (`daemon_io.layer_run_settings`), as the base layer under any explicit flags. The watcher-dispatched run passes it; before it, the dispatched converge ran at the CLI's 5-round default while the project said 8 (lens#78, 2026-09-07). A missing story / unreachable Lithos is a hard error (exit 2).
- **PR only.** converge pushes fixes to the PR head branch, so it requires a **PR** argument (`#142` / `142` / PR URL); a bare range / branch is rejected (use `develop review` for a read-only review of an arbitrary range). A **fork PR** is refused *pre-loop* (loom cannot push under origin credentials). Acceptance-criteria precedence and panel/profile selection are `develop review`'s, reused verbatim.
- **Budget.** `--max-cost` is a **soft, phase-boundary ceiling on the whole command**, not a hard monetary cap. The intake review's spend is carried into the loop's remaining ceiling, so converge stops *before starting further phases* once recorded spend reaches the threshold: if the intake spend alone meets it, converge stops with `failed` — **regardless of whether the intake was clean or blocking** (a clean intake does not bypass the budget). In external mode the same guard applies to the **triage** spend, but only where a paid follow-up remains: a batch with **no surviving finding** keeps its round-0 disposition (`already_clean` / `triage_rejected`, which the watcher reports and refunds) rather than reporting `failed` over a spend that has already happened with no fix loop to stop. It is **not** a guaranteed maximum: the intake is one atomic review pass that may already overshoot before it is checked; an in-flight coder/reviewer turn can cross the remaining ceiling atomically; a same-round **approval takes precedence** over a cost overrun (as in the develop loop), so an approved-and-pushed result's `total_cost_usd` can exceed `--max-cost`; and engines that don't report USD contribute `$0`. `--max-cost`/`--max-rounds` are validated (finite and `> 0` / `≥ 1`) both at the CLI and at the `converge_pr` API boundary (a `ValueError` for a bad caller config).
- **Gate timeout.** `--test-timeout` (default 900s, validated `≥ 1`) caps one gate check container — the `test` check, the other check-set checks, and autoformat. A repo whose non-integration suite exceeds the default must raise it: otherwise the `test` check times out **every round** (including at intake), the gate floor never clears even with green reviewers, and converge **stalls** rather than converging. The same flag exists on `develop review` (there a timed-out floor makes the report blocking) and mirrors the daemon's `--test-timeout`.
- **Push epilogue.** The fixed branch is pushed **only on approval**, and the guarantee is stronger than "never a non-fast-forward": push **only if the PR head is still exactly the resolved head**. An **atomic lease** (`git push --force-with-lease=<ref>:<expected_sha>`) plus a local **append-only ancestry check** enforce that, so a head **deleted**, **advanced**, or **force-rewound** between the pre-check and the push is refused (`merge_race`) — never silently recreated or overwritten — while a successful update is still a pure fast-forward (not a blind `--force`). `--no-push` converges locally and skips the push. A fork ref (absent on `origin`) is refused; auth / hook / branch-protection failures stay generic errors, not `merge_race`.
- **Outcome / exit code.** `already_clean` (intake didn't block — no coder ran, nothing pushed — or, in external mode, every injected finding refuted or `no_change_needed` with nothing committed and the loop's gate + panel approving the unchanged head (#380); reports on the PR **snapshot resolved before intake**, not a live re-check), `converged` and `triage_rejected` (external mode: no finding survived triage and at least one was refuted with evidence — the message names each disposition, since an approval beside a rejection was not refuted) exit **0** — the three statuses the JSON's `succeeded` flag reports as success; `not_converged` (the loop stopped without approval — `max_rounds` / `disputed` / `stalled` / `cost_exceeded`) and `infra_failed` (the loop died on the host — a slice-B auth / transport / spawn failure that persisted through its retries — or the **intake fetch** failed through its own 3 attempts (#431: a transport failure is retried with a short backoff, a persistent one ends the run here rather than raising); not a verdict on the change, `host_action` in the JSON, #377), `merge_race`, and `failed` (the intake was **incomplete** — interrupted / invalid / absent panel — or its spend exhausted `--max-cost`) exit **1**; a fork refusal exits **2**. `--json PATH` writes the structured summary (`status`, `succeeded`, `head_branch`, `rounds`, `fixer_commits`, `pushed`, `intake_cost_usd`, `total_cost_usd`, …). The reported `fixer_commits` counts only the coder's commits (PR head → HEAD), not the PR's original commits. `no_conflict` (resolve mode: nothing to resolve) → 0, `succeeded` false.
- **v1 limit.** If round 1's coder disputes every finding and commits nothing, the deterministic gate still runs on the unchanged head — a round that adds no commit converges only if the head was already gate-green. This is rare (the coder is told to fix, not dispute-all) and acceptable for v1.

Host-only like a develop run (`docker` + `claude`/`codex` + `gh`); not part of the hermetic `make check`.

### 4.15b `lithos-loom develop merge-gate` — trial merge + current check-set (PRD S3)

```
lithos-loom develop merge-gate <pr>
    [-p|--profile NAME] [--story TASK_ID] [--check-command NAME=CMD ...] [--check-state NAME=STATE ...]
    [--test-command CMD] [--parity-command CMD] [--generated-path PATH ...] [--regenerate-command CMD]
    [--image IMG] [--test-timeout N]
    [--no-push] [--keep-worktree] [--repo PATH] [--json PATH] [--config config.toml]
```

Answers *"will the PR's current base break if I merge this now?"* with **zero agent tokens**: in a throwaway worktree at the PR head it merges the base's **current** tip (`--no-ff` — a base move yields a real merge commit whose parents are the head and the base, never a rewrite of which commit the head is), then either reports the **conflicting paths** (the only source of that list — GitHub's API says `dirty` and nothing more; no check-set runs on a tree that does not exist) or runs the project's **current** check-set on the merge result — resolved from the story with `--story` (project doc + task `develop_*`, the same layering as `converge --story`; else `--profile`, else the host's `default_review_profile`), decided by the same **ledger-aware floor** the develop loop uses (an adapter-backed required check blocks through its findings at the configured threshold, never its exit code), and a required check that could not *execute* is `errored`, never green — nobody reviews here, and an unverified merge is never pushed (PRD S3 decision: the base is defended by today's gate, not the one the story passed a week ago; the record carries a **config fingerprint** of the resolved checks + image + test timeout + block threshold so the sweep's re-run key `(head_sha, base_sha, fingerprint)` re-gates an already-observed PR when the check-set tightens). When the gate is **green and the PR was behind**, the merge commit is pushed onto the PR branch through the same leased, ancestry-proved push `converge` uses (append-only; a branch that moved since the resolve is a `push_error` beside the green verdict, never a rewrite); `--no-push` disables it, and red / errored / no-checks / up-to-date results never push. Forks are refused from GitHub's own PR metadata **before** anything is fetched (`resolve_change(allow_fork=False)`) — a third-party head is never pulled into the operator's checkout. The worktree and its branch are removed afterwards unless `--keep-worktree`. Exit codes: `green` / `no_checks` 0, `red` / `errored` / `infra_failed` (the intake fetch failed on the host through its retries, #431: nothing merged or gated, `host_action` in the record) 1, `fork_unsupported` / `pr_closed` (merged or closed PR: not a live target) / `repo_mismatch` 2, `conflict` 3, `config_unresolved` 4 (`--story` is **strict**: where the daemon would degrade to built-ins — no project slug / doc, a read failure, a malformed gate setting — nothing is gated; S3 gates with the project's current config or not at all). The record's `verdict` is the gate's own decision (`RED` when the ledger floor blocks), not the process-exit aggregate. The record also carries a **settings fingerprint** — the resolved gate settings alone (image, timeout, threshold, the profile by **definition** — its check declarations and their catalog commands — plus a schema version, test command / gate, check tables, parity command), which `--resolve-only` reports **without** a fetch, a merge or a check (no GitHub call at all) — because the check-set fingerprint needs a worktree and the sweep has none; that is the fingerprint the sweep's re-run key actually compares. `--expect-repo owner/name` pins the run to a repository: the checkout's origin is compared **before** any fetch and a mismatch exits `repo_mismatch` (2) with a record naming both repos — the watcher passes it on every run, and `converge` takes the same flag for the remediation dispatcher. The github-watcher sweep drives this command as a subprocess on every base move and every settings change (§2.2, the watcher half of S3); on its own it is the operator's pre-merge check. See [`docs/cli/merge-gate.md`](cli/merge-gate.md).

Host-only (`docker` + `gh`); not part of the hermetic `make check`.

### 4.15c `lithos-loom develop deliver` — deliver a stopped run's branch by hand

```
lithos-loom develop deliver <run-id|task-id>
    [--branch NAME] [--story TASK_ID] [--base REF]
    [--no-gate] [--dry-run] [--json PATH]
    [--converge [--ac-file PATH] [--profile NAME]] [--config config.toml]
```

Turns a **stopped** story-develop run's branch into a delivered, monitored PR — the operator's **third choice** on a needs-human gate, beside its own pair (complete the gate → re-develop from scratch on a fresh branch; cancel the story → abandon). A run that stops without delivering (`disputed` / `needs_decision` / `stalled` / `max_rounds` / `cost_exceeded` / a coder or reviewer death) leaves a committable branch and a loom `human` gate, and every surface that could carry that work forward wants a **PR**: `converge` refuses a bare branch and the github-watcher's dispatchers key on a `pr` gate. Zero agent tokens — nothing is implemented or reviewed; the work already exists on the branch.

Five steps, each idempotent (a second invocation after a partial pass finishes the job and changes nothing else):

1. **Push, append-only.** The branch is classified against `origin`: absent → create; equal → nothing; an ancestor of the local branch → a fast-forward; **diverged → refused** (exit 1) naming both shas. Never a force — the divergence may be a collaborator's commit. The classification runs **under the delivery claim, immediately before the push**, and the push sends that exact **commit** (`<sha>:refs/heads/<branch>`), never the symbolic ref: a local process moving the branch in between can no longer have the command classify one commit and deliver another. A push that *reports* failure is verified against the remote before it is believed, in three shapes rather than two: a ref holding the pushed commit landed (the response was lost, not the update); a ref exactly where the classification left it is a proven non-landing and the refusal stands; a THIRD sha — another actor appended to the branch — has its history read, and our commit being in it means the push landed after all (step 2's head read-back then reports what the PR delivers), while anything left is `PUSH UNCERTAIN`, and the branch's upstream is set explicitly since a pinned refspec cannot carry `push -u` — that local write is best-effort **and reported**: it runs after the push, so a read-only / locked `.git/config` neither unwinds the pushed state nor passes silently, it becomes one `[Friction]` line. A push that reports failure over a remote that then **cannot be read** is `PUSH UNCERTAIN` (exit 2), never a refusal — "nothing was written" is the one claim that cannot be made there. A story a **live route dispatch still claims** is refused before any of this (`task_status` carries the claims): the run writes its terminal state at the end of its dialogue, but the daemon applies the result — and raises the needs-human gate — only afterwards, holding the route claim throughout, so a delivery inside that window gates a story whose escalation does not exist yet and leaves both gates standing. An absent claim is **not** proof the producer is gone (the runner's renew loop swallows failures, so a Lithos outage longer than the TTL expires the claim under a live run), so the refusal also requires the run's **escalation handoff** to be visible on the story AND still holding it — an OPEN needs-human gate naming the run, an open gate this delivery would retire, or a failed-attempt marker naming the run and naming no gate (the marker-only `[BlockerFailed]` shape, the only one that suppresses dispatch by itself; a marker that names a gate stops deciding the moment the operator completes it, which is exactly the ready-but-not-yet-claimed window a delivery must not run in) — unless the story already carries a delivery of its own (an idempotent re-run behind an open `pr` gate), **no daemon is running on this work dir** (the pidfile `drain` reads — one that exists but will not parse counts as running, since a booting daemon rewrites it under its lock), or the operator used the run-dir-less `--branch`/`--story` form. Those are reads, so the delivery additionally takes a **dispatch hold**: it claims every configured route on the story under an identity of its own (`<agent>-deliver`; a claim only excludes another *agent*) before the push and releases it after the gate work. A route that claimed first stops the delivery (exit 1, nothing written); one that arrives later — a daemon booting mid-delivery, past a point-in-time probe — finds the aspect held and defers, and the hold's release is the `task.released` that re-triggers its readiness check, which now defers the story behind the new `pr` gate. A run that has recorded **no outcome** at all (no terminal `state.json`, which the plugin writes only at run end) is refused too: the run may be mid-round, and `--branch` must not stand in for the branch its state never named — the run-dir-less `--branch` + `--story` form stays the operator's explicit assertion for a reaped run.
2. **Open or adopt the PR — but only this branch's own.** `gh pr list --head` matches the head **branch name** alone, so a PR opened from a *fork* with the same branch name is indistinguishable; adopting one would point the `pr` gate, merge tracking, review ingestion and the story's completion at a third party's work while retiring the story's escalation. A candidate is adopted only when it is **same-repository**, its **head is the sha just pushed**, and its **base is the base this delivery targets** (`--base`, else the repository's default — resolved *before* the decision, so an adopted PR can never merge into a branch `deliver` would not have opened onto); every check fails **closed**, since a field GitHub did not report is unknown provenance. Anything else refuses, naming what was found (exit 1 when this run pushed nothing, exit 2 when the branch is already on `origin`). Otherwise a PR is opened through the same `pr_delivery` seam story-develop uses on approval, onto `--base` or the repo's default branch, with the generated body (what / acceptance criteria / review / `Closes #N`) — whose *what* and *acceptance criteria* are **fenced, bounded and defanged** exactly like the quote below, since for a mirrored story they are an outside issue reporter's text (§5.5, PR body composition) — plus a **`## Provenance`** section naming the run, its stop **classification**, the branch and the coder's final handoff summary. The reason itself travels but **redacted and bounded** — urls (including `www.`-autolinked hosts), internal hostnames, IPv4 literals and bare `host:port` pairs, absolute / home paths and credential-shaped runs become `(url redacted)` / `(host redacted)` / `(path redacted)` / `(redacted)` — prose, not `<url>`, since GitHub's sanitizer drops unknown tags and an invisible redaction cannot be told from a truncation — and the text is capped, because it is uncurated agent/infra text and a PR body is world-readable; the operator reads the untouched original on the story's `[NeedsHuman]`, in the gate brief, or in `--dry-run`. The coder's final handoff goes through the SAME redaction and travels as a **fenced block** with closing keywords (`#12`, `GH-12`, `owner/repo#12`) and `@`-mentions rewritten (never by a code span, whose backticks the text's author controls; bidi and zero-width formatters are stripped with the control bytes) (it is agent-written into a read-write mount, and a PR description is live markup), and the reader that produces it refuses symlinks and non-regular files (`O_NOFOLLOW` + `fstat`), so a planted link cannot choose what a host-privileged process reads and a planted FIFO cannot hang the command. Provenance the run never recorded renders `unknown`, never `0` / `$0.00`. A `gh pr create` that *reports* failure is re-asked before it is believed, since the call can commit and lose its response and an open PR reported as never opened would stay ungated for ever: first under that same adoption rule, then — the branch can move between the create and the re-ask, leaving our own new PR reporting somebody else's sha — under the widest match still provably about this delivery, a same-repository open PR on this branch onto this base (the fork class stays excluded, and the head read-back reports the delivery partial and withdraws any approval claim, so nothing rests on the recovered head); a re-ask that cannot be MADE (create failed, list failed) is reported as `PR UNCERTAIN` and exits 2, never as an absence this run did not establish — no line in that state says `NO PR`, and the headline never claims `PUSHED` over an invocation that pushed nothing. Every `gh` call is **pinned** to `--repo <owner/name>` resolved from the checkout's `origin` (the remote step 1 pushed to) — gh's own inference resolves a fork checkout to its *parent*. After the PR exists its **head is read back** from GitHub and every later claim about the delivered revision is made against that, not against the sha the push sent: `gh pr create` opens from a head BRANCH (the API takes no sha), so an actor advancing `origin/<branch>` between the push and the create puts their commit behind a PR whose body describes ours, and adoption has the same check-then-act shape around its list. The window cannot be closed, so it is observed — a head that is not the pushed sha is a `[Friction]` naming both shas, exits 2, and withdraws the approval claim in the story's audit copy; a head that could not be read is UNVERIFIED — reported, partial, the approval left unbound rather than re-bound to the pushed sha, and the delivery left unmarked so the run that does read the head posts the record. `[story_develop] operator_github_login` is notified exactly as on a daemon delivery.
3. **Raise the `pr` gate** and record it on the story — `pr_gate_id` plus, on the same write, a per-key delete of the stop's failed-attempt marker and its `needs_human_gate_id`. Literally the daemon's own delivering-exit write (`record_delivery_on_story`, shared by both), so a hand-delivered story is indistinguishable from a daemon-delivered one to every later sweep; it is made whenever the **live** story does not already say it, so a first pass that created the gate but lost the write is *repaired* by the next run rather than skipped. A story already carrying an open `pr` gate **for this PR** adopts it rather than stacking a second blocker; one carrying a gate for a *different* PR — **even beside a matching one** — refuses (exit 2, every gate and the human gate left as they are) rather than letting the story's merge semantics stay hostage to a PR that does not contain this branch. The decision is taken on a **fresh** read (the initial one predates the push), which is authoritative about the story too — one that went **terminal** meanwhile gets no gate and no gate completion (#372) — under a `deliver` **claim** on the story whose TTL exceeds the command's whole external budget and which is **renewed immediately before the gate work**; a renewal that does not land means exclusivity cannot be proved, so the gate work is skipped entirely and the claim is not released.
4. **Complete the stop's loom `human` gate(s)** — read from the story's incoming `waits_on_gate` **edges**, never from `needs_human_gate_id` (provenance only) — **after** step 3, so the story is never momentarily on the ready frontier: behind a `pr` gate it is absent from `lithos_task_ready`, so the runner's readiness check defers it and the completion cannot trigger a duplicate run. When no `pr` gate could be raised the human gate is deliberately **left open**: it is then the only thing between the story and a re-dispatch. **Which gates** takes two keys, both required: the gate's `route` is one this host CONFIGURES (an allowlist over `[[routes]]` — a denylist of the subsystem routes loom ships today would admit the next one added, and completing an `external-remediation` gate is the operator's **consent** to re-arm the S5b budget, i.e. autonomous `converge --from-github` spending money and pushing to the delivered PR), and the gate NAMES the run being delivered (`metadata.run_id`) — a story may match two dispatch routes, each with its own stopped run and its own open decision. With no candidate naming any run, a single candidate is unambiguous and is retired; two are not, and neither goes (the run-dir-less `--branch`/`--story` form takes that same rule). Everything else is left **open**, printed, and named in the finding with why — safe in every case, since the `pr` gate holds the story either way. A retired gate authorises clearing its OWN route's failed-attempt marker only, and `needs_human_gate_id` survives while it points at a gate that was kept. If a dispatch claims the story mid-delivery, the `pr` gate is still raised but NO human gate is completed (its escalation may still be on its way).
5. **Post `[ManualDelivery]`** on the story (§8) — the run, the PR (opened or adopted), the delivered sha (always, whether or not this run pushed it), **why the run stopped** (whole and unredacted, control bytes out: the PR body publishes only a bounded, redacted rendering and tells its reader the story carries the rest, and the crash this command salvages is exactly the case where the daemon died before posting any other record of it), the gate that now holds the story, the gates retired, and the gates deliberately kept open (with their routes); degradations ride along as `[Friction]` text in the same finding, each named once. The record says what was DONE: a gate phase that failed reads "the pr gate was NOT raised", never the deliberate `--no-gate` hand-off's sentence. One rule: post unless the story's `metadata.manual_delivery` marker already records a **complete** delivery of this `(run, PR)` in at least this state — the marker's `gated` **and** `swapped` fields are floors on the state the delivery left behind (`swapped` = no open `human` gate that could be this run's escalation remains — measured against the story's gates, never against this invocation's authority to retire them, which moves with the host's route config), so a run that gates a PR delivered `--no-gate`, or that completes the human gate an earlier pass could not, posts the correction while a pass that achieves less stays silent. Achieved gating counts a `pr` gate the STORY already carries for this PR, not only one this invocation raised — a `--no-gate` pass over an already-gated PR names the gate that holds it and never records it as UNMONITORED — and `swapped` is what keeps the gate-swap provenance from being lost across such a pass. The marker is written *after* the post (finding-then-mark) and only for a delivery that finished — so a repair pass never duplicates a record the story already carries, a partial pass stays re-postable until the run that completes it records the truth, and a post that failed or a process that died re-posts next run. On the story rather than the gate so `--no-gate` gets the same guarantee and a gate the merge sweep completes cannot take the record with it; a crash between post and marker costs at most one duplicate, the same at-least-once trade every `post_finding_then_mark` caller makes.

From there the PR is a first-class PR-maintenance object (§2.2): landability, external-review ingestion + remediation, the base-move re-gate, the conflict resolver, merge → story completed + dependents nudged, and it counts against the project's S6 admission cap.

**The repo, not the worktree.** `state.json` names the branch; the branch ref lives in the project's checkout whether or not the run's worktree survived. The run dir is used only to *find* the branch and the story (plus the run's provenance: rounds from `state.json`, cost + test-gate verdict from its `result.json` `escalation.brief`; for the **approved** salvage — a delivery that failed (#194) or outlived its budget (#189) — the PR records the panel's approval as an approval, and its stop reason is that delivery failure, which `state.json`'s `failure_reason` never carries — but that approval is published only for the **revision and story it was given on**: the run's recorded head (the tail of `result.json`'s run-bound `commits`) must equal the sha being delivered and the story must be the run's own, since a branch is a mutable ref and `--story` replaces the acceptance criteria the PR publishes. Either check unmet — including a run that recorded no head at all — downgrades the line to "approved, but NOT confirmed for this revision", naming which half could not be checked, rather than publishing a review of code the panel never saw); every write is `git -C <repo>` + `gh` + Lithos, against `metadata.project` → `[projects.<slug>].repo`. `--branch NAME --story TASK_ID` needs no run dir at all — the fallback for a host with `retain_failed_workdirs = false`.

`--converge` chains a re-review into the delivery. It runs **between step 2 and step 3** — after the PR exists, before the `pr` gate. That order is the whole coordination story: the watcher's dispatchers (merge-gate, conflict resolver, external-review remediation) act only on OPEN `pr` gates and the route-runner only on a story on the ready frontier, where the needs-human gate keeps this one from being, so while the chained run works nothing can see the PR and nothing can race its coder or its push — no lease, no second protocol, the PR is simply not yet observable; the delivery's own claims are held across it — taken for the longest a claim can live (Lithos's 8-hour cap, `DELIVER_CHAIN_CLAIM_TTL_MINUTES`) rather than the plain delivery's 60 minutes, since a multi-round chain outlives the short lease and Lithos will not renew a lease that has already expired — and the gate phase still re-proves its lease before writing, so a chain that somehow outlived even that only makes the gate work a re-runnable partial. A story already behind an open `pr` gate is **refused** the chain before anything is written (its PR is delivered and monitored, and a chained run there could overlap the watcher's own) — the standalone `develop converge <pr> --story <id>` is the tool for a PR that is already watched. A converge that ends `not_converged` (or crashes) leaves the `pr` gate exactly where step 3 puts it and its exit code becomes the command's; a delivery that is already unfinished when converge's turn comes (an unverified or moved PR head) skips it and exits 2, and a gate failure AFTER converge ran is still the partial exit 2 with converge's outcome on the record (`converge: exit N` / `CRASHED`). The chain: `develop converge <pr> --story <id>` on the PR just delivered, in the same process and through converge's own parser (so every `develop_*` layer, panel and check-set behind `--story` is the one an operator typing the command would get), with the acceptance criteria read from the **live story's current description** (title + body) — the text the operator edits when a dispute sends them to the story. Deliberately not `metadata.acceptance_criteria` (a story can carry an older value there while its description has been rewritten, and preferring it re-reviews against the stale copy) and never the PR body's copy, which was written from the same story a moment ago. The criteria are resolved **once, before the push**, into one snapshot: the text **printed** — bounded, stripped and quoted — beside the `converging #N under …` line and in the `--dry-run` plan is the text handed to converge as `--ac`. An `--ac-file` is read at that same boundary, whole and strict UTF-8 exactly as converge would read it, and its *contents* travel rather than its path — a path is read twice, and an edit between the two reads would leave the operator approving one text while the panel judges another, while a lenient preview would pass an invalid byte that converge's strict read then rejects with the PR already pushed and gated. So everything converge would refuse refuses here instead: missing, a directory, unreadable, not UTF-8, or empty / whitespace-only. The run is **pinned** like every other loom-initiated converge dispatch: `--expect-repo` (the `owner/name` resolved from the checkout's `origin`) and `--expect-head` (the head step 2b verified behind the PR), so a branch moved under the delivery makes converge a no-op rather than a paid round pushing onto an unverified revision. `--ac-file PATH` overrides it (the path is passed on, so converge reads the file itself) and `--profile NAME` picks the review profile; both are **refused without `--converge`**, since this command reviews nothing and a silently-ignored acceptance file reads as one that was honoured. converge's exit code and summary become the command's, so a `not_converged` run exits non-zero — with the `pr` gate exactly where step 3 put it, because the PR is delivered either way and the operator's next move is the one after any non-converged remediation. Refused with `--no-gate` (converge pushes review fixes, and an UNMONITORED PR is the standalone command's business); previewed under `--dry-run` as a sixth plan line (`6 converge: would converge #N under <AC source>`, naming the PR only when the plan already knows its number — an adoption — since a PR this run would open has none yet); and **skipped** after a partial delivery (exit 2), which is said in the output rather than hidden behind converge's own exit code.

The delivered PR url is also recorded in the run's private `delivery.json` (best-effort, beside the daemon's own delivery markers) the moment the PR exists — the fast, offline path for `develop list` (§4.14) — and a **completion bit** only once every step landed, which is what `develop prune` keys on (a partial delivery's exit-2 text says to re-run the command on this run dir, so the dir must outlive the partial). The story's **`pr` gate** remains the authoritative record, and those commands fall back to it for any run the work dir cannot answer for.

`--no-gate` opens the PR alone: no `pr` gate, the human gate left open, and the PR **UNMONITORED** (nothing tracks its merge, ingests reviews, or re-gates it) — said so in the finding. `--dry-run` prints the five steps with every fact **resolved** and writes nothing. Resolved means *asked*: the remote state from git, and — through the same `pr_plan` reads step 2 itself makes — the repository's default base and the concrete step-2 decision (`adopt #N` / `open a new PR onto <base>` / the `REFUSE` an unadoptable same-name PR produces), beside the would-be title and the gates it would complete or keep. Naming the base as "the repo's default branch" and step 2 as "adopt or open" would have the operator approve a guess in place of the decision. The preview asks BEFORE step 1 and the real step 2 asks after it, so the push is projected into the decision: an open PR for a branch this delivery will fast-forward is at `origin`'s current sha now and at the delivered one then, and the plan reads it as the adoption it will be rather than refusing a PR that cannot refuse. The two `gh` calls are reads; nothing is pushed, created or written to Lithos, and a push the plan refuses stops there (step 2 reads nothing — the real invocation never reaches it). When a new PR would be opened the plan also prints the coder's handoff quote **as it would be published**: that quote is the one part of the body loom did not author, and its redaction is a shape filter rather than a confidentiality boundary, so this read is the control. Every line loom did not author (the stop reason, the story title, the quote, a `gh` refusal) is stripped of terminal control bytes, bounded, and printed with each continuation line indented behind a `|` marker — stripping escapes leaves LF, and a newline at column 0 is a forged plan line while volume scrolls the plan away; the story line takes the title's first line only, as the PR title does. The `error:` line of a refusal, which carries `git` / `gh` stderr, is stripped the same way, as are the `[Friction]` notes of the end-of-run report. Exit codes: `0` delivered (or adopted with nothing left to do, or a dry-run plan); `1` **refused, and this run wrote nothing** (diverged remote, unknown run, branch absent from the checkout, a run that already delivered, a story a live route dispatch still claims, a stopped run whose escalation has not appeared while a daemon runs on this work dir, a run that has recorded **no outcome** — no terminal `state.json`, so it may be mid-round; `--branch` does not stand in for it, an **approved** run whose automated delivery is neither complete nor recorded-failed — the daemon may still be opening its PR, a story that is not open without `--no-gate`, an unmapped project, a non-GitHub `origin`, another `deliver` holding the claim, an unreachable Lithos — or a `gh` failure / unadoptable PR while the branch was already on `origin`); `2` **partial** — something is committed and something is owed: a push with no PR, an external write whose outcome could not be read (`PUSH UNCERTAIN` / `PR UNCERTAIN`), a gate half that did not complete, or a `--json` record that could not be written. The classification follows what has been **committed**, not which step raised, so once anything is outside the host the command never reports "nothing written". Host-only (`gh` + a project checkout); not part of the hermetic `make check`. See [`docs/cli/deliver.md`](cli/deliver.md).

### 4.16 `lithos-loom eval review` — review-correctness eval harness (#183)

```
lithos-loom eval review [--case ID] [-k N] [--bar FLOAT] [--cases-dir PATH] [--report-dir PATH]
                        [--profile NAME] [--reviewer NAME]... [--reviewer-override PERSONA.FIELD=VALUE]...
```

A **seeded-defect benchmark** that measures how reliably the reviewer panel catches real defects — review correctness as a *number*, not a vibe. Each **case** (a directory under `evals/review/cases/<id>/` with a `case.toml` + `ac.md`) pairs a known-buggy `base..head`, the acceptance criteria the reviewer receives, and the expected finding(s) a correct review must surface. The harness runs review-only mode (§4.15) against the case's head **K times** (default 5) and reports, over the K runs: **catch-rate** (every expected defect surfaced), **severity-correctness** (caught at/above the expected band), and **false-positive rate** (on the paired known-good head). Catch and FP are each shown as a count over K plus a **Wilson 95% confidence interval** (#182), so a rate is read with its sampling error — a low-K run cannot prove a clean panel (`5/5` still spans ~`57-100%`). A sample whose reviewer turn **crashed** (no verdict — `status` `invalid` / `not-run`, e.g. a provider usage limit) is **errored**: excluded from the catch / FP denominators and reported as `+Nerr`, so agent flakiness never masquerades as a review miss (a genuine catch is still counted even if a panel peer crashed). Beside the defect-specific FP rate each paired case reports its **noise** (#310): the `noise` column reads `NOISY/VALID blkN` — known-good runs that reported *anything at all* (same valid denominator as `fp`, so `fp 0/3` beside `noise 3/3 blk3` describes the same three runs) and how many of them **held approval** (the report's own `blocking` rule: any reviewer below its threshold, an incomplete panel, or a blocking floor). The FP rate alone asks only whether a known-good run reported *the case's expected defect*, so a panel filing four unrelated findings on a clean head and blocking every time still scores `0/3` — which flatters exactly the changes most likely to be harmful (anything raising catch-rate by lowering the bar for what counts as a defect); three candidate arms of the RH-1 artifact prompt scored an identical `fp 0/3` while ranging from silent to blocking every run. `summary.json` carries `noise_rate` + CI, `known_good_findings_per_sample`, `known_good_blocked_per_sample`, `known_good_blocked`, and the same per-sample counts + block flags for the **buggy** arm — recorded but deliberately **not** rated, since an extra finding on a defective head may be a real second defect. Errored samples are excluded from the noise denominator like every other rate (an incomplete panel reports nothing and blocks by definition). `--max-known-good-block-rate RATE` turns the block count into a gate (exit 1, like a floor regression), **off by default** because no baseline for these numbers exists yet; cases with no known-good arm are never convicted by it. The numbers are pure counting off the retained report JSON, so an existing `--report-dir` can be re-derived offline with no judge and no tokens. A case **passes** at `catch-rate ≥ --bar` (default 0.8) over the *valid* samples — agents are stochastic, so it's a rate, not a single pass/fail; a case with zero valid samples cannot pass. Matching defaults to a **mechanism LLM-judge** (`--judge`, on by default): it confirms each finding describes the case's *specific* defect mechanism — vetoing a same-topic false hit and rescuing a keyword-less correct catch — because a purely structured match (file + ≥1 keyword) over-counts when the known-good shares the defect's topic (the first live run measured 100% FP that way); `--no-judge` falls back to the cheap structured matcher. The judge is a **measurement instrument, so it fails loudly** (#307): its answer carries a status — a genuine **veto** (`ok`), a reply whose `MATCHED:` line could not be read (`unparsed`), or a call that produced none at all (`failed` — a timeout, a missing CLI, retried once first). Only a veto is data; the other two are an **absence** of a verdict, so those samples are excluded from every denominator exactly like a crashed reviewer and reported separately as `+Njerr` plus a stderr line — a judge timeout used to score as a review miss and silently depress catch-rate. There is deliberately **no whole-reply fallback** when the verdict line is missing: the prompt asks the model to reason before concluding, so scanning that prose for finding ids scored "f-001 does NOT describe this" as a match, and `MATCHED: none of f-001, f-002` matched both ids — each manufacturing a catch out of a rejection. A turn that did not **complete** (non-zero exit, claude `is_error`, a codex `turn.failed` or missing `turn.completed`) is `failed` and its text is never parsed — it may be partial or stale, and the codex stream retains the last agent message even when a later event fails the turn, so a crash could otherwise manufacture a verdict. Only the narrower case of a turn that completed but minted **no resumable session handle** is recorded as an *anomaly* and still scored: both engines fold that handle into `TurnResult.succeeded` so a later resume turn can re-attach — irrelevant to a one-shot judge Q&A, and gating the scorer on it would mean a CLI that stopped echoing a handle turned every case into zero valid samples. `TurnResult` therefore carries `completed` (the turn's own outcome) alongside `succeeded` (`completed` **and** resumable). Because the structured matcher is pure over the stored findings, **both** answers are computed on every run at no extra cost: the catch cell gains a trailing `struct N/M` **only when the two disagree** (silent at zero, like `+Nerr`), and `summary.json` always carries `structured_caught_per_sample`, `judge_status_per_sample` and `judge_errored` — so a judge/structured divergence shows up in the headline instead of being findable only by re-scoring a report dir by hand. Disagreement is judged **per sample**, not on the totals: a judge catching sample 0 and missing 1 while the structured matcher does the reverse both tally `1/2`, and comparing totals alone would hide a case where every sample disagreed. `summary.json`'s `n_valid` and `known_good_blocked` use the same combined reviewer-or-judge exclusion the rates and the gate do (with `false_positive_n_valid` recorded explicitly), so a retained report can never contradict its own numbers. `--report-dir DIR` retains every run's report at `DIR/<case>/<variant>-<i>.json` plus a per-case `DIR/<case>/summary.json` (rates, per-sample booleans, CIs, tier) so a costly K-sample run is re-analysable for variance without re-scoring. With the judge on it also writes the **verdict audit trail** at `DIR/<case>/judge/<variant>-<i>.json` — per expected: the mechanism asked about, the matched ids, the status, and the judge's raw reply — so a veto is explicable after the fact rather than invisible (#307). It is a *subdirectory* on purpose: `<variant>-<i>.json` is the stable `ReviewReport` contract that offline re-scoring globs, and a sibling `buggy-0.judge.json` would match `buggy-*.json`. Under `--no-judge` no `judge/` directory is written at all, so its absence is meaningful. Cases score in two **tiers** (RH-6; `tier = "floor" | "frontier"` in `case.toml`, loader-validated): the headline is a **pooled catch-rate over frontier (discriminating) cases** with a Wilson CI, beside a **class-balanced** frontier line (#404: per declared blind-spot `class`, the per-sample catch pooled across the cases that declare it — within one case a class is caught in a sample when every expected of that class is — with its own Wilson CI, and the mean over classes as a point summary with no interval, so a class that recurred across PRs counts once; unclassed expecteds are excluded and counted; a class with no valid sample is named and left out; the `class` vocabulary is `BLIND_SPOT_CLASSES` in `case.py`, mirrored in the README's taxonomy, loader-validated, and not part of the scoring fingerprint), while **floor** (saturated) cases are a regression gate whose rows read `ok`/`REGRESSED`. A **multi-expected** case is a conjunction the case row presents as one number, so it gets one indented row per `[[expected]]` (`└ [i] <class> caught/valid CI`, the same valid-sample denominator) and `summary.json` carries `caught_per_expected` / `catch_rate_per_expected` / `catch_rate_ci_per_expected` / `expected_classes` — the diagnosis beside the verdict, derived from what the judge already returns per expected. The command **exits 1 iff a floor case falls below the bar, a case has zero valid samples (reviewer *or* judge infra failure), or — when `--max-known-good-block-rate` is given — a case blocks its known-good head above that rate or produced no valid known-good sample to judge it by** (the arm runs *after* the buggy one, so an exhausted quota is exactly when an explicitly requested clean-head gate must not read "no evidence" as "no violation"; without the flag an unmeasurable known-good arm stays a reporting gap, as before). Both rate options (`--bar`, `--max-known-good-block-rate`) are rejected pre-paid unless they are finite and within `[0, 1]` — an out-of-range rate does not error on its own, it silently redefines the run (`--max-known-good-block-rate 10`, a typo for `0.10`, disables the very gate it requests) — a frontier FAIL is the measurement, not a failure of the run. The **panel-override axis** (RH-7) varies the panel per run without editing cases: `--profile NAME` replaces the panel with the profile's personas *and* sets its check-set (gate-only profiles rejected unless `--reviewer` supplies the panel); repeatable `--reviewer NAME` explicitly enumerates the panel (add/remove; wins over `--profile`'s panel); repeatable `--reviewer-override PERSONA.FIELD=VALUE` (`FIELD` ∈ `model`|`effort`|`tool`) adjusts personas where present in the effective panel (names validated against the registry). All overrides fail closed before any paid run, and each case's `summary.json` records the effective profile + panel so report dirs are comparable arm-to-arm. The **explicit-model policy** (#304, §5.5) applies here too: after override resolution, `[story_develop.default_models]` fills each panel member's model and a reviewer still on `model=None` aborts the whole invocation pre-paid — so `summary.json` records the actual model of every reviewer, never a silent image-CLI builtin (#303); the resolved panel (not the case's bare personas) always drives the run, and the per-case stderr line prints it. The **judge** is covered too: with `--judge` on (the default), the judge's model resolves from `default_models[judge-tool]` — absent means the invocation is rejected pre-paid (or run `--no-judge`) — and `summary.json` records `judge: {tool, model}` (`null` when disabled), since the judge's verdicts decide what counts as a catch. An **artifact case** (RH-3 / #294; `artifacts_dir` + `artifact_provenance = "captured" | "synthetic"` in `case.toml`, both-or-neither; the root must be a real non-symlink directory **inside the case dir** — absolute/`..`/symlinked roots rejected at load *and* at seed time via one shared check, since an escaping root would expose arbitrary host files to the reviewer container — with ≥1 non-empty regular file, no symlinks anywhere, and a gate-enforced 2 MB per-case byte budget) measures the **approval-hold artifact-review pass** instead of the diff panel: the harness seeds the case's checked-in rendered-page captures into the run's artifacts dir and runs review-only in artifact-only mode — no check-set, one `reviewer_artifacts.md` round — so a catch is attributable to the artifact surface (findings carry no pass provenance, hence one surface per case; pair with a diff-form twin to A/B the two). Measuring **false positives** on that surface needs **paired captures** (RH-1): a `[known_good]` head must declare its own `artifacts_dir` under `[known_good]` (validated identically, and sharing the case's one `artifact_provenance` — same pages, same recipe, two heads), and the seeder picks the variant matching the head under review. Declaring only one half fails closed at load: without the pairing the fixed code would be reviewed against the buggy captures, so the FP rate would measure the captures rather than the review — which is why #302 rejected `[known_good]` on artifact cases outright. The **pairing invariants** are enforced for the same reason: the two heads may not be the same sha or the same patch file (and, once materialised, may not resolve to the same commit or the same **tree** — two different patches can build byte-identical code), and the two capture roots must be distinct, non-nested, hold the same relative paths, and differ in at least one capture's bytes. An artifact case with no `[known_good]` stays catch-only. Scoring is unchanged; `summary.json` additionally records `artifacts: {n_files, provenance}` plus `known_good_n_files` when the case is paired. Unknown `case.toml` keys are rejected at load (a typo'd `artifacts_dir` would silently measure the wrong surface). Seeded with the **#180/#171** case; every future escape becomes a regression case. **On-demand only — never part of `make check`** (it spends real tokens and needs the host sandbox + agent CLIs); the harness *logic* is unit-tested hermetically with the review function stubbed. See [ADR 0005](adr/0005-review-correctness-eval-harness.md) and [`evals/review/README.md`](../evals/review/README.md).

### 4.17 `lithos-loom eval rescore`

Score an already-retained `--report-dir` **again, offline** (#307). No reviewer ever runs: scoring is a pure function of `(case.expected, stored report JSON, judge)` — no git, no worktree, no container — so a costly K-sample sweep can be scored again for **judge calls alone** (69 for the whole pinned baseline, against hours of container reviewer runs). That is what makes judge variance measurable at all, and what turns a judge-prompt change from "invalidates a paid baseline" into "costs a few dollars to re-score". `lithos-loom eval rescore REPORT_DIR [--case ID] [--cases-dir PATH] [--bar RATE] [--judge/--no-judge] [--judge-tool claude|codex] [--judge-repeats N] [--out FILE] [--allow-changed-cases] [--dry-run]`.

**`--judge-repeats N`** is the measurement the command exists for: the judge is asked each question N times over *identical stored findings*, and the table gains `flip` and `spread`. Both appear only above one repeat; a single verdict cannot flip. **Repeat 0 stays authoritative**: this command measures variance, it does not silently re-estimate while measuring — majority-of-N is #307's suggestion 3, conditional on what this reports.

A judge **error is never a verdict**, and the stability columns are built on that. A timeout and a veto both match nothing, so a site counts as **stable** only when every repeat actually answered *and* they agreed; a site where two repeats answered differently is **flipped** (counted even if another repeat errored — a disagreement seen is a fact about the judge); anything else judged is **unmeasured** and reported outside the ratio, never inside it. So `flip` reads `FLIPPED/MEASURED` with a `+Njerr` suffix, and an all-errored measurement reads `UNMEASURED`, not `100% stable`. The suffix counts **every** site that hit a judge error, not only the unmeasurable ones: a site that both flipped and errored stays in the denominator (the flip is real), so keying the count on exclusion would hide its failed repeat from every aggregate. The roll-up line prints both — `N site(s) hit a judge error (M unmeasurable)` — and the payload records `errored_sites` beside `unmeasured_sites`. Sites where the run produced no findings are excluded throughout — the judge never saw them, and counting free unanimity as stability would flatter a quiet arm. `spread` reads `MIN-MAX/VALID` over **each universe's own valid denominator**: a repeat where the judge errored has fewer scorable samples, and holding K fixed would render that as a drop in catches rather than as missing data.

The results table is the **same renderer** `eval review` uses, so a re-score column-diffs against the run that produced it, and `rescore.json` reuses `summary.json`'s field names so drift compares field-for-field. It defaults to `<report-dir>/rescore.json` — at the dir root, one payload for the whole invocation — and is written atomically (temp + `os.replace`, the temp name randomised so two concurrent invocations cannot share one scratch file and strand the loser after it has paid). `--out` redirects it, but is rejected up front if it names a retained report or `summary.json` (overwriting a paid input with a re-score of it), a directory, a path whose parent does not exist, or any name but `rescore.json` **inside a case dir** — the loader accepts exactly `summary.json`, `rescore.json` and `<variant>-<i>.json` there, so a stray file would let a *successful* run leave the dir unloadable by the next one. Per case the payload carries the `judged` and `structured` results, the effective `bar` with its `bar_source`, the per-site verdicts, and the drift block. **Sites are recorded even at one repeat**, each verdict with its `status`, matched ids, `detail` and raw `reply` — the ids alone cannot say why two identical asks differed, and without the status a timeout is indistinguishable from a veto on disk.

**Drift** compares the per-sample arrays against what the run recorded, including both judge-status arms and both error arms: an original veto and a re-score timeout both leave `caught` false, so verdicts alone would call a case unchanged while its valid denominator dropped to zero. Sample *counts* are compared too — a dir that gained or lost a trailing sample is a different corpus. A key the recorded summary never had reports `null`, since most retained dirs predate most fields and "absent" must not read as "agreed"; under `--no-judge` the judge-status arms report `null` for the same reason, and the heading says the whole delta is judge-vs-structured, not drift.

**Scoring bar**: `--bar` is optional and defaults to **the bar the run recorded**. Re-scoring at the module default a run scored at `--bar 0.6` would report `REGRESSED` for a case whose numbers never moved — the re-score would be measuring its own flag. A run with no recorded bar (every dir written before #307) falls back to the default with a loud note; passing `--bar` overrides and says which runs it overrode.

Everything fails closed **before the first judge call**: the rate options (§4.16's rule), `--judge-repeats 0`, `--judge-repeats N` with `--no-judge` (a lever that cannot fire), a missing/empty report dir, malformed or non-`ReviewReport` JSON, a non-contiguous sample index (the recorded per-sample tuples are positional, so a gap would misalign the drift comparison), an unexpected filename, an `--out` collision, every case absent from the tree reported at once, and the #304 explicit-model policy on the judge. Retained reports are **structurally validated** at load — every field the scorer reads (`reviewers`, each reviewer's `status`, the report's `blocking`, each `findings` entry and its `rationale` / `files` / `finding_id` / `severity`) and every summary field a drift comparison consumes, **element types included** (`[1] == [True]` in Python, so an int array would compare equal to a boolean one and report no drift where the corpus differs) — because the whole corpus is loaded before the first case is judged, so a malformed report in the last case must not surface after the first has been paid for. `status` and `blocking` are checked for the two distinct ways they break. `status` decides whether a sample counts as a review at all, and `review_incomplete` keys on the *presence* of an error status — so a missing or misspelled one (`"invald"`) reads as a clean review and inflates the valid denominator, while an unhashable one raises inside a frozenset membership test. It is therefore **required** and must be one of `REVIEWER_STATUSES` (`LGTM` / `FINDINGS` / `invalid` / `not-run`, the on-disk contract's own list); every one of the 407 reviewers across the retained corpus carries a canonical status, so nothing real is refused. `blocking` never raises — `bool("false")` is `True`, silently inverting the noise instrumentation — and stays optional, since reports predating #310 carry no such key. The **verdict-request count** is printed first (exact as a count of questions asked, since the reports are already parsed and the judge short-circuits a findings-less sample without an agent call) alongside its **retry ceiling**: a failed call retries once, so N requests can cost up to 2N agent invocations, and printing only the first number would understate a flaky sweep by 2×. `--dry-run` stops there. Each case is then **named on stderr before it is judged** — `[5/12] 289-symlink-artifacts — 50 request(s), 120/345 done` — from the same exact counter the preflight total uses, so the two can never disagree. Without it a long sweep is silent between the preflight and the final table, and a working run is indistinguishable from a hung one (on the first live 345-request run the only way to tell was inspecting the judge subprocess). Suppressed under `--no-judge`, which returns in under a second. **Case identity**: `summary.json` records an `expected_fingerprint` — a hash of exactly what the *scorer* consumes: the case id and its `[[expected]]` blocks (the id is in, so a case renamed in place reads as changed rather than silently comparing across identities; `ac.md`, personas and profile are out, since those change what the *reviewer* saw, which a re-score never revisits — that is [#309](https://github.com/agent-lore/lithos-loom/issues/309)'s question) — plus the run's `bar`. A **mismatch aborts** unless `--allow-changed-cases`; an **absent** fingerprint warns loudly and proceeds, because every dir written before the field exists lands there and refusing them would make the whole retained corpus unrescorable. **A measurement never sets the exit code** — a re-scored floor case reading `REGRESSED` is a finding about the judge, and a gate that runs no reviewers would gate on the judge's mood; exit 2 is usage failure only.

### 4.18 `lithos-loom eval triage` — the S5a triage step on known verdicts (PRD S8)

```
lithos-loom eval triage [--case ID] [-k N] [--bar RATE] [--max-over-suppression RATE] [--tool claude|codex] [--model ID] [--effort E] [--timeout SECONDS] [--cases-dir PATH] [--report-dir PATH]
```

On-demand, host-only (docker + the agent CLI), not part of `make check`. Each case under `evals/triage/cases/` is one tree (a sha, or `base` + `head_patch` applied at run time) plus a batch of findings, each declared `proceed` (known-true, or `ambiguous = true`), `reject` (known-false, with the `refutation` — files and line ranges — a correct rejection must cite) or `nothing` (no claim at all — a pure approval, which a correct triage answers `NOTHING_TO_REMEDIATE`). The batch reaches the step through the production intake (`external_intake_reviews`: ledger ids, `[author]` prefix, one anchor, severity `minor`). Each sample is **one read-only triage turn over the whole batch** under converge's reviewer timeout (`--timeout`, default 3600) — the production shape of `converge --from-github`'s S5a step — scored on three rates: **reject** (known-false rejected with a citation into their declared refutation — file, and line range when given — over every known-false opportunity; `--bar`, default 0.8), **approval** (`nothing` findings answered `NOTHING_TO_REMEDIATE` rather than costing a paid round, at the same bar) and **over-supp** (must-proceed findings suppressed by EITHER verdict, over every such opportunity; `--max-over-suppression`, default 0 — one wrongly suppressed true finding fails the case). A degraded turn (failed, or no verdict file) is the step's default-to-act, not a verdict: the sample is *errored* and excluded from both denominators. The triage agent's model is required explicitly (#304: `--model`, else the loom config's `[story_develop.default_models]` entry for `--tool`). Prints a per-case table (Wilson 95% CIs over clustered opportunities — a lower bound on the uncertainty) and a pooled line; `--report-dir` retains `<case>/sample-<i>.json` (the raw verdict file, per-finding line classes and correctness) and `<case>/summary.json` (rates, `samples_with_suppression`, an `expected_fingerprint` of what the scorer consumed). Exit 1 only when a case has no valid sample; a FAIL is the measurement. Shipped fixtures are preflighted hermetically where the checkout is present (`tests/test_eval_triage_shipped.py`: the tree builds, every anchor and refutation path is tracked at it, every range lies inside its file; skipped with a reason otherwise). See `evals/triage/README.md`.

### 4.19 `lithos-loom eval resolve` — the S5 conflict-resolution path on real merges (PRD S8)

```
lithos-loom eval resolve [--case ID] [-k N] [--bar RATE] [--tool claude|codex] [--model ID] [--effort E] [--max-rounds N] [--coder-timeout S] [--reviewer-timeout S] [--probe-timeout S] [--profile P] [--reviewer NAME]... [--reviewer-override PERSONA.FIELD=VALUE]... [--cases-dir PATH] [--report-dir PATH]
```

On-demand, host-only (docker, the agent CLIs, and the target project's toolchain), not part of `make check`. Each case under `evals/resolve/cases/` is a **real conflicting merge** — the PR's `merge_base`, its head (a sha, or `merge_base` + `head_patch`), and the `base` branch tip that landed meanwhile — plus an **executable oracle**: `[[probe]]` commands (an argv, no shell; `{case_dir}` / `{worktree}` rendered shell-quoted) run with cwd = a detached worktree at the tree under test, exit 0 = the property holds, and two controls the oracle must discriminate — a `known_good` tree every probe passes and a `known_bad` tree at least one fails (each a sha or `base` + patch). Each sample is **one `converge --resolve-conflicts` run with no push** (`converge_pr` in resolve mode: the case's `title` + `ac.md` are the PR's intent, its `personas` / `profile` the panel and check-set catalog on the composed tree, its declared project settings — `image`, `parity_command`, `test_command`, `check_commands`, `check_states`, `artifacts_path`, what a `--story` run would resolve from the context doc — the gate, `--max-rounds` the round budget), scored on: **resolved** (a merge commit on the PR head got past the markers guard), **coder-right** (every probe holds on the round-1 merge commit — the coder's own resolution), **pipeline-right** (every probe holds on the final tree), **approved** (the panel converged AND the final tree descends from the PR head — S5's push precondition; a rewritten history is never "the merge S5 would have pushed"), and **UNSAFE** = approved AND NOT pipeline-right — the merge S5 would have pushed; one fails the case regardless of `--bar` (default 0.8 on pipeline-right). A correct resolution the panel rejected is *wasted* (marked on the row). An `infra_failed` run, a loop that ended `interrupted`, a reviewer whose final handoff was invalid, a probe that could not run (launch failure or `--probe-timeout` — an execution error, never a verdict on the tree; on a control it refuses the case), or a harness crash (the run or the probes) is an *errored* sample, excluded from every denominator; **approved** and both right-rates are contingent on **resolved**. Fail-closed order: the coder's and every reviewer's model must be explicit (#304); the oracle is validated on both controls **before the first paid sample** (refused otherwise); a merge the intake refuses (`no_conflict` / `conflict_unsupported` / `base_moved`) aborts the case on its first sample with nothing spent. Prints a per-case table (Wilson 95% CI on pipeline-right); `--report-dir` retains `<case>/sample-<i>.json` (score, per-probe results on both trees, paths, shas), `sample-<i>.merge.diff` (the merge commit's combined diff), `sample-<i>.final.diff`, `sample-<i>.conversation.md`, and `<case>/summary.json` (rates, per-sample tuples, the effective coder + panel + declared project settings, the materialised tree shas, an `expected_fingerprint` of the case id + probes). Exit 1 only when a case has no valid sample or its fixture cannot be measured; a FAIL is the measurement. Shipped fixtures are preflighted where the checkout is present (`tests/test_eval_resolve_shipped.py`: the trees build, the merge conflicts in text paths only, the oracle discriminates its controls). See `evals/resolve/README.md`.

## 5. Plugin Contract

Plugins are subprocesses invoked by a route-runner. They receive a small CLI surface and write an atomic `result.json`.

### 5.1 Invocation

```
<command> --task-json <path> --work-dir <path> --result-file <path>
```

- `--task-json`: read-only JSON file. Today its contents are `{"task": <event-payload>}` — the bus event's payload (a Lithos task envelope) wrapped under a single `task` key. The resolved project entry from the local TOML is **not** included in the file; a plugin that needs the project's on-disk repo path uses the `{{repo}}` command token (below) or loads the TOML itself.

  **`{{repo}}` substitution.** Beyond the three path tokens, a route `command` may carry a `{{repo}}` token. The runner resolves it from `[projects.<slug>].repo` keyed by the claimed task's `metadata.project`, before the plugin forks — so one route serves every registered project, and the repo a plugin acts on is derived from the task's own project rather than hard-coded per route. A `{{repo}}` route whose task has no `metadata.project`, or whose slug isn't in `[projects.*]` on this host, is released with a `[BlockerFailed]` finding (`route misconfigured: …`) and never run. Routes without the token don't require a project.
- `--work-dir`: per-task staging directory at `<orchestrator.work_dir>/<task_id>/`. The plugin owns the tree; the runner reads only the result file.
- `--result-file`: path the plugin must write atomically (temp file + fsync + rename). Partial files must never be observable.

Substitution tokens (`{{task_json}}`, `{{work_dir}}`, `{{result_file}}`) in the route's `command` are filled in by the runner before fork.

### 5.2 Result Schema

The full schema is at `docs/result-schema.json` (JSON Schema Draft 2020-12). Required fields: `schema_version` (const 1), `task_id`, `status`, `exit_code`.

```json
{
  "schema_version": 1,
  "task_id": "uuid",
  "status": "succeeded",
  "exit_code": 0,
  "started_at": "2026-05-29T10:00:00Z",
  "finished_at": "2026-05-29T10:05:00Z",
  "worktree": "/abs/path or null",
  "artifacts": { "key": "rel/path or /abs/path" },
  "commits": ["40-char-sha"],
  "pr_url": "https://github.com/o/r/pull/170",
  "spawned_tasks": ["task_id"],
  "metadata_updates": { "pr_url": "https://..." },
  "error": null
}
```

For a failed run, replace `status` with `"failed"` (or `"interrupted"`) and set `error` to an object with the required keys `category` (one of `config`, `environment`, `input`, `agent`, `git`, `github`, `lithos`, `delivery`, `usage_limited`, `internal`) and `message`, plus the optional boolean `retriable`. No other `error` keys are accepted. (`delivery` (#194) flags an approved dialogue whose PR delivery failed before a PR opened — see §5.5.)

A `failed` result may additionally carry an `escalation` object — the plugin's own account of why it stopped, in the shape the runner's needs-human gate is built from (§2.2, b91177d2):

```json
{
  "escalation": {
    "reason": "max_rounds",
    "summary": "round 5: NOT approved (max_rounds)",
    "brief": { "branch": "loom/us42", "rounds": 5, "cost_usd": 48.53, "test_gate_verdict": "GREEN", "findings_by_severity": {"critical": 0, "major": 1, "minor": 0}, "worktree": "/…", "conversation_log": "/…" }
  }
}
```

`reason` (required) is the closed vocabulary shared with the gate's `metadata.escalation_reason` (the schema enum is pinned equal to `gates.ESCALATION_REASONS`); `summary` (required) is one line (the runner truncates to 200 chars); `brief` is free-form detail copied verbatim onto the gate as `run_brief`. `story-develop` fills it from its `DevelopResult`: the stop status (`max_rounds` / `stalled` / `disputed` / `cost_exceeded`) verbatim, `needs_decision` for an un-contested coder decision (9d5ebca6 — whose brief is the DECISION: every question with its options **whole** (both their length and the size of the collection were checked on admission; blockquoted in the gate description, with any mark that did not fit named as not-admitted), the finding it answers, the reviewer's verdict, and the branch / worktree / conversation-log locators, with the rounds / cost / findings-by-severity post-mortem deliberately left out; its `summary` stays loom-authored, since that line is what the push sinks publish), `infra` for an `infra_failed` run (slice B — the summary is the reason line with its host action), a `failed` run split into `coder_failed` / `reviewer_failed` by its bare `failure_reason`, `delivery` for a failed PR delivery. Absent → the runner composes the gate from `error.category` (`delivery` → `delivery`, `environment` → `infra`, else `failed`) / `error.message` + `rounds` / `worktree`.

An `interrupted` result may additionally carry a `resume` object marking the interruption as retryable:

```json
{
  "resume": {
    "resume_after": "2026-06-12T15:00:00+00:00",
    "run_id": "abc12345",
    "coder_session": "uuid",
    "reviewer_sessions": { "code-quality": "uuid" }
  }
}
```

`resume_after` (required within the block) is the earliest instant a re-run is expected to succeed — the provider's parsed reset time, or a fixed fallback delay when no hint was parseable. The session ids let a future run resume its on-disk transcripts from the retained work dir.

**What the runner does with each field today:**

| Field | Status |
|---|---|
| `schema_version`, `task_id`, `status` | Required by schema; `status` drives the runner's branch (see §2.2). |
| `error.message` | The escalation summary (and so the `[NeedsHuman]` finding text + the gate's `escalation_summary`) when `status == "failed"` and no `escalation` block is present; the `[BlockerFailed]` text on the marker-only fallback. |
| `escalation` | Optional, on `status == "failed"`. The **runner** builds the needs-human gate from it (§2.2): `reason` → `metadata.escalation_reason`, `summary` → `escalation_summary`, `brief` → `run_brief`. |
| `error.category` | Read only when `escalation` is absent, to pick the gate's reason (`delivery` → `delivery`, `environment` → `infra`, else `failed`). |
| `resume.resume_after` | Schedules the in-process re-dispatch on `status == "interrupted"` (see §2.2). |
| `pr_url` | Optional. The PR an approved run delivered (story-develop, #188). On a `completes_task = false` success the **runner** reads it to raise the `pr` gate that blocks the delivered story (Epic H / US10, §2.2) — a success with no `pr_url` creates no gate and posts a loud `[Friction]` (no fallback since US11). It is also read (offline) by `develop attach` to name the PR in the terminal summary, and recorded under the idempotency key so a reaped success still surfaces it. |

(`spawned_tasks` gained its first producer in 819370e5 — story-develop records the tasks spun out of out-of-scope findings, declaratively.) Plugins may populate them; they have no effect on Lithos today. |

### 5.3 Runner Lifecycle

The route-runner enforces `max_runtime_seconds` (per-route config). On timeout, it sends SIGTERM and waits a grace period; if the plugin hasn't exited, it sends SIGKILL, then escalates (`escalation_reason=timeout`). Result-file absence after exit is treated as a contract violation: the runner raises a needs-human gate (`escalation_reason=contract_violation`, the retained work dir as the brief), posts `[NeedsHuman] route <name>: contract_violation — plugin contract violation: <detail>; …` and releases the claim (§2.2).

`retain_failed_workdirs = true` keeps the work directory for triage on failure; on success the work-dir is removed.

### 5.4 Bundled Plugins (scaffolded)

`prd-decompose` is present under `src/lithos_loom/plugins/` as a Python module with a prompt file. Its body is a stub; it does not yet produce real `result.json` output. The route-runner code path is the load-bearing piece exercised by tests. (The former `story-implement` / `story-review-human` stubs were removed — `story-develop` is the one implement→review→PR path; see §5.5.)

### 5.5 story-develop (shipped)

`story-develop` runs the full implement → review → fix → approve loop with containerised agents (one persistent coder session + an N-reviewer panel; per-round commits, an objective multi-check deterministic gate (an ordered check-set run in throwaway containers; the default set is the single `test` check — #131/ADR 0003 §4) whose per-check result + a `git diff --stat` are injected into **both** the coder and the reviewer prompts each round (#136/ADR §6) — every range the loop measures (that stat, the `base_sha` the reviewer diffs from, the round-commit count, converge's `{commit_log}`) is **merge-aware** (PRD S5c): the loop carries the recorded start sha *and* the live base ref (`origin/<base_branch>` when it exists, else the local branch; the PR's base ref for converge) as a `RangeBase`, resolves the fork point per round as the newer of the two along HEAD's history (`git merge-base HEAD <ref>`, never rewinding to a lagging ref), diffs three-dot and enumerates commits `--first-parent` — so a branch that absorbs a merge of its base is reviewed on its own work only, never on the base's landed PRs; a run that never merges its base is measured exactly as before; and the branch itself is cut at the base's **current** tip — the sha of `refs/remotes/origin/<base_branch>` after a fetch by explicit refspec whenever the checkout has an `origin` remote — the refspec creates the tracking ref, so a checkout that never materialised it is fetched too (a fetch that fails or races another fetch falls back to the last-fetched ref, else the local branch, logged; the operator's own branch is never moved; a sha, not the `origin/…` name, so no upstream config is written under a lock concurrent cuts would trip over), else the local branch (#390: lens #85 was cut at a local `main` one merge behind origin and delivered a PR born in conflict) — usage-limit reactions, optional PR delivery — which ends at the open PR: the inline Copilot round was retired by S2 slice D (gate 15690a0e); external reviews are ingested by the github-watcher sweep and remediated by `converge --from-github`, and the per-project/per-task `develop_copilot_review` dial (default off, over the route-level `--copilot-review` flag) fires one fire-and-forget Copilot request at PR open. **Coverage prerequisite:** that replacement runs only where a `pr` gate exists and the github-watcher sweeps it (`[github_watcher] enabled` + `pr_merge_poll_enabled` + `external_reviews_enabled`) — a standalone run creates no gate (its delivery note says the review is NOT auto-monitored; respond via `develop converge <pr> --from-github`), and a failed gate creation now states the lost review monitoring in its `[Friction]` alongside the duplicate-PR hazard). The full design is `docs/prd/archive/story-develop.md` (shipped + archived); the standalone CLI surface is `python -m lithos_loom.plugins.story_develop --help`.

**Daemon mode.** Passing `--task-json` (with `--work-dir` and `--result-file`) switches the plugin to the route-runner contract:

```
uv run python -m lithos_loom.plugins.story_develop \
    --task-json {{task_json}} --work-dir {{work_dir}} --result-file {{result_file}} \
    --repo {{repo}}
```

- `--repo` takes the runner's `{{repo}}` token (§5.1), resolved per task from `[projects.<slug>].repo` keyed by `metadata.project` — so one route serves every registered project. (An absolute path also works if you want a route pinned to one checkout.)
- The task (title, body, `metadata.acceptance_criteria`) comes from `task.json`; `--description` / `--task-id` / `--no-lithos` / `--complete-on-approval` / `--reviewer` / `--develop-config` are rejected in daemon mode.
- **Idempotency short-circuit (US-18).** `--idempotency-key KEY` dedups a daemon run (default: the task id from `task.json`). The first run under a key that ends `succeeded` records its `result.json` in a host-persistent store; a later run under the same key **replays that recorded payload verbatim and exits 0 without re-running** — no second agent loop, no second PR (checked before config resolution, the agent loop, and PR delivery). A record short-circuits only when it passes **all three** gates: (1) it claims success (`status == "succeeded"` **and** `exit_code == 0`); (2) it validates against the full `result.json` schema (`docs/result-schema.json`) — a record missing required fields like `schema_version` / `task_id`, or otherwise off-contract, is rejected even when it claims success, since replaying it would hand the runner an invalid result; (3) its `task_id` matches the task being run — so a reused key (or a tampered store) never replays one task's result into another's. A failed, interrupted, or malformed record is ignored so the task stays retriable (and only a succeeded run is ever recorded, so a failed/interrupted run leaves no marker). The recorder keys off the **explicit** `--idempotency-key` when given, not the task id. Store: one `<sha256(key)>.json` file per key under `$LITHOS_LOOM_IDEMPOTENCY_DIR`, else `$XDG_STATE_HOME/lithos-loom/story-develop/idempotency`, else `~/.local/state/lithos-loom/story-develop/idempotency` — on disk (not the per-task `work_dir`, which the runner overwrites each dispatch) so the short-circuit survives invocations and daemon restarts. The store is bounded: each write prunes it back to the newest `LITHOS_LOOM_IDEMPOTENCY_MAX_RECORDS` (default 10000) records, and evicting an old record just means a later dispatch under that key re-runs. **Trust boundary:** the store is plain JSON at operator-home privilege with no cryptographic integrity — write access to that directory is a trust boundary (the `task_id` binding blocks cross-task replay, but a local process that can write the dir can suppress/redirect a single named task's development). *Out of scope (follow-ups):* in-flight concurrent dedup (locking, while a first run is still going); uniform application across all plugins via the plugin SDK (US-14); the A2A-race path (US-37).
- **Config lookup.** Reviewer config is resolved from the project-context doc's metadata at `projects/<slug>/<slug>-project-context.md` (slug from `task.metadata.project`; fallback: lexicographically-smallest `project-context`-tagged doc under `projects/<slug>/`). - **Model + reasoning effort (#93).** `model` (e.g. `"opus"`, `"sonnet"`, or a full id) and `effort` (a reasoning-effort **level**: `low` / `medium` / `high` / `xhigh` / `max`) are configurable per agent: project-wide on `develop_coder` and per-reviewer in the `develop_reviewers` pool; per-task on the coder via `task.metadata.develop_model` / `develop_effort`. `effort` is **not** a token budget (`MAX_THINKING_TOKENS` is legacy and ignored by current adaptive-reasoning models) and there is **no universal cross-tool effort vocabulary** — Loom adopts **Claude's `--effort` levels as canonical**; each wired tool maps the canonical level onto its own mechanism. Codex (#94) has no effort flag but accepts `model_reasoning_effort` as a `-c key=value` config override, so a codex agent's `effort` is passed as `-c model_reasoning_effort=<level>` (`max`, which codex lacks, coerces to `xhigh`; `model` is honoured via `codex -m`); a not-yet-wired OpenCode would use `--variant high/max/minimal`. This matters in the sandbox: the container mounts auth files only, never the operator's `config.toml`, so an unset `effort` means the CLI's builtin default depth, not the host pin. `effort` defaults to **the agent's default** (no `--effort`); `model` has no such fallback since #304 — every agent must resolve to an explicit model (bottom layer: `[story_develop].default_models`, §3.1) or the run fails closed, because the sandbox image CLI's builtin default is recorded nowhere and drifts with image rebuilds (#303). The persona registry still leaves `model=None` (no hard-pinned, staleable id in code) — explicitness lives in config. Standalone flags: `--coder-model` / `--coder-effort` and `--reviewer-model` / `--reviewer-effort` (the latter apply to every `--reviewer`; per-reviewer values need `--develop-config`). In daemon mode the standalone `--coder-model` / `--coder-effort` flags act as a route-level fallback that project/task metadata overrides. Below all of these, EVERY agent-running surface (daemon mode, the standalone plugin CLI, `develop review` / `converge`, the eval harness's panel and judge) consults one final layer: a **host-wide, per-tool default model** in the loom TOML's `[story_develop].default_models` table (§3.1), keyed by each agent's resolved `tool` (`claude` / `codex`) — the lowest-priority `model` source; an agent whose tool has no configured default (and no higher-priority pin) **fails the run closed** (#304). There is no global-default counterpart for `effort`. Invalid-value handling differs by surface: **standalone CLI** flags **error** (non-zero exit) on bad input (empty/whitespace model, or an off-canonical effort level); **project/task metadata and the daemon-mode CLI fallback** drop an invalid value with a `[Friction]` finding and continue — daemon-mode config resolution never fails the run (so the effort flags are validated by `parse_effort`, not argparse `choices`, which would otherwise reject a bad route fallback at parse time). A malformed route fallback is surfaced with friction **even when metadata already supplies that field** (so a route-config typo isn't silently masked); the valid fallback value is *applied* only where metadata left the field unset.
- **Container shared memory.** Every **workload** container the plugin launches — deterministic-gate checks, per-turn agent containers, and the isolated auto-format pass — runs with `--shm-size 1g`: Docker's 64MB `/dev/shm` default crashes chromium under page-heavy headless-browser e2e workloads (a `make e2e` parity step, or agents driving playwright). `1g` is a tmpfs **capacity limit**, not preallocated memory, and `--ipc=host` stays disabled (hardening preserved). This is a fixed host policy (`CONTAINER_SHM_SIZE`), not per-project config; the short-lived tool-probe container (`command -v` only) is deliberately outside the contract — it runs no workload. Operators sizing a host: a `thorough` run can hold a coder + several reviewer/check containers concurrently, each with this ceiling.
- **Agent tools (#94).** Each agent's `tool` is `claude` or `codex`, declarable independently per coder (`develop_coder.tool` / `--coder`) and per reviewer (`develop_reviewers[].tool`), so a heterogeneous panel (e.g. `code-quality = codex`, `security = claude`) and an engine-switching `fallback_chain` both work. Codex runs as `codex exec --json --dangerously-bypass-approvals-and-sandbox` (first turn) / `codex exec resume <thread_id> …` (later turns) inside the same hardened per-turn container model (ADR 0002). Two codex specifics: (1) the session handle is **minted by the tool** — the `thread_id` from the first turn's `thread.started` `--json` event is captured and reused for resumes (claude's is a caller-supplied uuid); (2) the per-run config/transcript dir is `CODEX_HOME` (under the work-dir, never `/tmp`) with a single `auth.json` bind-mounted from `~/.codex`, and codex has no skills concept (it honours the worktree `AGENTS.md`). **Cost gap:** codex reports token usage, not USD, so codex turns contribute `0.0` to the `max_cost_usd` ceiling — for codex agents the ceiling is unenforced (a run stays bounded by `max_rounds` + per-turn timeout); a token→USD pricing map is a follow-up. When `max_cost_usd` is set **and** any participating tool (coder, a reviewer, or a reachable `fallback_chain` entry) can't meter USD, story-develop logs a one-time startup WARNING naming exactly those tools — so an operator who set a ceiling learns it only bounds the USD-reporting participants. The message is **capability-driven** off the Engine adapter's `meters_cost_usd` (ARCH-2/E4/#102), so a future non-metering engine is named automatically without a code edit; the ceiling checks themselves are untouched. Codex usage-limit *strings* are not yet captured (feasibility-gate G4), so a codex limit currently classifies as a generic `agent_error` rather than `usage_limited` — an engine `fallback_chain` still switches *to* codex on a claude limit, but switching *off* codex on a codex limit awaits the captured strings.
- **Engine adapter (ARCH-2).** Everything the plugin must know to run a specific tool — its capabilities (`meters_cost_usd` / `mints_session_handle` / `supports_effort`), container provisioning (config mount + env var, auth files, skills dir), the per-turn CLI argv (`cli_argv`, plus its `docker exec` wrapper `build_exec_argv`), the unified turn parse (`parse_turn`), and the session-transcript layout — lives on a per-tool **`Engine`** behind a registry (`engines.get_engine(tool)` / `is_supported` / `supported_tools`), so adding a tool is one adapter rather than new `tool`-string branches across the container / turn / transcript / config code. The capabilities **express** the decisions ADR 0002 + #94 already made; the adapter does not re-decide the session mechanism ([ADR 0002 addendum](adr/0002-story-develop-session-mechanism.md#addendum-arch-2--the-engine-adapter-expresses-this-mechanism-it-does-not-change-it)). The **bare** host-side argv `cli_argv(session_id=None)` (no `docker`, no session flags) is what the review-correctness eval judge (§4.16) runs off-container, so the in-container turn path and the host-direct judge call share one implementation of "invoke tool X and read its result."
- **Ecosystem-aware gate applicability (#133 / ADR 0003 §4).** When no explicit `develop_test_command` is set, the `test` check's command is auto-detected per ecosystem (Python / Node / Rust / Go, by marker file). Applicability is **declared, not inferred from absence**: a markerless / docs-only repo declares the gate not-applicable (so there is simply no gate), but a repo whose detected ecosystem *expects* a check that has **no runnable command** is treated as **expected-but-absent** — a *required* check there **blocks approval** (the coder prompt names it `EXPECTED BUT ABSENT`) instead of silently passing, so deleted or missing tests in a code repo cannot slip the gate. The per-ecosystem catalog of the canonical checks (`format` / `lint` / `typecheck` / `test` / `sast` / `dep-audit`) and the resolver that turns a *desired* set into concrete commands ship here as the foundation a Review Profile (#139) selects against; a *required* check with no mapping for the detected ecosystem fails resolution with an operator-actionable error rather than silently degrading. The first-class deterministic-finding ledger (stable ids, per-tool severity mapping) over these checks is #132. **Per-check command override (#273):** a repo may declare its own command for any **non-test** check via `develop_check_commands` metadata or the `--check-command NAME=CMD` CLI flag (on `develop`, `develop review`, `develop converge`); an overridden check runs that command **verbatim** — trusted as-is (no `uv`-wrap, no tool-probe, exactly like `develop_test_command`) and **beats** catalog discovery — but only where the canonical check applies to a detected ecosystem (an override for an N/A check is inert). This is the fix for a canonical command that over-scopes vs the repo's real policy (bare `uv run pyright` scanning a test tree full of pre-existing type debt instead of the repo's scoped `make typecheck`), which otherwise forces extra fix rounds and a repo-config change bundled into the feature branch. **An override runs raw (`raw_exit`):** its verdict is its exit code, read end-to-end without the finding-adapter path — even when its command *begins* with an adapter tool (`ruff` / `bandit` / `pip-audit`), no JSON/exit-zero flags are appended to the operator's string. So overriding a check opts it out of structured findings (its raw exit code + output tail feed the coder). An override is also inert when the active profile does not select that check, not only when the check is N/A for the detected ecosystem. **Per-check state 3-state (#273 slice 2):** a repo may set any **non-format** check's blocking state via `develop_check_states` metadata or `--check-state NAME=STATE` (on `develop`, `develop review`, `develop converge`) — `required` / `informational` / `off`. `off` **drops** the check cleanly (runs nothing, records nothing), kept distinct from a required-but-tool-absent check (an expected-but-absent blocking placeholder that still blocks); `required` / `informational` override the profile's declared state. This generalizes the `test_gate` boolean — `test_gate=false` is exactly `{ test = "off" }`, and an explicit `check_states["test"]` wins over the legacy flag. Coupling caveat (Refinement 3): on a **compiled-language** repo (Rust / Go) the compiler / test run *is* the type check (there is no separate `typecheck` check), so turning the `test` check off silently removes type checking — the gate logs a loud warning in that case. **Aggregate repo-parity check (#273 slice 3 / [ADR 0010](adr/0010-aggregate-repo-parity-check.md)):** setting `develop_parity_command` metadata (or `--parity-command` on `develop` / `develop review` / `develop converge`) appends a `repo-parity` check — **required**, **candidate-stage** (run once on the approval candidate, not every round), **raw exit** (runs the command verbatim, no adapter, blocks on non-zero, raw output tail to the coder). It runs **regardless of detected ecosystems**, so it closes "gate-green ≠ repo-CI-green" for a repo whose CI enforces checks beyond the structured set (diagram/codegen drift, docs lint, license checks) *and* is the **primary** gate for an ecosystem the catalog can't model (C/C++). It is **explicit opt-in** (no auto-probe); the repo-side contract is that `parity_command` be a superset of CI. Not part of the `check_states` 3-state — to disable it, unset `parity_command`. The delivery regression gate keys only on `test`, so parity does not run at delivery. Check isolation (#282): `run_check_set` exports the committed tree **freshly for every check, into a never-reused directory**. Checks mount the tree read-write, so without re-export a mutating check (a test suite or coverage run regenerating `docs/generated`) would leak its side effects into later checks' input — order-dependent verdicts, and in the worst case a false-green `repo-parity` judging an already-regenerated tree; and because establishing a fresh tree never deletes a previous check's (which a check can render undeletable — a mode-000 directory, other-UID files from a custom `develop_image`), a poisoned tree can't turn the next required check into a skipped non-blocking infra error either. The guarantee is scoped: every check's verdict is independent of earlier checks' **workspace-tree** mutations, on every path (develop, review, converge) — the persistent tool-cache mount is deliberately shared across checks and rounds, so cache-level side effects are outside it. Note the parity command runs in a tree **without git metadata** (`export_tree` extracts committed content only), so it must not shell out to `git`; assert generated-artifact freshness with a baseline-first content compare instead. Because a raw-exit check leaves **no** ledger finding and is not the `test` gate, a blocking `repo-parity` (or command-override) result is **named explicitly** in the operator-visible outcome — the run message, the `[DevelopResult]` finding, and the standalone summary (via `DevelopResult.blocking_checks`) — otherwise a final-round parity-only failure (reviewers pass, parity red) would be invisible and survive only as the round's `output_repo-parity.txt` artifact. **Precedence:** `parity_command` resolves project › task › route like every scalar `develop_*` field — task metadata beats project metadata beats the route `--parity-command`; a layer may **replace** a lower command but **cannot disable** it (metadata `None`/absent = inherit, blank rejected), so a route `--parity-command` is a per-route policy floor applied to every project that route serves (see [ADR 0010](adr/0010-aggregate-repo-parity-check.md) "Precedence and disabling").
- **Deterministic-finding ledger + live lint (#132 / ADR 0003 §5).** Finding-producing checks — today a live **`lint` (ruff)** check added as an extra **informational** check on every Python repo where ruff is present (it runs **regardless of `develop_test_gate`**, which scopes the `test` check only — disabling tests must not silently drop the lint floor) — have their JSON output parsed into a per-run **gate finding ledger**: each finding gets a stable `gate/<check>-NNN` id (a violation keeps its id across rounds; one that vanishes on a clean re-run is closed `fixed`; identity is `check + rule + file/line + package`, so two packages sharing a CVE stay distinct), a severity **mapped from the tool's native level** (ruff `W`→minor else major; bandit HIGH→critical / MEDIUM→major / LOW→minor; pip-audit→major), and is **gate-owned** — the coder cannot mark a `gate/*` finding fixed (closure is re-running the check green). These structured findings are injected into the coder + reviewer prompts (in place of a raw output tail) and into the `[DevelopResult]` finding, and persisted to `gate_ledger.json` (survives a resume). A finding-producing check runs in a JSON / don't-fail-on-findings mode so the tool's exit code never decides blocking (its severity does, ADR §5). The `lint` check began as **informational** (#132); per-profile check-set membership is #139 and the **required floor went live in #140's floor slice** — `lint` now blocks `standard` when the ledger holds a `major`+ ruff finding (see Review Profiles below). `bandit` / `pip-audit` adapters + severity tables ship too and light up once a profile selects those checks (the tools live in `ralph-sandbox` as of its SAST update).
- **Review Profiles (#139 / ADR 0003 §1–§3).** A **Review Profile** is a named bundle of {panel personas, deterministic check-set (per-check state + stage), blocking policy} — the dial for review strength. Three canonical profiles ship: **`minimal`** (`strength_rank` 10; gate-only panel; required checks `format` / `lint` / `test`), **`standard`** (rank 20, the **default**; panel correctness + security; required `format` / `lint` / `typecheck` / `test`, informational `sast`), **`thorough`** (rank 30; panel correctness + security + architecture + test-quality + dependency-hygiene; required + `sast` + `dep-audit` + `coverage`, informational `semgrep` — the expensive checks staged to the approval-candidate round). `sast` (bandit) is informational on `standard` (kept so per Option A; its first-party bandit baseline is triaged as of #173, so promoting it to required is now a deliberate option) and required only on `thorough`, an explicit opt-in (#140 floor slice, Option A) — monotonicity holds because `standard`'s required floor stays a subset of `thorough`'s. Selection precedence: per-task `task.metadata.develop_review_profile` › project-context `develop_review_profile` › host `[story_develop].default_review_profile` › built-in `standard`; an unset layer inherits the one below, silently. An **explicit-but-unknown** profile name **fails closed** — the run halts before any agent runs with a blocking `[Friction]` (the deliberate exception to the friction-not-fail norm: silently substituting a profile would defeat the dial) — unless the host sets `[story_develop].unknown_profile = "strongest"`, which falls back to the strongest configured profile + friction (never weaker). A **load-time `strength_rank` monotonicity invariant** requires a higher-ranked profile's required checks **and** required personas to be a superset of every lower-ranked profile's (non-monotonic → a `ConfigError` at load). #139 **resolves + validates** the profile; **#140 slice 1** applies it to the **deterministic check-set**: the resolved profile selects which checks run, with real per-image tool probing and **per-check staging** — fast checks (`lint` / `typecheck` / `sast` / `test`) run every round for tight coder feedback, while candidate checks (`dep-audit` / `coverage` / `semgrep`) run only on the **approval candidate** (the round that would otherwise pass). A **fast** check runs before the panel each round, so it feeds the coder + reviewer prompts + the gate ledger (ADR §6); a **candidate** check runs only on the approval candidate, so its result reaches the gate ledger + the `[DevelopResult]` finding and, when it blocks, holds approval so a follow-up round surfaces it to the coder/panel. `format` is not run as a standalone gate check; instead the **auto-format pass (#134, ADR §4)** runs each detected ecosystem's formatter in **write** mode (`ruff format` / `prettier --write .` / `cargo fmt` / `gofmt -w .`, image-probed once per run, image-global — never `uv run`-wrapped) immediately after the coder's commit, and commits any change as a **separate** commit on the round so the gate **and** the reviewer panel see that exact formatted tree (loom never formats after approval). The formatter is treated as **untrusted** (a repo-controlled formatter config / plugin can run arbitrary code): each runs against an **isolated `git archive` export** of the coder's commit — never the live worktree — in a hardened container with `--network none` and a cache **separate** from the deterministic gate's, so it cannot reach the `.handoff` orchestration channel (worktree-only, absent from the export), poison the gate's package cache, or egress. Changes are applied back to the worktree's tracked files only when a formatter **exits clean** (success-gated): a nonzero / timed-out run may have left a half-rewritten tree, so its edits are discarded rather than reach the gate / panel. The pass is **best-effort** — an absent / erroring / nonzero formatter is skipped, never fatal — and because formatting is applied deterministically up front, the read-only `format` check should always already be clean, so it stays required-but-non-blocking. **#140 slice 2** applies the profile to the **reviewer panel** (*replace-default-only*): when no reviewers are explicitly selected (no `develop_default_reviewers` / task `reviewers` / `--reviewer` / `--develop-config`), the profile's personas become the panel — `standard` → correctness + security (up from the single `code-quality` reviewer), `thorough` → all five (#137) — and each persona still picks up the route/host model + effort layers (a persona's own explicit effort, e.g. `security`'s `xhigh`, is respected, not blanket-downgraded). An explicit reviewer selection still **wins** (the escalate-only floor — you cannot select *below* the profile's persona floor — is the overrides slice). **#140 floor slice** makes each profile's **required floor actually block** (it is no longer informational-only — the deterministic gate now gates approval, not just the panel): a *required* check blocks when its tool is **expected-but-absent** or **times out**, or — for a finding-producing tool (ruff / bandit / pip-audit) — when the **gate ledger holds an open finding at or above `major`** for it (severity, not raw exit, decides for a finding-producing tool, ADR §5) **or** when it exited **red with no open findings** — a `--exit-zero` adapter that exits non-zero failed to run, so an empty-ledger red blocks rather than silently passing (#167 floor-liveness); a no-adapter tool (pyright / pytest / coverage / semgrep) reads its raw exit code. **Informational** checks never block, even RED. **Env-dependent** checks — `typecheck` / `coverage` (+ `test`), whose tool runs *inside* the project venv (pyright resolves third-party imports; pytest / coverage run the code) — run via `uv run` on a uv-managed repo (a `uv.lock` is present) so they resolve inside the project venv materialised in the gate container, exactly as the `test` check already does; bare, `pyright` sees the throwaway container's empty environment and false-positives (#165). The static-analysis checks (ruff / bandit / semgrep — AST/source only) **and** `dep-audit` stay **bare** and image-global (`pip-audit` is an *external auditor*, not a project dependency, so it is never `uv run`-wrapped). `dep-audit` audits the project's **resolved** deps — `uv export --no-emit-project --format requirements-txt | pip-audit -r /dev/stdin` (#167), not the container's ambient env; `command_tool` resolves the pipe's consumer (`pip-audit`) as the adapter tool so the floor reads its severity ledger (and a failed run blocks via floor-liveness). Per **Option A** the default `standard` blocks only on `lint` + `typecheck` + `test` (exactly what `make check` already enforces — zero new false-positive surface), with `sast` (bandit) informational on `standard` (its first-party baseline is now triaged — #173 — but promotion stays a deliberate choice); `thorough` additionally blocks `sast` / `dep-audit` / `coverage`. `minimal` is gate-only, but a true zero-reviewer panel is the overrides slice, so the floor slice keeps the built-in reviewer + a `[Friction]` for `minimal` for now. As of **#173** the `thorough` candidate-stage gates are runnable on a uv project: `sast` scopes off `.venv`/vendored deps (a bare `bandit -r .` scanned third-party code in the materialised venv), `coverage` runs `coverage run -m pytest && coverage report` against a real `[tool.coverage] fail_under` (with `coverage` provisioned as a dev-dependency, since it is venv-resident), and the repo's first-party bandit baseline is triaged via per-site `# nosec`. Still to come: additive escalate-only per-task/project **overrides** + `allow_escalation` (audited), making `minimal` truly gate-only and the persona floor non-weakenable.
- **Canonical reviewer personas (#137 / ADR 0003 §8).** A built-in registry of one-dimension reviewer personas, **opt-in by name** — name any of them in `develop_default_reviewers` (or a task's `metadata.reviewers`) and it resolves to a ready-made spec with its engine, severity floor, reasoning effort, and a focused `system_prompt` baked in; no need to redefine the prompt in `develop_reviewers`. An explicit `develop_reviewers` entry of the same name **overrides** the canonical (so a project can re-tune one). As of **#140 slice 2** the zero-config default follows the **`standard`** profile — a project that selects nothing runs `standard`'s **correctness + security** panel (replacing the former single generalist `code-quality` reviewer); the dial is the Review Profile (#139), an explicit reviewer selection still wins (a typo'd one falls back to the single `code-quality` reviewer), and gate-only `minimal` keeps that single reviewer + a `[Friction]` until the overrides slice wires a true zero-reviewer panel (the floor itself shipped in #140's floor slice). The personas use **heterogeneous engines on purpose** (diverse engines → diverse blind spots, #94):

  | persona | engine | threshold | focus (one dimension) |
  |---|---|---|---|
  | `correctness` | codex | major | boundaries, off-by-one, races, error handling / propagation, idempotency, resource cleanup; **input domains** — a value of the right *type* but outside the documented range / unit / set, asked for **both** outcomes (does it raise, or silently return a wrong answer) (RH-1) |
  | `security` | claude (xhigh) | minor | OWASP Top 10 (2025) + CWE: injection, broken access control / IDOR, secrets, SSRF, deserialization, crypto misuse; **both directions** of a privileged/unprivileged boundary — what is read *and* where the result lands (RH-1) |
  | `architecture` | codex | major | module boundaries per `AGENTS.md`, abstractions / coupling, public surface; reviews the full `base..HEAD` |
  | `test-quality` | codex | minor | edge cases, mocks that hide behaviour, determinism, AC↔test mapping |
  | `dependency-hygiene` | claude | minor | new-dependency justification, supply-chain reputation, pinning, license |

  Each persona prompt is held to **one dimension** with an explicit "NOT your job" deferral; the base reviewer templates add a **"stay strictly within this focus"** discipline line (only when a focus is set, so the generalist default is untouched) and a shared **severity-calibration** rubric (critical / major / minor definitions) so the panel calibrates consistently before the orchestrator applies each persona's `block_threshold`. Personas leave `model` unset (inherit the route / project default — no hard-pinned, ageing model id); an operator may still pin a cheaper model per persona. *Deferred:* the test-quality persona's "coverage tail" (ADR §8) awaits a gate that captures coverage — bundled with the SAST gate work (#135 / #132).
- **Status mapping.** `approved` → `succeeded`; with the route's `completes_task = false` (§2.2) the runner then leaves the task **open** for human merge — raising a `pr` gate that structurally blocks the story (Epic H / US10) and releasing — rather than completing it, so an approved run never closes a github-linked issue for un-merged work. `interrupted` (usage-limit pause budget exhausted) → `interrupted` with `error.category="usage_limited"` and a `resume` block (the runner schedules a re-dispatch, §2.2); `infra_failed` (slice B: an auth / transport / spawn failure persisted through its retries — see the failure reactions below) → `failed` with `error.category="environment"`, `retriable=true` and `escalation.reason="infra"`, so the runner's needs-human gate names the host action; every other stop (`max_rounds`, `stalled`, `disputed`, `needs_decision`, `cost_exceeded`, `failed`) → `failed`. An approved dialogue whose **PR delivery fails** before a PR opens (e.g. `push_branch()` / `gh pr create` raises) → `failed` with `error.category="delivery"` carrying the reason (#194), **not** `succeeded` — no PR exists, so the task stays open/retriable and the run is not recorded under the idempotency key; the daemon also drops a private `run_dir/delivery.json` failure marker so `attach` reports it at once (§4.14). The **standalone CLI** (`--open-pr`) shares this exact path via `pr_delivery.deliver_guarded` (ARCH-1.S3): a delivery failure there likewise **skips `--complete-on-approval`** (an approved dialogue with no PR is not done) and **exits non-zero**, and writes the same private `delivery.json` markers (so the on-disk delivery contract is now symmetric across both surfaces) — closing a latent gap where standalone marked the task completed and exited `0` on a failed delivery. The markers use the identical format `develop attach` reads; note that `attach`'s run-dir *discovery* targets the daemon `<work_dir>/<task_id>/<run_id>` layout, so a standalone run under its default `<work_dir>/<run_id>` layout is **not** auto-discovered by `attach <run-id>` — the marker gives on-disk contract parity, not turnkey standalone attach (which would need discovery support for the standalone layout).
- The plugin still owns its Lithos round-trip directly (the `[DevelopResult]` finding + `develop_*` metadata, same as `--task-id` mode); `result.json` carries `status` for the runner, so there is no double-application.
- **Out-of-scope escape (819370e5).** A reviewer may mark a finding `status: out-of-scope` — REAL, but not this story's to fix (pre-existing on the base, a harness/pipeline fault, another story's agreed work). The status is reviewer-owned (a coder handoff cannot set it — its route stays the dispute flag), **resolved** (never counts toward any block threshold, leaves the stall signature like any resolution), and **requires a `deferral_reason:` saying why** — a separate handoff key, so the mandatory why can never overwrite `rationale:`, which keeps describing what the defect is (a NEW finding filed directly as out-of-scope must carry both); the parse rejects the handoff otherwise, and the reviewer is re-prompted. On the **artifact pass** every finding is validated as a first sighting regardless of any carried-over id (`check_findings_as_new`) — `apply_artifact_review` remints ids, so the existing-id exemption from these rules never applies there. At run end every deferred finding is **spun out as its own Lithos task** via `task_spawn` (a `discovered_from` edge lands atomically; `inherit_tags=false` is load-bearing — inheriting would copy the story's `trigger:*` tag and auto-dispatch the spawned task), best-effort with the same never-fail-a-finished-run policy as the results post: a failed spawn degrades to the finding text preserved in the `[DevelopResult]` under a loud `SPAWN FAILED` note. The `[DevelopResult]` carries a dedicated `deferred out-of-scope findings` section (the open-findings section filters on `is_open` and would silently drop a resolved deferral), the metadata patch records `develop_deferred_tasks` (the spawned ids), and `result.json` gains its first `spawned_tasks` producer (still runner-ignored, §5.2). Spawns are deliberately **not de-duplicated across runs** — a retried run whose reviewer defers the same defect again files a second task; both carry `deferred_from_task`/`deferred_from_run` provenance. On the eval side, a deferred finding is an **escape, not a catch**: `match.actionable_findings` excludes `out-of-scope` findings from both the structured matcher and the judge (noise counts keep them), so a panel that wrongly defers a seeded in-scope defect drops that case's catch — the floor sweep is the mis-defer detector, no separate fixture needed. Prompt surface: `FORMAT.md` documents the status; `reviewer_round.md` / `reviewer_rereview.md` teach it narrowly ("never for a defect this diff introduced or touched"); `reviewer_artifacts.md` is deliberately untouched (a measured surface — reviewers there learn the status from `FORMAT.md` alone).
- **Needs-decision escalation (9d5ebca6).** The coder may mark a finding `status: needs-decision` instead of `disputed` when it is out of *this story's* reach — the acceptance names a capability the product does not have, or asks for a guarantee the platform cannot give. It is the ordinary dispute **plus** the decision behind it, carried in its own handoff keys `decision_question:` (the one thing a human must answer) and `decision_options:` (the options and what each costs), with `coder_response:` keeping the reasoning and `rationale:` still describing the finding. **Both halves are required, each at most 2000 characters**: a mark missing or overrunning either is recorded as a plain `disputed` under the ordinary guard — a gate brief naming no choices or costs would tell the operator less than the deadlock it replaces, and a decision too long to publish whole would reach them as a *prefix* of the question they must answer, which an ellipsis signals but does not repair. Length is therefore part of the **admitted domain**, not a publication trim, and so is the size of the **collection**: `decision_phase` admits decisions in panel-then-ledger order while they fit a 12 000-char publication budget (the first always fits — every field is bounded), and a mark past it is not a decision on that run at all — it stays the ordinary dispute it also is and is named as *not admitted*, since an id standing in for a question rebuilds by hand exactly the investigation this feature removes. The same admission runs where the result is assembled, on the same ordered input, so what the run says it has is exactly what both operator surfaces carry **whole**. Only the supporting context beside a decision (the finding's rationale, the coder's reasoning) is trimmed — at 600 chars, saying so, with the whole text a conversation-log read away. The coder handoff stays parse-tolerant so a malformed decision can never drop the round's other disputes. The **reviewer gets exactly one turn**, and must **answer explicitly** on any such finding it keeps open — explicitly, because only an answer is a record; an unanswered decision is uncontested and escalates. The two verdicts are exhaustive and mutually exclusive: `decision_verdict: contest` **plus** `decision_contest:` quoting the acceptance line the finding already meets (degrading it to an ordinary `disputed` under the unchanged two-round guard; a contest without its citation is rejected), or `decision_verdict: concede` **with no citation** (the pair contradicts itself and is rejected — it used to pass validation and then silently contest). Resolving the finding answers it too; **omitting the verdict is rejected and re-prompted once per turn** — one pass names every unanswered decision in a single correction, because the panel allows exactly one correction retry and an ask per *finding* let N unanswered decisions consume N rejections (the second failing the handoff). After that correction the review **lands** whatever it says: failing the handoff instead would let the coder (the party the guard adjudicates) turn its own scope dispute into a `reviewer_failed` stop by marking findings the reviewer might miss (security/f-008). The apply-time rule over what lands is the acceptance criteria's own partition, and it is **total**: only a clean `contest` + citation contests — everything else (no verdict at all, a contest without its citation, a concession that still cites) is **uncontested**, leaves the decision pending, and escalates at the end of that round (correctness/f-001). A clean `concede` is recorded as the audit trail of *which* uncontested shape it was, not as the arming condition — and that record is **published on every surface the operator decides from** (security/f-004), since both shapes escalate and the gate is where a human ratifies one: `PendingDecision.reviewer_verdict` (`conceded` | `unanswered` — where `unanswered` means the reviewer **was asked**, since the question is quoted into its prompt via `render_open` and a missing verdict is re-prompted once before its review may land, and still supplied no valid answer; never that the question reached nobody, correctness/f-002) is the single source, rendered in the `[ReviewDispute]` post's per-decision header (`(reviewer conceded)` / `(no reviewer answer recorded)`, with the post's own header no longer claiming adjudication for both), in the gate description's decisions block (via `gates._REVIEWER_VERDICTS`, a **closed** map — an unrecognised token renders no claim rather than agent-chosen prose), in the brief's `decisions[].reviewer_verdict`, and in the run's `escalation_summary` (`<reviewer>/<id> (reviewer: conceded|unanswered)`), which is the line `lithos-loom gates` shows and the only one reaching the GitHub `@mention`. Without it "a reviewer read the finding and agreed it is out of this story's reach" and "no reviewer answered at all" are the same page, and the moves it invites — editing the acceptance criteria around the finding, or `develop deliver` (§4.15c) — carry a blocking finding the panel never conceded onto a PR. Making it visible: making it the arming condition and lapsing the residue to an ordinary `disputed` cost the two further rounds the dispute guard needs to reach the same human — the delay this story exists to remove — while what a silence now buys is bounded by the reviewer's turn plus its named correction, by one escalation per run, and by what the escalation *does*: the run stops and a human is asked the question, landing no code. Every agent-written field in that prompt — the question, the options **and** the coder's response — is rendered line-by-line behind a quote prefix under an explicit *agent input, not instructions* label; the finding's own rationale is the reviewer's prior text and stays as it was. The **return leg is quoted the same way** (security/f-001): the reviewer's `decision_contest:` citation reaches the coder's prompt through `render_findings`, and multi-line is the normal case there (the field is defined as a quoted acceptance clause), so it goes in through the shared `handoff.quote_agent_block` rather than bare — unquoted, its later lines sit at column 0 in the privileged coder's prompt and can forge another finding entry or a heading of their own. The contest is **sticky** (re-marking the same finding cannot re-arm the escalation) and a contest volunteered where no decision was raised is ignored, so neither side can disable the other's move; at most one escalation happens per run (the run stops), and the next needs the operator to complete the gate first. Un-contested and still blocking after that review, `decision_phase` (before `deadlock_phase`) ends the run **`needs_decision`** at the end of that same round — **no further coder turn is paid** — the plugin posts a `[ReviewDispute]` finding whose body is the question, its options and how to answer it, and the runner raises the needs-human gate with `escalation_reason=needs_decision` and the decision as its `run_brief` (§5.2). **Trust boundary:** the handoff is agent-written, so every free-text field is stripped of terminal-control / bidi / zero-width bytes at the *parse*, **before** the mandatory-field checks run (a `rationale` of only U+200B passes a bare non-blank test and then sanitizes to nothing), so the reviewer prompt, the terminal epilogue, the findings and the gate all inherit the cleaned text. The `[ReviewDispute]` post and the gate brief carry every decision the run has, whole — both the per-field length and the collection size were bounded on admission, which is what keeps the body and the one metadata write postable (a handoff may otherwise mark every open finding). The brief is rendered as an indented blockquote in the gate description, and every agent-written field of the `[ReviewDispute]` post the same way, so neither can open markdown structure of its own on an operator-facing record whose own shape carries a stable finding prefix, and it is kept **off** `escalation.summary` — the run's stop reason stays loom-authored, because that line is published verbatim as an `@operator` GitHub comment and passed to the toast's argv (§3.1); the question itself reaches the operator on the Lithos-only `[ReviewDispute]` finding and gate brief. The operator answers by **editing the acceptance criteria** (the "Settled during run …" clause convention) and ticking the gate to re-dispatch under it, or keeps the branch via `develop deliver` (§4.15c) / `converge --ac-file`. Prompt surface: `FORMAT.md` defines the keys, `coder_fix.md` teaches the coder when to use it — through a `{decision_escape}` slot the loop fills from `coder_decision_escape.md` — and `reviewer_rereview.md` teaches the verdict + contest. Every reviewer prompt that can be **asked** for a verdict carries the same contract from ONE fragment, `reviewer_decision_answer.md`, filled into a `{decision_answer}` slot (`panel_prompts.decision_answer_block`): the re-review, and the **reseed** a provider usage limit builds — a fresh session, but run under the same `FindingLedger.check`, so a replacement reviewer owes the same verdict, and since the lapse went a non-answer escalates (security/f-005). The reseed also gained the `{open_findings}` slot the re-review has, since `render_open` is the one call that puts the coder's question in front of a reviewer quoted and labelled as agent input — without it the question reached a reseeded reviewer only through the raw coder handoff file, unquoted and unframed. Round-1 `reviewer_round.md` is the one re-review-shaped prompt that takes neither — no coder finding exists yet, so no decision can be pending. **Story-develop only.** `develop converge` (§4.15a) shares this fix loop but has no needs-decision surface behind it — `converge_pr` flattens every unapproved run to `not_converged`, and both watcher consumers (external remediation, the conflict resolver) branch on that top-level status — so a converge run leaves the slot empty and builds its ledgers with `decisions_enabled=False`: a coder `needs-decision` there is recorded as the ordinary `disputed` it also is, under the unchanged two-round guard, and the escalation never fires. Extending the escape to converge means giving those two paths a decision outcome of their own, and is its own slice. The motivating pair: two runs in one day ended `disputed` on findings the coder was right to refuse, $26.44 and $89.41 after it first said so.
- **Review-metadata record (#139 / ADR 0003 §11).** Every run's metadata patch records, alongside `develop_status` / `develop_branch` / `develop_run_id` / `develop_rounds` / `develop_cost_usd` (+ `develop_pr_url` when delivered), the per-run review signal for later outcome-correlation: `develop_review_profile_used` (the **resolved** profile that ran — an output-only key, kept distinct from the operator's `develop_review_profile` *input* selection so recording the run never pins a task's profile), `develop_review_panel` (the reviewer names in the final panel), `develop_findings_by_severity` (the final panel's findings counted by severity, canonical `critical` / `major` / `minor` zero-filled), and `develop_test_gate_verdict` (`GREEN` / `RED` / `TIMEOUT`, when a gate ran). The same record (profile + panel + findings) also lands in the durable run-state `state.json`. The basket of post-merge outcome signals + success-metric rollup it correlates against is a later phase (ADR §11, reserved-shape).
- **Coder prompt discipline (plan-first + pragmatic test-first).** Both coder templates (`coder_init.md` implement turn, `coder_fix.md` fix turn) carry an explicit working discipline: understand the task + surrounding code and plan the approach before editing, make the **smallest change** that satisfies the acceptance criteria (or resolves the finding), and add a test that would **fail without the change** for each acceptance criterion / real bug fix **and run that targeted fast test** (red→green) — pragmatically, matching the project's existing test layout rather than manufacturing ceremony tests for trivial code. The run is scoped to the **targeted fast test**, not the full suite, so it never relaxes the single-turn / no-background-and-wait rules. This complements the test-quality persona (which judges whether the tests actually protect the behaviour) and the objective gate; it does not relax the single-turn / no-background-and-wait rules (#115) — the gate still owns the authoritative test run.
- **Sandbox capability disclosure (SC-1).** At run start the resolved `develop_image` is probed once in a short throwaway container (`sh -c` over a fixed catalog: language runtimes and their versions, `playwright` / `$PLAYWRIGHT_BROWSERS_PATH` / a chromium binary), and the result is rendered into a `{sandbox_facts}` section carried by **every** coder and reviewer template — including `reviewer_reseed.md`, whose fresh session has no other history. The result is cached by the image's **content digest** (`docker inspect --format '{{.Id}}'`, not `RepoDigests`, which is empty for a locally-built image); the digest is re-resolved at every run start, so two tags of one build share a probe and rebuilding a tag **in place** re-probes rather than serving stale facts. A probe failure is sticky for the process, so a hanging probe costs its timeout once rather than once per entry point. Coder prompts additionally get the "treat this list as authoritative" framing; reviewer prompts get the facts alone, so a panel can falsify an environment claim without being handed how-to prose that is off its lane. Claims are exactly as wide as the search behind them: a tool the probe misses renders as *not found on PATH*, not *not present*, and only the positive findings are framed to the coder as authoritative — `command -v` cannot see a tool installed outside `PATH`, and an absence loom never established is the original defect inverted. Networking is likewise narrowed to what loom can see: it reports that it does **not disable** container networking (only the formatter runs `--network none`) and says outright that outbound reachability was not probed — not passing `--network none` does not prove egress works. **A probe that cannot run injects nothing** and posts one `[Friction]`: reporting an absence nobody measured is the exact defect this exists to prevent (lens T1-S11, where a coder declined to verify its rendering because "there is no Node/Chromium in the sandbox" — the image had node 20, playwright 1.62 and chromium, and had already driven that browser to produce the screenshots under review). Prompt rendering itself performs no I/O; it reads the primed cache, which is what keeps `make check` hermetic.
- **Coder handoff salvage (#114).** The coder gets one non-interactive turn per round and must end by writing its handoff file; a turn that ends cleanly *without* one normally fails the round. To avoid discarding completed work when an agent strands its turn (the observed case: it backgrounds a slow suite and stops before the handoff step), the orchestrator re-prompts the coder **once** — only when the turn exited **cleanly** and left **uncommitted** changes in the worktree (there is real work to save) — to write just the handoff, then re-checks. Recovered → the round proceeds normally (commit → gate → review); still missing → it fails as before (`no coder handoff file`). Exactly one extra turn, always on, no config. (The coder prompt already forbids backgrounding-and-waiting (#115); this net recovers the cases that slip through.)
- **Reviewer artifact salvage (#298).** A reviewer turn that **fails** after writing a valid handoff for the round — the observed class: engine-infra deaths (auth 401 token revocation, websocket stream disconnect) landing after the review was already written — no longer terminally fails the run as `reviewer handoff invalid`. After a failed turn (initial or correction retry) the orchestrator re-reads the round's handoff; if it parses **and** passes the finding-lifecycle validation, the artifact is authoritative and the round proceeds (the failed turn is still recorded as a failure fixture, preserving the classification-capture trail). Salvage is **provenance-guarded**: the handoff is content-fingerprinted before each attempt, and only a file the failed attempt *itself* created or rewrote is eligible — a stale valid file left by an earlier attempt (a usage-limited attempt before a tool-switch or pause retry, or a prior dispatch resuming into the same round) is never accepted. **Usage-limited** turns are excluded — the usage-limit reaction (tool switch / budgeted pause) owns those. A **clean** turn whose handoff stays invalid after the one correction re-prompt still fails as before: that is reviewer output, not infra. The reviewer-side sibling of the coder handoff salvage above.
- **Failure reactions (slice B of the needs-human arc, task 5dbeb0c8; closes #298 / #277 part 1 / #103).** Every agent turn — the coder's, each reviewer's, the #114 handoff nudge — runs through one wrapper (`agent_session.turn_with_reactions`) that classifies a failed turn over the **whole** turn (result text + stderr + the retained structured payload: codex `failure_events`, a claude API error's status, or unparseable stdout kept verbatim in `raw["unparsed_stdout"]` — the #405 shape printed the 401 as a bare line before the JSON and the old parser dropped it) into one closed vocabulary and applies a per-class reaction table:

  | class | signal | reaction |
  |---|---|---|
  | `usage_limited` | the provider limit wordings (incl. a codex `usage_limit` event) | pause within the shared budget / tool-switch (T5, unchanged) |
  | `auth_failed` | `Failed to authenticate`, OAuth session expired / token revoked, `authentication_failed`, a 401, an invalid key, `Not logged in · Please run /login` (#382) | **one** retry after 20 s, the host's CURRENT auth file first written into the container's bind-mounted inode in place via `docker exec -i … cat >` (#403: the single-file mount pins the inode at container start and the CLI refreshes by rename-replace, so a container alive across any host-side token refresh — another claude process, the eval judge — keeps reading the pre-refresh token; the 2026-09-12 lens#82 loss and the 2026-09-15 lens78 reviewer death were this, the host's credentials valid throughout), then escalate — the host action then names a real re-authentication |
  | `transient_infra` | stream disconnect, websocket idle timeout, `ECONNRESET`/`ETIMEDOUT`/…, 5xx / 429 / overloaded, a provider's "at capacity" refusal (#419) | retry after 30 s then 120 s, then escalate |
  | `oom_or_spawn` | exit 137; a container the turn site's post-failure probe finds stopped or gone (`docker inspect`, #412 — the docker daemon restarted under the turn: exit 255, no text; decided before any text is read, like exit 137); `container … is not running`, `No such container`, `OCI runtime exec failed`, out of memory | one retry after 10 s, then escalate — the `[Friction]` a converge run's `infra_failed` leaves names the run's branch, so a fix the coder had committed before the host died is recoverable |
  | `timeout` / `agent_error` | the per-turn wall clock; anything unrecognised | the plain failure path (never mis-pause, never mis-retry) |

  A retry resumes the same session with a continuation prompt when its transcript survived, else re-issues the original prompt fresh; retry counts are per class; backoff never spends the pause budget; every failed attempt is recorded as a fixture. Salvage runs **before** classification at every site: a reviewer whose failed turn wrote a valid handoff (#298) and — new — a **coder** whose failed turn wrote this round's handoff (provenance-guarded by a pre-turn content fingerprint, infra classes only) proceed on the work product; the ordinary failure path judges everything else. When a retry class is exhausted the run ends **`infra_failed`** — its `failure_reason` names the agent, the class, the attempts, the failure and the host action ("log the agent CLI in on the host … then complete the gate to re-dispatch", plus — for `auth_failed` — whether the credentials were re-synced from the host before the retry, #403) and the daemon maps it to `failed` / `environment` / `retriable` / `escalation.reason=infra` (the needs-human gate). The recorded fixtures live under `tests/fixtures/agent_failures/` (the captured lens#82 OAuth death, the lens#89 docker-restart exec death, the lens 28105098 codex capacity refusal (#419), plus labelled synthetic shapes); a new real failure is promoted from the run's `failures/` dir into that corpus and the pattern table — never guessed.
- **PR body composition (f6babfd8 security/f-004).** The generated body is *what* (the story description) / `Closes #N` / *acceptance criteria* / *review* (verdicts, rounds, test gate, agent cost, Lithos task), plus the `## Provenance` section a hand delivery adds (§4.15c) — one builder (`pr_delivery.build_pr_body`) for the daemon's delivery and `develop deliver` alike. **Every section loom did not author is published fenced**: the coder's handoff quote, *and the story's own description + acceptance criteria* — for a story the github-issue watcher materialised those are the GitHub issue body an outside reporter wrote (the mirror creates the task with `description = issue.body`, §2.2; delivery re-reads the story live). A PR description is live markup opened under the operator's `gh` identity, and a rewrite pass over arbitrary markdown can only ever enumerate the constructs it knows — GitHub autolinks a bare url, `~~~` opens a fence exactly like ``` does, and every reference link form (`[label][ref]`, `[ref][]`, `[ref]`, `![alt][ref]`) hides its target in a definition that renders as nothing. So each section goes in a **code block whose fence is measured against its own content** (one backtick longer than the longest run inside it): nothing in it renders, and no line of it can close the block early and splice live markup into the sections loom composes after it — the panel verdicts the operator merges on, and loom's own `Closes #N`, which an unclosed `~~~` would otherwise switch off entirely (a PR that silently stops closing its source issue on merge). Each section is **bounded** too (8000 characters of quoted content, the explicit `(truncated …)` marker's room reserved *inside* that cap rather than added on top of it, the whole text staying on the story) — at the **input**, before a single pattern runs, as well as at the result, and counted in characters the section can actually carry: whatever the pipeline drops or collapses anyway — the invisibles, a fence run — comes out **before** the input cut, since padding with something that never reaches the page would otherwise be the cheapest way to publish a section that is nothing but the truncation marker. **Whitespace is not in that set and is never normalised**, at the section's edges as well as between its words: a code block preserves every space, tab and blank line, so deeply indented code, an exact-output fixture or an ASCII diagram is the reporter's content, not padding — acceptance criteria that *open* on an indented line keep that indentation, and a final line keeps its trailing spaces. Whitespace that exceeds the budget is cut and marked `(truncated …)` like any other text, never quietly squeezed to fit; a section that is nothing *but* whitespace carries nothing and is published as no section at all. The bound itself is what matters: a GitHub issue body may be 64 KiB and GitHub rejects a PR body over the same limit, so an unbounded section would let a reporter fail `gh pr create` for every delivery of the story they filed, and an unbounded *pattern input* lets that same author choose how much of the delivery path's CPU their issue body costs. Inside the fence the text is **also defanged** (`publish_text.defang_markup`, belt-and-braces for the machines that re-ingest the body rather than render it — an LLM reviewer, the external-review sweep): closing keywords in every form the parser honours (`#12`, `GH-12`, `owner/repo#12`, the issue url, emphasised, `&nbsp;`-separated, reference-wrapped), `@`-mentions, tag-opening `<` (inline HTML — a hidden `<!-- … -->`, an `<img>` beacon), the `](` of every inline link or image and the `]:` of every link-reference definition (the one sequence each family cannot be written without — so a nested label, a backslash-escaped `]` inside one, or a blockquote / list prefix is no way past, and the rule stays a fixed-width match rather than a scan over an author-sized label), backtick **and** tilde fence runs, and every invisible character (the C0/C1 controls, the line / paragraph separators, the interlinear annotators, and Unicode's `Default_Ignorable_Code_Point` property in full — the bidi formatters, the zero-width and filler code points, the variation selectors, the U+E0000 tag block — kept as a table of named code-point blocks so it can be checked against that property rather than drifting from it — and as the ONE definition, imported by `cli/_deliver_facts.sanitize_for_terminal`, `cli/develop._sanitize` and `plugins/story_develop/handoff.sanitize_agent_text` rather than copied into each, since the copies that were declared identical by comment had in fact drifted) are each rewritten so the text still reads the same and binds nothing — never by a code span, whose backticks the text's author controls. The same rule is the SOLE defence on the one place a fence will not do, `develop deliver`'s one-line provenance bullet (§4.15c). The `Closes #N` line loom composes itself from the story's `metadata.github_issue_url` is the only live closing keyword in the body.
- **PR title composition (security/f-001).** The **title** is the other half of the same boundary and gets its own rule, `publish_text.publish_title` — shared by the daemon's `pr_delivery.deliver()` and `develop deliver` so the two cannot drift. For a mirrored story the title is the external issue's title (the watcher creates the task with `title = issue.title`), and a PR title is not inert: with the repo default squash-merge message (`COMMIT_OR_PR_TITLE`) a **multi-commit** PR — and loom's are deliberately multi-commit — takes its commit *subject* from the PR title, and GitHub honours closing keywords and `@name` in commit messages on the default branch. That is raw text, so no fence reaches it: an issue titled `Closes #1 parser crashes` would otherwise close issue #1 under the operator's account on merge with nothing in the body to show why. `publish_title` takes the **first line — chosen before the text is trimmed**, since the argument is the whole task text (`title\n\nbody`) and trimming first would let a story with an empty issue title publish the first line of the issue *body* as its PR title — strips the invisibles (`CONTROL_CHARS_RE` — otherwise they reorder the PR list, the notification email and the commit subject), gives a closing keyword the same `→` the body's defang gives it, puts a space behind a mention's `@`, and caps the result at 90 characters (a non-positive cap raises). A title that comes back **empty** — an issue titled with nothing but default-ignorable code points leaves one — falls back to the **branch name** on both paths: `gh pr create` rejects an empty title, which would otherwise fail every delivery of that story after the branch was already pushed. Separators, **not entities**: a title is plain text rather than markdown, so the body's `&#64;` / `&lt;` rewrites would be published literally.
- **Operator notification on delivery (#113).** When `[story_develop].operator_github_login` (§3.1) is set in daemon mode (or `--notify-github-login` is passed standalone), a delivered PR requests that user as a GitHub reviewer so native email/web/mobile notifications fire. If they **authored** the PR — the usual case, since loom runs under the operator's own `gh` auth and GitHub rejects a self review-request with HTTP 422 — it falls back to **assigning** the PR to them (allowed for self, still notifies). The run summary records "requested review from / assigned to `<login>`". Best-effort: a failure is noted, never fatal. Unset → no notification (the PR still lands in the operator's own PR list).

The `[story_develop].default_models` layer (§3.1) is a **host-wide, per-tool** default model read from the loom TOML: it fills any agent (coder or reviewer) the layers above left unset, keyed by that agent's resolved `tool`. It is per-tool rather than per-role so a heterogeneous panel (#94) picks the right default for each agent (a codex reviewer and a claude coder draw from different keys). There is no analogous global default for `effort` — an unset level means each CLI's own default depth.

**Explicit-model policy (#304).** There is no "agent default" tail below the `default_models` layer any more: an agent that would still run with `model=None` after every layer **fails the run closed before any container starts** — daemon mode reports it as a do-not-retry `config` failure through `result.json`; `develop review` / `develop converge` exit with a usage error; the eval harness rejects the whole invocation pre-paid (§4.16). Rationale: the fallback was the sandbox image CLI's builtin default — a value recorded nowhere that drifts with image rebuilds and silently changed what benchmark arms measured (#303). The policy covers the folded-in built-in `code-quality` reviewer too, and extends to **usage-limit fallback chains**: a reviewer's `model` belongs to its PRIMARY tool only, so after an engine switch the replacement engine draws its model from `default_models[<new tool>]` (a claude model string must never reach `codex -m`) — every reachable, supported fallback-chain tool must therefore have a per-tool default, validated up front with the same fail-closed error. The error names each offending agent and its tool; the fix is a `[story_develop.default_models]` entry for that tool (or any higher-priority per-agent pin).

## 6. Event Bus Contract

### 6.1 Event Schema

```python
@dataclass(frozen=True)
class Event:
    type: str  # dotted name, e.g. "lithos.task.created"
    timestamp: datetime  # UTC; when the source published the event
    payload: Mapping[str, Any]  # event-type-specific; see §6.4
```

Events are passed by reference through the in-process bus. Subscribers must not mutate the payload.

### 6.2 Filter Language

Each `[[subscriptions]]` stanza may carry both filters; an event passes when both hold (logical AND):

- **Structural `match.<key>` tables.** A `match.tags = ["X", "Y"]` requires the event payload's task / note to carry every listed tag (superset semantics). Other `match.*` keys check equality on the named payload field.
- **`where = "<python-expression>"`.** The expression is evaluated in a restricted scope exposing `event` (the Event object) and `task` (= `event.payload` for task events). Only safe builtins are available; no imports, no attribute lookups outside the allowed names.

`match` runs first as a cheap structural filter; `where` runs on the survivors.

### 6.3 Dispatch Semantics

- **Concurrent fire-and-forget.** Each subscription has a bounded async queue; events dispatched to a full queue increment a drop counter and emit a WARNING log line. Slow subscribers do not block fast ones.
- **Per-subscription retry.** Failure raises an exception; the runner sleeps `initial_delay` then retries with `exponential` (or `linear`) backoff up to `max_delay`. After `attempts` exhausted, `on_persistent_failure = "friction"` posts a `[Friction]` finding to the related task; `"ignore"` suppresses.
- **Idempotency is the handler's responsibility.** Handlers must be safe under replay (cold-start re-emission, network reconnect with `Last-Event-ID`, daemon restart). Pre-check before mutating Lithos state.

### 6.4 Event Catalog

Payloads are dicts; the exact key set depends on the source. Task-event payloads are the Lithos task envelope as returned by `lithos_task_list` / `task_status` (fields like `id`, `title`, `status`, `tags`, `metadata`, `claims`, and lifecycle timestamps such as `resolved_at`). Note bootstrap events are intentionally minimal (`{id, title, path}`); subscriptions that need the full body or tags re-fetch via `lithos_read`. Subscriptions should treat payloads as opaque dicts and look up specific keys defensively — additional fields may be present and field absence depends on the underlying Lithos response.

## 7. Obsidian Projection

### 7.1 File Layout

```
<vault_path>/
├── <tasks_file>                              # default: _lithos/tasks.md
├── <projects_dir>/                           # default: _lithos/projects/
│   ├── <slug>/
│   │   ├── <slug>-project-context.md         # canonical project doc (per Lithos KB convention)
│   │   ├── <other-file>.md                   # any additional project-context-tagged doc
│   │   └── <slug>-done.md                    # task-archive's append-only history (vault-only)
│   └── _unassigned/
│       └── _unassigned-done.md               # archive bucket for tasks with missing metadata.project
└── _lithos/conflicts/                        # note-push conflict snapshots
```

All writes use a dot-prefixed temp file (`.<filename>.tmp.<rand>`) plus `os.replace` for atomicity. The dot prefix matters: Obsidian Sync (and Dropbox-style observers) skip dotfiles, avoiding a publish noise.

### 7.2 Tasks-Plugin Line Shape

Open-task line:

```markdown
- [ ] <title> 🆔 lithos:<id> [#project/<slug>] [#lithos/<route-name>] [⛔ lithos:<dep_id>...] [🔺⏫🔼🔽⏬] [📅 YYYY-MM-DD]
```

Resolved-task line (completed / cancelled):

```markdown
- [x] <title> 🆔 lithos:<id> [#project/<slug>] ✅ YYYY-MM-DD
- [-] <title> 🆔 lithos:<id> [#project/<slug>] ❌ YYYY-MM-DD
```

The renderer always emits fields in this exact order. Priority, deps, and due-date markers are dropped on resolved lines; the resolved-date marker is always last so the Tasks plugin's `sort by done date` / `done after` filters parse correctly. Operator-side tags from `task.tags` are NOT rendered today.

| Token | Meaning | Source | Direction |
|---|---|---|---|
| `[ ]` / `[x]` / `[-]` | Status: open / completed / cancelled | `task.status` | Bidirectional. `[/]` and `[>]` are detected on read, no-op on write. |
| `🆔 lithos:<id>` | Task ID | `task.id` | One-way (identity; never edited by operator). |
| `#project/<slug>` | Project tag | `task.metadata.project` | One-way. |
| `#lithos/<route-name>` | Active human-blocking claim's route | route lookup based on the active claim | One-way; surfaces while a human-blocking route holds the claim. |
| `⛔ lithos:<blocker_id>` | One marker per Lithos blocker naming another task (US8) | `lithos_task_blocked` | One-way (Lithos canonical). |
| `🔺⏫🔼🔽⏬` | Priority (highest / high / medium / low / lowest) | `task.metadata.priority` | Bidirectional. Absent emoji = no priority. |
| `📅 YYYY-MM-DD` | Due date | `metadata.scheduled_for` if set; else `today` for human-blocking tasks; else absent | Bidirectional via `metadata.scheduled_for`. |
| `✅ YYYY-MM-DD` | Completed date | `task.resolved_at` | One-way; only rendered for `[x]` lines within TTL. |
| `❌ YYYY-MM-DD` | Cancelled date | `task.resolved_at` | One-way; only rendered for `[-]` lines within TTL. |

### 7.3 Projection Filter

A task is projected when `is_human_actionable(task, routes)` returns true:

- The task is `open`, AND
- It is **not a non-`human` gate** — a `pr` / `timer` / `ci` / `external_task` gate is resolved by an automated poller, not the operator, so a `task_type="gate"` task projects **only** when `metadata.gate_type == "human"` (the one gate kind whose resolution *is* a human ticking a box). A `pr` gate must not land in `tasks.md` as a `- [ ]`, because ticking it from the obsidian-sync child would complete the gate and re-develop merged work. An **`epic`** is deliberately *not* filtered — unlike a gate, ticking an epic is the intended manual roll-up (epic completion stays manual until the extension's Phase 4), so it stays projected via the orphan rule below. AND
- Either (a) no `[[routes]]` matches the task's tags, OR (b) a route matches AND that route has `human_blocking = true` AND the route currently holds the claim.

Dependency-blocked tasks still project (with the `⛔` marker); the Tasks plugin's own queries decide whether to surface or hide them.

Tasks with terminal status (`completed` / `cancelled`) project with `[x]` / `[-]` and the corresponding `✅` / `❌` date marker, lingering until either (a) the `task-archive` subscription evicts them on the next flush after archiving, or (b) `resolved_ttl_days` elapses since `resolved_at`.

### 7.4 Project-Context Projection

Each `project-context`-tagged note under `projects/` projects to one file at `<vault>/<projects_dir>/<slug>/<filename>.md`, where:

- `<slug>` = the directory name under Lithos's `knowledge/projects/<slug>/`.
- `<filename>` = the slug of the doc's `title` (Lithos slugifies title → filename).

Frontmatter envelope:

```yaml
---
lithos_id: <uuid>
lithos_version: <int>
lithos_updated_at: <ISO 8601>   # omitted when the note has no updated_at
slug: <directory-name>          # omitted when the note has no slug
status: <whatever Lithos returned>   # omitted when null; common values: active, archived, quarantined
tags:                           # omitted when empty
  - project-context
  - ...
---
# <title>

<body>
```

Key order is stable (`lithos_id` → `lithos_version` → `lithos_updated_at` → `slug` → `status` → `tags`). Optional rows are omitted entirely rather than rendered as `null` or `[]`. `status` is whatever Lithos returned for the note — Loom passes it through verbatim. The body below the frontmatter is the Lithos doc body, prefixed with `# <title>`. Frontmatter is daemon-managed; operator edits to frontmatter fields are not pushed back. Body edits are pushed via `note-push` (see §7.5).

Filename migration: if Lithos changes the doc's title (changing the slug), the projection writes the new path first, then unlinks the old path. Order matters — a failed new write leaves both copies on disk rather than losing the content.

### 7.5 Bidirectional Note Push

`ObsidianDirWatcher` polls projected files. When the body-only hash diverges from the projection's last write, it emits `obsidian.note.modified` with the operator's body and the current local `lithos_version`. `note-push`:

1. Fetches canonical via `lithos_read(id)` for current title / tags / status.
2. Calls `lithos_write(id, content=body, expected_version=local_version)`.
3. On `status=updated`: re-fetches via `lithos_read` to refresh the local frontmatter (`lithos_version`, `lithos_updated_at`).
4. On `status=version_conflict`: invokes the conflict resolver — moves the operator's body to `<vault>/_lithos/conflicts/<slug>.<file>.<ts>.md`, writes canonical to the original path, logs `[Friction]` WARNING.
5. On `status=duplicate`: no-op (Lithos detected the body is identical to canonical).

**Frontmatter-only edits are silently absorbed.** The watcher hashes the body only; adding a custom YAML field (e.g. a Dataview field) does not trigger a push. Custom fields persist until the next projection rewrite, at which point the renderer reconstructs frontmatter from scratch and the custom field is lost. This is by design — frontmatter is daemon-managed.

**Cold-start divergence.** If the daemon was down while the operator edited a projected file, the bootstrap projection detects the local-vs-canonical body diff and routes through the same conflict resolver (operator's body preserved in `_lithos/conflicts/`, canonical pulled to the original path).

### 7.6 Per-Project Task Archive

When `task-archive` is configured, the `obsidian-projection` handler also marks tasks as "surfaced" in an in-memory map whenever it writes a task line. On `lithos.task.completed` / `lithos.task.cancelled`, the `task-archive` handler:

1. Skips tasks that were never surfaced (background / route-claimed-only work).
2. Resolves the target file from `task.metadata.project`; falls back to `_unassigned-done.md` if missing or unknown.
3. Renders one Tasks-plugin line (terminal-status drops priority + due-date markers; `✅` or `❌` carries `task.resolved_at`).
4. Dedups against existing lines in the file (lazy-read on first event per project).
5. O_APPEND writes the line.
6. Marks the task as archived so the projection evicts it from `tasks_file` on next flush.

The done file is **vault-only and append-only** — the dir-watcher excludes the `-done.md` suffix so operator edits are inert. Deleting a done file can be recovered with `project regenerate-done` (which rebuilds from Lithos, all-resolved-tasks superset).

### 7.7 Filter Knobs

- **`include_blocked`** (default `true`): when `false`, tasks **Lithos reports as blocked** are not projected.

**Blocked-ness in the projection (Epic G / US8).** The ⛔ markers and the `include_blocked` gate read Lithos's authoritative blocked set via `lithos_task_blocked`, not `metadata.depends_on`. That list records what a task *declared*, so it stayed true forever — a ⛔ persisted long after its dependency completed, and `include_blocked = false` hid a task that nothing was actually waiting on. The set is swept **once per flush cycle** (the restart bootstrap re-emits every open task, and a burst renders into one file write anyway), so a change landing mid-burst is picked up on the next cycle. A sweep failure degrades to "nothing blocked" and logs — the projection is a display, and a missing marker beats a missing task. `lithos_task_blocked` has no per-task filter and no cursor, so the sweep is capped at `BLOCKED_QUERY_LIMIT` (500 — the projection's own knob, distinct from the runner/dry-run `READY_QUERY_LIMIT` so it can be raised independently, since US11) and a **full page** means the set is truncated: tasks beyond the cut render without ⛔ and slip past `include_blocked = false`, and a WARNING says so. This sweep is unnarrowed (it spans every project), so it is the likeliest of the three to truncate. The degradation deliberately *differs* from the runner's (§2.2): there, one direction is plainly unsafe (dispatching a task whose blocker is still open), whereas here both are display errors — so the tiebreak is recoverability. Hiding an actionable task makes it vanish from the vault with nobody able to notice; showing a blocked task is visible and ignorable. Hence: **hide only on positive evidence of blocked-ness, never on inferred unblocked-ness.** Markers are emitted only for blockers naming *another* task: ⛔ references another line's 🆔, so a `cycle` blocker (which names the task itself) has nothing valid to point at. Gate blockers — invisible to the old metadata mirror — now render.
- **`exclude_tags`** (default `[]`): tasks carrying any listed tag are not projected. Useful for suppressing automation noise (e.g. `["influx:run", "influx:backfill"]`).
- **`resolved_ttl_days`** (default `7`): how long resolved tasks linger in `tasks_file` when `task-archive` is NOT configured, OR (when `task-archive` IS configured) the bootstrap-replay window the archiver looks back over on restart.

## 9. Errors and Exit Codes

CLI commands use a unified exit code convention:

| Code | Meaning |
|---|---|
| `0` | Success (or clean user abort at a `--yes`-gateable prompt). |
| `1` | Operational failure — Lithos call failed, config load failed, slug collision, missing project, partial-import failure, network unreachable. |
| `2` | Input validation failure — invalid flag combination, unknown project, unknown priority, malformed task lines, cross-project tag, empty parent, `lithos_id` / `--slug` mismatch, unreadable source file. |

`lithos-loom run` exits `0` on clean shutdown (a completed drain included), non-zero on child crash or SIGKILL after timeout, `1` when a live daemon already holds the work dir's pidfile or its lock cannot be established. `lithos-loom drain` exits `0` when the daemon exited, `1` when there was no daemon to signal, `2` when `--timeout` ran out with the daemon still draining (§4.1a).

### 9.1 Common Validation Failures

- **`unknown project '<slug>'`** (exit 2, `task create`): the `--project` value isn't in the union of (a) slugs from `lithos_list(path_prefix='projects/', tags=['project-context'])` and (b) the TOML `[projects.<slug>]` registry. The TOML side lets a host run capture against a slug that hasn't yet been promoted to a project-context doc in Lithos.
- **`unknown priority '<value>'`** (exit 2, `task create`): `--priority` must be one of `highest|high|medium|low|lowest`.
- **`--target-file and --no-insert are mutually exclusive`** (exit 2, `task create`).
- **`slug '<X>' already exists at doc <id>`** (exit 1, `project create`): refuses to overwrite. Use `project import --tasks-only --slug <X>` if you wanted to add tasks instead.
- **`no project at slug '<X>'`** (exit 1, `project import --tasks-only`): includes near-miss suggestions when typo distance ≤ 2.
- **`lithos_id resolves to project Y; --slug=X; refusing`** (exit 2, `project import --tasks-only`): the source file's frontmatter `lithos_id` points at a different project than `--slug`.
- **`obsidian_sync.vault_path must be a non-empty path string`** (exit 1, validate-config): the `[obsidian_sync]` block is malformed.
- **`tasks_file must be relative to vault_path`** (exit 1, validate-config): absolute paths in `tasks_file` are rejected.

### 9.2 Runtime Failures

- **`plugin <pid> did not honour SIGTERM within 5.0s; sent SIGKILL`** (route-runner WARNING): the plugin exceeded `max_runtime_seconds` and didn't shut down. The claim is released and `[BlockerFailed]` is posted.
- **`plugin contract violation: did not write <path>`** (route-runner WARNING): the plugin exited but no `result.json` exists. `[BlockerFailed]` posted; claim released.
- **`note-push conflict for doc=<id>`** (note-push `[Friction]`): operator and Lithos both edited the doc; the operator's body is preserved at `_lithos/conflicts/<slug>.<file>.<ts>.md`, canonical was pulled to the original path.
- **`obsidian-projection: skipped <slug>: no project-context doc in Lithos`** (doctor): TOML registers a slug Lithos doesn't know. Either create the doc in Lithos or remove the TOML stanza.

## 11. Multi-Host Deployment

The vault host (typically a workstation with Obsidian) runs the full daemon — the supervisor spawns both route-runner and obsidian-sync children. Other hosts (additional workstations, headless servers) run with `[obsidian_sync]` omitted; the supervisor spawns only the route-runner child.

There is no inter-host coordination. Each host:

- Registers as `lithos-orchestrator-<host>` via `orchestrator.agent_id`.
- Reads its own TOML config (different `[projects.<slug>]` registry, different routes).
- Claims tasks competitively via `lithos_task_claim` (Lithos guarantees collision safety).

Per-project automation (the `[projects.<slug>].repo` field) is host-specific. If host A doesn't have the repo checked out, it can't claim tasks for that project. Project existence is a Lithos fact (the project-context doc); project automation is a host fact (the TOML entry).

Obsidian Sync (the app) handles delivering the vault to the operator's secondary devices (laptop, phone). Loom doesn't see those devices.

## 12. Not Implemented

The following are absent from the current surface. Some are explicit non-goals; others are queued in `docs/prd/`. Listed here so readers don't go looking.

- **Plugin body for `prd-decompose`.** Scaffolding under `src/lithos_loom/plugins/`; no real logic.
- **Application of `result.json` fields beyond `status`.** `metadata_updates`, `artifacts`, `commits`, `spawned_tasks`, `exit_code`, `error.retriable` are schema-validated but not used by the runner today (§5.2).
- **`orchestrator.max_concurrency` enforcement.** Parsed and stored but never read at runtime — there is no global cap on concurrent plugin runs. A single route runs its tasks serially; multiple routes run concurrently without contending. Tracked in [#85](https://github.com/agent-lore/lithos-loom/issues/85).
- **Resolved project entry in `task.json`.** Plugins receive `{"task": <payload>}` only.
- **Startup reclaim of stale claims.** Claims age out via Lithos's own TTL; the route-runner does not actively release them on startup.
- **Hot-reload of TOML config.** Operator restarts the daemon.
- **Persistent event log.** Restart relies on source re-authority + subscriber idempotency.
- **Containerised daemon.** Loom runs as a host process; Lithos and adjacent services may run in docker.
- **Other planned work** (`prd-generate`, agent-driven reviews, brain, `merge-stories`, A2A endpoint, GitHub issue watcher, multi-host PRD-affinity, docker sandbox, cost tracking). See `docs/prd/` for PRDs.

## Appendix A: Worked Example — Capture a Task from Obsidian

1. Operator highlights "Review staging deploy" in any note, fires the capture-task hotkey.
2. The Templater macro shells out to `lithos-loom project list --format json` to populate the project dropdown, and `lithos-loom obsidian-sync show --format json` to learn the configured `tasks_file` path.
3. Modal opens; operator selects project `lithos-loom`, optionally fills priority and tags, submits.
4. Macro shells out to `lithos-loom task create --project lithos-loom --title "Review staging deploy" --no-insert`; CLI prints the new task_id.
5. Macro inserts a wikilink at cursor: `[[_lithos/tasks.md|Review staging deploy]] 🆔 lithos:<id>`.
6. Meanwhile: Lithos broadcasts `task.created` via SSE → the daemon's `LithosEventStream` receives it → `obsidian-projection` re-renders `<vault>/_lithos/tasks.md` with the new line.
7. Total elapsed: ~250–500ms from submit to projected line landing.

## Appendix B: Worked Example — Bidirectional Project-Context Edit

1. Operator opens `<vault>/_lithos/projects/lithos-loom/lithos-loom-project-context.md` in Obsidian and edits the body.
2. Saves. `ObsidianDirWatcher` polls every 250ms; on next tick, the body hash diverges from `sync_state.note_body_hashes[doc_id]`.
3. Watcher emits `obsidian.note.modified` with the operator's body and the local `lithos_version`.
4. `note-push` calls `lithos_write(id, content=body, expected_version=local_version)`.
5. Lithos returns `status=updated` with the bumped version.
6. `note-push` calls `lithos_read(id)` to refresh `lithos_version` and `lithos_updated_at` in the local frontmatter.
7. The dir-watcher detects the post-write file change but matches it against its last-known mtime + content hash → suppresses as a self-write.

If a separate agent had pushed a body change between steps 1 and 4, step 5 would return `status=version_conflict`. The resolver moves the operator's body to `_lithos/conflicts/lithos-loom.lithos-loom-project-context.<ts>.md`, writes canonical to the original path, and posts a `[Friction]` WARNING. The operator can diff the two files to recover their edit.
